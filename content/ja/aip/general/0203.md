# フィールド動作の文書化

protocol buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（必須かどうか、オプショナルかどうかなど）をユーザーに説明することが慣例である。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは、フィールドが必須であるか、immutableであるかといった、よく理解されたフィールド動作を記述するために`google.api.field_behavior`アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の`etag`フィールドは、いかなる`google.api.field_behavior`も割り当てる**べきではない**（should not）。
  - さらに、`oneof`フィールドは`google.api.field_behavior`を省略**してもよい**（may）が、この場合、コメント内で特定の動作を文書化**すべきである**（should）。
- アノテーションは、フィールドの動作を正確に記述するすべての[google.api.FieldBehavior][]値を**含まなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは最低限、`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存している。新しいフィールドを追加する際には、どの値が関連するかを慎重に確認し検討すること。

アノテーションのないフィールドは、後方互換性のために`OPTIONAL`として解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提示される語彙は*記述*目的のみであり、それ自体がバリデーションを追加するものではない。目的は、この動作をクライアントに一貫して文書化することである。

### ネストされたメッセージのfield behavior

ネストされたメッセージの`google.api.field_behavior`アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージのフィールド動作が`REQUIRED`であり、親フィールドが`OPTIONAL`である場合がある：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されている場合、`text`フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは`name`フィールドに付加**しなければならず**（must）、他のフィールドに付加**してはならない**（must not）（[リソース名を表現するフィールド][fields representing resource names]を参照）。

`IDENTIFIER`の値は、そのフィールドが作成メソッドのコンテキストでは入力として受け入れられず（すなわち`OUTPUT_ONLY`）、同時に`IMMUTABLE`とみなされ、リソースを主入力として受け取る変更メソッド（例：[標準Update][aip-134]）の入力として受け入れられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableなフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はフィールドを無視**すべきである**（should）が、変更が要求された場合は`INVALID_ARGUMENT`でエラーと**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- アプリケーションのライフタイム中に変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにはimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、名前が通常`Request`で終わるメッセージ）内のフィールドは、これが既に暗示されているため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- AIP-214で説明されている`ttl`フィールド。

**警告:** input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常`Request`で終わるメッセージ）内のフィールド、またはサブメッセージ内のフィールドである場合、optionalとして記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル`optional`とフィールド動作`OPTIONAL`は相互排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにそのフィールドを含めても何も行われないことを示す（サーバーはこのフィールドの値をすべてクリア**しなければならず**（must）、入力時のこのフィールドの値の存在の結果としてエラーをスロー**してはならない**（must not））。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（AIP-161を参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、または下位のメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常`Response`で終わるメッセージ）内のフィールドは、これが既に暗示されているため、output onlyとして記述**すべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソース上に存在し**なければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエスト上でそのフィールドの値を**提供しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドマスクにもそのフィールドが存在せず、フィールドへの変更がないことを示す場合に限り、そのフィールドを省略**してもよい**（may）（そうでない場合は、値を**提供しなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、通常`Request`で終わるメッセージ）内のフィールドである。この場合、値はリクエストの一部として**提供しなければならず**（must）、提供しなかった場合はエラー（通常`INVALID_ARGUMENT`）を**発生させなければならない**（must）。

上記の「truthy」という用語を次のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false`以外の値
- 繰り返しフィールドとマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つ任意のメッセージ

以下のことを示すためにフィールドをrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きでrequiredとなるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブーリアンの`false`、整数の`0`、enumの未指定値など）は未設定の値と区別がつかないため、requiredフィールドにfalsyな値を設定するとエラーとなる。このことからの帰結として、requiredなブーリアンは`true`に設定**しなければならない**（must）。

### Unordered List

リソースの繰り返しフィールドに対する`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、unordered listとして記述**すべきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよく**（may）、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`の値の追加または変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味的な変更を表す可能性がある。以下は、`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前`OPTIONAL`とみなされていた（暗黙的またはその他）既存のフィールドへの`REQUIRED`の追加
* 既存のリクエストメッセージへの`REQUIRED`としてアノテーションされた新しいフィールドの追加
* 以前入力として受け入れられていた既存のフィールドへの`OUTPUT_ONLY`の追加
* 以前出力として出力されていた既存のフィールドへの`INPUT_ONLY`の追加
* 以前可変とみなされていた既存のフィールドへの`IMMUTABLE`の追加
* 以前入力として無視されていた既存のフィールドからの`OUTPUT_ONLY`の削除
* 既存のフィールドからの`IDENTIFIER`の削除

後方互換性の*ある*変更もあり、以下の通りである：

* 既存のフィールドへの`OPTIONAL`の追加
* 既存の`name`フィールドへの`IDENTIFIER`の追加
* 既存のフィールドでの`REQUIRED`から`OPTIONAL`への変更
* 既存のフィールドでの`OUTPUT_ONLY`または`IMMUTABLE`（あるいはその両方）から`IDENTIFIER`への変更
* 既存のフィールドからの`REQUIRED`の削除
* 以前レスポンスで除外されていた既存のフィールドからの`INPUT_ONLY`の削除
* 以前immutableとみなされていた既存のフィールドからの`IMMUTABLE`の削除

## 根拠

### Identifierフィールド動作

リソース名は、準拠するあらゆるリソースの主要識別子であり、作成時にユーザーによって完全に構築されることはない。そのようなフィールドは通常`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、それらはリソース自体が主要なリクエストペイロードであるシナリオでは、主要識別子として消費されることも多い。そのようなフィールドは`OUTPUT_ONLY`とは*みなされ得ない*。さらに、標準Updateのような変更リクエストでは、主要識別子としてのリソース名はその場で変更できない。そのようなフィールドは通常`IMMUTABLE`フィールド動作が割り当てられる。これらの矛盾し文脈依存するフィールド動作は、リソース名フィールドの動作を特定し伝達するために新しい値が必要であることを意味した。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれか**でなければならない**（must）。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドはrequiredまたはoptionalのいずれかであり、したがって少なくともそれぞれ`REQUIRED`または`OPTIONAL`アノテーションを持つべきである。`INPUT_ONLY`のみを提供してもフィールドの必要性を伝えることはできないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラム的なクライアントとユーザーの理解を向上させる。

アノテーションを必須化することは、API作成者がAPIの初期作成時に動作を明示的に考慮することを強制する。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更が生じる可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]内のリソースに後方互換性のない変更が生じる。詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須化された。この変更以前は、アノテーションが省略されることがよくあった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で後からfield_behaviorの値を追加または変更することは、後方互換性がない可能性がある。詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

API作成時にfield_behaviorを必須化することの利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
