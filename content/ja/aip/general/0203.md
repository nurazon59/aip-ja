# フィールド動作の文書化

protocol buffers でフィールドを定義する際、フィールドの動作に関する特定の側面（必須かオプショナルかなど）をユーザーに説明することが慣例となっている。さらに、この動作を他のツールが理解できることは有用である（例えば、クライアントライブラリのシグネチャを最適化するためなど）。

## ガイダンス

API は、フィールドが必須か immutable かなど、十分に理解されているフィールド動作を記述するために `google.api.field_behavior` アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- API は、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを**適用しなければならない**（must）。
  - この例外として、リソースメッセージ上の AIP-154 の `etag` フィールドは、いかなる `google.api.field_behavior` も**割り当てるべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を**省略してもよい**（may）が、その場合はコメントで特定の動作を**文書化すべきである**（should）。
- アノテーションは、フィールドの動作を正確に記述する [google.api.FieldBehavior][] の値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を**使用してはならない**（must not）。
- API は、最低でも `REQUIRED`、`OPTIONAL`、または `OUTPUT_ONLY` のいずれかを**使用しなければならない**（must）。

**警告:** `field_behavior` は proto レベルの動作には影響しないが、多くのクライアント（CLI や SDK など）はコード生成にこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを慎重に検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` と解釈される。それでも、このアノテーションを**省略してはならない**（must not）。

**注:** このドキュメントで示される語彙は*記述的*な目的のみのものであり、それ自体はバリデーションを追加するものではない。目的は、この動作をクライアントに対して一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージが `REQUIRED` のフィールド動作を持ち、親フィールドが `OPTIONAL` であってもよい：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されていれば、`text` フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに**付与しなければならず**（must）、他のフィールドに**付与してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names] を参照）。

`IDENTIFIER` の値は、作成メソッドのコンテキストでは入力として受け付けられず（つまり `OUTPUT_ONLY`）、かつ `IMMUTABLE` とみなされ、リソースを主要入力として受け取る変更メソッド（例：[Standard Update][aip-134]）では入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に**適用してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、必須またはオプショナルのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または同様のもの）で immutable フィールドを受け取った場合、更新マスクに含まれていても、値が一致すればそのフィールドを**無視すべきであり**（should）、変更が要求された場合は `INVALID_ARGUMENT` で**エラーとすべきである**（should）。

immutable フィールドの潜在的なユースケースは以下の通り（これは網羅的なリストではない）：

- アプリケーションの存続期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件的に immutable」なフィールドに immutable アノテーションを**付与してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input only と記述**すべきである**（should）。特に、リクエストメッセージ（RPC の引数としてのみ機能し、通常 `Request` で終わる名前のメッセージ）内のフィールドは、既に暗黙的であるため input only と記述**すべきではない**（should not）。

input only フィールドの潜在的なユースケースは以下の通り（これは網羅的なリストではない）：

- AIP-214 で説明されている `ttl` フィールド。

**警告:** input only フィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPC の引数であり、通常 `Request` で終わる名前のメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、オプショナルと記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細は AIP-149 を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も起こらないことを示す（サーバーはこのフィールドの値を**クリアしなければならず**（must）、入力に値が存在してもエラーを**スローしてはならない**（must not））。同様に、サービスは更新フィールドマスク内の output only フィールドの存在を**無視しなければならない**（must）（AIP-161 を参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーの下位のメッセージのフィールドである場合にのみ、output only と記述**すべきである**（should）。特に、レスポンスメッセージ（RPC の戻り値としてのみ機能し、通常 `Response` で終わる名前のメッセージ）内のフィールドは、既に暗黙的であるため output only と記述**すべきではない**（should not）。

output only フィールドは、API にとって適切であれば空の値に**設定してもよい**（may）。

output only フィールドの潜在的なユースケースは以下の通り（これは網羅的なリストではない）：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に**存在しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみ required と記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである場合。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでそのフィールドに値が**提供されなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクに含まれていない場合（フィールドに変更がないことを示す）に限り、そのフィールドを**省略してもよい**（may）（そうでない場合は**提供されなければならない**（must））。
- RPC の引数であるリクエストメッセージ（通常 `Request` で終わる名前のメッセージ）上のフィールドである場合。この場合、値がリクエストの一部として**提供されなければならず**（must）、提供されなかった場合はエラー（通常 `INVALID_ARGUMENT`）を**引き起こさなければならない**（must）。

上記の「truthy」という用語を次のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、および `false` 以外の値
- repeated フィールドとマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つメッセージ

以下のことを示すためにフィールドを required と**記述すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件的に必須となるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブーリアンの `false`、整数の `0`、enum の未指定値など）は未設定の値と区別がつかないため、required フィールドを falsy な値に設定するとエラーになる。この系として、required なブーリアンは `true` に設定されなければならない。

### Unordered List

リソースの repeated フィールドに `UNORDERED_LIST` を使用することは、サービスがリスト内の項目の順序を保証しないことを示す。

サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、フィールドは unordered list と記述**すべきである**（should）。

unordered list を持つリソースは、リストを安定した順序で**返してもよく**（may）、ランダム化された不安定な順序で**返してもよい**（may）。

## 後方互換性

`google.api.field_behavior` の値を追加または変更することは、既存のクライアントにとって互換性がないと認識される API の意味上の変更を表す可能性がある。以下は `google.api.field_behavior` における後方互換性のない変更の例である：

* 以前に（暗黙的または明示的に）`OPTIONAL` とみなされていた既存のフィールドに `REQUIRED` を追加すること
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加すること
* 以前に入力として受け付けられていた既存のフィールドに `OUTPUT_ONLY` を追加すること
* 以前に出力として出力されていた既存のフィールドに `INPUT_ONLY` を追加すること
* 以前に変更可能とみなされていた既存のフィールドに `IMMUTABLE` を追加すること
* 以前に入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除すること
* 既存のフィールドから `IDENTIFIER` を削除すること

後方互換性が*ある*変更もあり、以下の通りである：

* 既存のフィールドに `OPTIONAL` を追加すること
* 既存の `name` フィールドに `IDENTIFIER` を追加すること
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更すること
* 既存のフィールドで `OUTPUT_ONLY` や `IMMUTABLE` から `IDENTIFIER` に変更すること
* 既存のフィールドから `REQUIRED` を削除すること
* 以前にレスポンスで除外されていた既存のフィールドから `INPUT_ONLY` を削除すること
* 以前に immutable とみなされていた既存のフィールドから `IMMUTABLE` を削除すること

## 根拠

### Identifier フィールド動作

リソース名は、準拠するリソースの主要な識別子であり、作成時にユーザーが完全に構築することは決してない。このようなフィールドは通常 `OUTPUT_ONLY` のフィールド動作が割り当てられる。しかし、これらはリソース自体が主要なリクエストペイロードとなるシナリオでも、主要な識別子として使用されることが多い。このようなフィールドは `OUTPUT_ONLY` とはみなせ*ない*。さらに、Standard Update のような変更リクエストでは、主要な識別子としてのリソース名はその場で変更できない。このようなフィールドは通常 `IMMUTABLE` のフィールド動作が割り当てられる。これらの相反する文脈依存のフィールド動作は、リソース名フィールドの動作を区別して伝えるために新しい値が必要であることを意味した。

### 必要なアノテーションのセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須かオプショナルのいずれかであり、したがってそれぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを**持つべきである**（should）。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションの必須化は、API 作成者が API の初期作成時に動作を明示的に検討することも強制する。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更をもたらす可能性がある。例えば、オプショナルフィールドを必須にすると、RPC のメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023年5月に field_behavior が必須となった。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後に field_behavior の値の一部を追加または変更すると、後方互換性がなくなる可能性がある。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

API 作成時に field_behavior を必須化する利点は、そうしない場合のクライアントと API ユーザーへのコストを上回る。
