# フィールド動作のドキュメント化

Protocol Buffers でフィールドを定義する際、フィールドの動作の特定の側面（required か optional かなど）をユーザーに説明するのが慣例である。さらに、この動作を他のツールが理解できることも有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

API は `google.api.field_behavior` アノテーションを使用して、フィールドが required や immutable であるなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- API は、リクエストで使用されるメッセージまたはサブメッセージのすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - これの例外は、リソースメッセージ上の AIP-154 の `etag` フィールドであり、これには `google.api.field_behavior` を割り当て**るべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合、コメント内で特定の動作を文書化**すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する [google.api.FieldBehavior][] の値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- API は、最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` は proto レベルの動作に影響を与えないが、多くのクライアント（CLI や SDK など）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が適切かを十分に確認し、検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` と解釈される。それにもかかわらず、このアノテーションは省略**されてはならない**（must not）。

**注:** このドキュメントで提示される語彙は*記述的*な目的のみのものであり、それ自体が検証を追加するものではない。その目的は、クライアントのためにこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージに対する `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージのフィールド動作を `REQUIRED` とし、親フィールドを `OPTIONAL` とすることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されると、`text` フィールドは required となる。

## 定義

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは `name` フィールドに付与**されなければならず**（must）、他のいかなるフィールドにも付与**されてはならない**（must not）（[リソース名を表すフィールド][fields representing resource names] を参照）。

`IDENTIFIER` の値は、create メソッドのコンテキストではそのフィールドが入力として受け付けられない（すなわち `OUTPUT_ONLY`）ことを伝える一方で、`IMMUTABLE` ともみなされ、リソースを主入力として受け付ける変更メソッド（例：[標準 Update][aip-134]）では入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、required または optional のいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）で immutable フィールドを受け取った場合、それが更新マスクに含まれていても、値が一致する場合にはそのフィールドを無視**すべきである**（should）が、変更が要求された場合には `INVALID_ARGUMENT` でエラーを返す**べきである**（should）。

immutable フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下のとおりである：

- アプリケーションの生存期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きで immutable」なフィールドには immutable アノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドが Input only として記述されるのは、それがリソースメッセージ内のフィールド、またはリソースメッセージ内に含まれるメッセージのフィールドである場合に限る**べきである**（should）。特に、リクエストメッセージ（通常 `Request` で終わる名前を持つ、RPC の引数としてのみ機能するメッセージ）内のフィールドは、これがすでに暗黙的であるため、Input only として記述**すべきではない**（should not）。

Input only フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下のとおりである：

- AIP-214 で説明されている `ttl` フィールド。

**警告:** Input only フィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、それがリクエストメッセージ（通常 `Request` で終わる、RPC の引数であるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optional として記述**してもよい**（may）。

**注:** フィールド存在ラベル `optional` とフィールド動作 `OPTIONAL` は相互に排他的ではない。詳細は AIP-149 を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も行われない（サーバーはこのフィールド内のあらゆる値をクリア**しなければならず**（must）、入力時にこのフィールドに値が存在することを理由にエラーを送出**してはならない**（must not））ことを示す。同様に、サービスは、更新フィールドマスク内の Output only フィールドの存在を無視**しなければならない**（must）（参照: AIP-161）。

さらに、フィールドが Output only として記述されるのは、それがリソースメッセージ内のフィールド、またはツリーのさらに下位のメッセージのフィールドである場合に限る**べきである**（should）。特に、レスポンスメッセージ（通常 `Response` で終わる、RPC の戻り値としてのみ機能するメッセージ）内のフィールドは、これがすでに暗黙的であるため、Output only として記述**すべきではない**（should not）。

Output only フィールドは、API にとって適切であれば空の値に設定**してもよい**（may）。

Output only フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下のとおりである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）（かつ空でない値に設定**されなければならない**（must））ことを示す。

フィールドが required として記述されるのは、以下のいずれかの場合に限る**べきである**（should）：

- ユーザーが入力としていずこかで提供するリソース上のフィールドである場合。この場合、リソースは `"truthy"` な値が*格納されている*場合にのみ有効である。
  - リソースを[作成する][aip-133]場合、create リクエスト上のフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新する][aip-134]場合、ユーザーは、フィールドがフィールドマスクにも存在しない（フィールドに変更がないことを示す）場合に限り、そのフィールドを省略**してもよい**（may）（そうでない場合、値が提供**されなければならない**（must））。
- リクエストメッセージ（通常 `Request` で終わる名前を持つ、RPC の引数であるメッセージ）上のフィールドである場合。この場合、リクエストの一部として値が提供**されなければならず**（must）、そうしない場合、エラー（通常は `INVALID_ARGUMENT`）が発生**しなければならない**（must）。

上記の `"truthy"` という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/空バイト、`false` 以外の値
- repeated フィールドと map の場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの `"truthy"` フィールドを持つ任意のメッセージ

以下のことを示す目的でフィールドを required として記述**すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで required となるフィールド。
- ユーザー入力として決して使用されない、任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（boolean の `false`、整数の `0`、enum の未指定値など）は未設定の値と区別がつかず、したがって required フィールドに falsy な値を設定するとエラーが発生する。このことからの当然の帰結として、required な boolean は `true` に設定しなければならない。

### Unordered List

リソースの repeated フィールドに対する `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

サービスが、リスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、フィールドは順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返**してもよい**（may）し、ランダムな不安定な順序で返**してもよい**（may）。

## 後方互換性

`google.api.field_behavior` の値の追加または変更は、既存のクライアントにとって互換性がないと認識される API の意味的な変更を表す可能性がある。以下は、`google.api.field_behavior` に関する後方互換性のない変更の例である：

* 以前に（暗黙的または明示的に）`OPTIONAL` とみなされていた既存フィールドに `REQUIRED` を追加する
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加する
* 以前に入力として受け付けられていた既存フィールドに `OUTPUT_ONLY` を追加する
* 以前に出力として出力されていた既存フィールドに `INPUT_ONLY` を追加する
* 以前に mutable とみなされていた既存フィールドに `IMMUTABLE` を追加する
* 以前に入力として無視されていた既存フィールドから `OUTPUT_ONLY` を削除する
* 既存フィールドから `IDENTIFIER` を削除する

*後方互換性がある*変更もいくつかあり、以下のとおりである：

* 既存フィールドに `OPTIONAL` を追加する
* 既存の `name` フィールドに `IDENTIFIER` を追加する
* 既存フィールドで `REQUIRED` から `OPTIONAL` に変更する
* 既存フィールドで `OUTPUT_ONLY` または `IMMUTABLE`（あるいはその両方）から `IDENTIFIER` に変更する
* 既存フィールドから `REQUIRED` を削除する
* 以前にレスポンスで除外されていた既存フィールドから `INPUT_ONLY` を削除する
* 以前に immutable とみなされていた既存フィールドから `IMMUTABLE` を削除する

## 根拠

### Identifier フィールド動作

リソース名は、どんな準拠リソースにとっても主識別子であり、作成時にユーザーによって完全に構築されることは決してない。このようなフィールドには通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかしながら、リソース自体が主リクエストペイロードとなるシナリオでは、主識別子として使用されることも多い。このようなフィールドは `OUTPUT_ONLY` とはみなせ*ない*。さらに、標準 Update のような変更リクエストでは、主識別子としてのリソース名をその場で変更することはできない。このようなフィールドには通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの矛盾しコンテキストに依存するフィールド動作のため、リソース名フィールドの動作を特定して伝達するための新しい値が必要であった。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは required または optional のいずれかであり、したがってそれぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを指定してもフィールドの必要性が伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションの必須化は、API 作成者が API の初期作成時に動作を明示的に検討することも強制する。

初期作成後にフィールド動作を変更することは、クライアントにおける後方互換性のない変更につながる可能性がある。例えば、optional フィールドを required にすると、RPC のメソッドシグネチャや[宣言的クライアント][Declarative client]におけるリソースの後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)のセクションを参照。

## 履歴

2023-05 に field_behavior が必須化された。この変更以前は、アノテーションがしばしば省略されていた。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後的にいくつかの field_behavior の値を追加または変更することは、後方互換性がない可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)のセクションを参照。

API の作成時に field_behavior を必須化することの利点は、そうしないことによるクライアントと API ユーザーへのコストを上回る。
