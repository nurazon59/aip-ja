# フィールド動作の文書化

Protocol Buffers でフィールドを定義する際、フィールドの動作に関する特定の側面
（必須かオプションかなど）をユーザーに説明するのが通例である。さらに、他の
ツールがこの動作を理解することは有用である（例えば、クライアントライブラリの
シグネチャを最適化するため）。

## ガイダンス

APIは、必須やimmutableといった、よく理解されたフィールド動作を記述するために
`google.api.field_behavior` アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべての
  フィールドに `google.api.field_behavior` アノテーションを適用
  **しなければならない**（must）。
  - これの例外はリソースメッセージ上のAIP-154の `etag` フィールドで、
    `google.api.field_behavior` を割り当てる**べきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略
    **してもよい**（may）が、この場合、コメントで特定の動作を文書化
    **すべきである**（should）。
- アノテーションは、フィールドの動作を正確に記述するすべての
  [google.api.FieldBehavior][] 値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- APIは最低限、`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれか1つを使用
  **しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作には影響しないが、多くの
クライアント（例：CLIやSDK）はコード生成のためにこれらに依存している。
新しいフィールドを追加する際には、どの値が関連するかを十分に検討し考慮する
こと。

アノテーションがないフィールドは、後方互換性のために `OPTIONAL` と解釈される。
それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** この文書で示される語彙は_記述_目的のみであり、それ自体で検証を追加
するものではない。目的は、クライアント向けにこの動作を一貫して文書化すること
である。

### ネストされたメッセージの field behavior

ネストされたメッセージの `google.api.field_behavior` アノテーションは、親の
アノテーションから独立している。

例えば、親フィールドが `OPTIONAL` である一方で、ネストされたメッセージが
`REQUIRED` の field behavior を持つことができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定された場合、`text` フィールドは必須である。

## 語彙

### IDENTIFIER

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に
使用されることを示す。これは `name` フィールドに付与**しなければならず**
（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を
表すフィールド][fields representing resource names] を参照）。

`IDENTIFIER` 値は、作成メソッドのコンテキストにおいて、フィールドが入力として
受け入れられない（つまり `OUTPUT_ONLY`）ことを伝える一方で、`IMMUTABLE` とも
みなされ、リソースを主入力として受け取る変更メソッド（例：[標準
Update][aip-134]）の入力として受け入れられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用
**してはならない**（must not）。

### IMMUTABLE

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。
これは、入力または出力、必須またはオプションのいずれのフィールドにも適用
できる。

サービスが更新リクエスト（または同様のもの）でimmutableフィールドを受け取った
場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視
**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` で
エラー**にすべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- アプリケーションのライフタイム中に変更できないリソースの属性
  （例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドには、immutableアノテーションを
付与**してはならない**（must not）。

### INPUT_ONLY

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが
出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソース
メッセージに含まれるメッセージのフィールドである場合にのみ、input only と
記述**すべきである**（should）。特筆すべきは、リクエストメッセージ（RPCの
引数としてのみ機能し、通常は `Request` で終わる名前を持つメッセージ）内の
フィールドは、これが既に暗黙的であるため、input only と記述**すべきではない**
（should not）ことである。

input only フィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- AIP-214 で説明されている `ttl` フィールド。

**警告:** input only フィールドは稀であり、使用前に慎重に検討すべきである。

### OPTIONAL

`OPTIONAL` の使用は、フィールドが必須ではないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常は `Request` で
終わる名前を持つメッセージ）上のフィールド、またはサブメッセージ上の
フィールドである場合、optional と記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` と field behavior
`OPTIONAL` は相互に排他的ではない。詳細については AIP-149 を参照。

### OUTPUT_ONLY

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストの
メッセージにそのフィールドを含めても何も行われないことを示す（サーバーはこの
フィールドの値を**クリアしなければならず**（must）、入力時にこのフィールドに
値が存在する結果としてエラーを**スローしてはならない**（must not））。同様に、
サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視
**しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーのより
深い位置にあるメッセージのフィールドである場合にのみ、output only と記述
**すべきである**（should）。特筆すべきは、レスポンスメッセージ（RPCの戻り値
としてのみ機能し、通常は `Response` で終わる名前を持つメッセージ）内の
フィールドは、これが既に暗黙的であるため、output only と記述**すべきではない**
（should not）ことである。

output only フィールドは、APIにとって適切であれば空の値に設定
**してもよい**（may）。

output only フィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく導出または構造化された情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### REQUIRED

`REQUIRED` の使用は、リクエストまたはリソース上でフィールドが存在
**しなければならず**（must）、空でない値に設定**しなければならない**（must）
ことを示す。

フィールドは、_次のいずれか_ の場合にのみ required と記述**すべきである**
（should）：

- ユーザーがどこかで入力として提供するリソース上のフィールドである。この場合、
  リソースは「truthy」な値が_格納されている_場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでフィールドの値を提供
    **しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスク
    にも存在しない場合に限り、フィールドを省略**してもよい**（may）。これは
    フィールドに変更がないことを示す（そうでない場合、提供**しなければ
    ならない**（must））。
- RPCの引数であり、通常は `Request` で終わる名前を持つリクエストメッセージ
  上のフィールドである。この場合、値はリクエストの一部として提供
  **しなければならず**（must）、提供しなかった場合はエラー（通常は
  `INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の「truthy」という用語を次のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false` 以外の値。
- repeatedフィールドおよびマップの場合、少なくとも1つのエントリを持つ値。
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つ任意の
  メッセージ。

以下のことを示すために required と記述**すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 一部の状況で条件付きで必須となるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）
  上のフィールド。

**注:** ほとんどの場合、空の値（ブーリアンの `false`、整数の `0`、enum の
未指定値など）は未設定の値と区別できないため、required フィールドをfalsyな
値に設定するとエラーが発生する。このことから必然的に、required ブーリアンは
`true` に設定**しなければならない**（must）。

### UNORDERED_LIST

リソースのrepeatedフィールドでの `UNORDERED_LIST` の使用は、サービスがリスト
内の項目の順序を保証しないことを示す。

サービスが、サービスの判断でリストをソートする状況を含めて、リスト内の要素の
順序がユーザーが送信した順序と一致することを保証しない場合、フィールドは
unordered list と記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返し**てもよく**
（may）、ランダムで不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントにとって
互換性がないと認識される API の意味的な変更を表す可能性がある。以下は、
`google.api.field_behavior` に関する後方互換性のない変更の例である：

* 以前は（暗黙的または明示的に）`OPTIONAL` とみなされていた既存フィールドへの
  `REQUIRED` の追加
* 既存のリクエストメッセージへの `REQUIRED` とアノテーションされた新しい
  フィールドの追加
* 以前は入力として受け入れられていた既存フィールドへの `OUTPUT_ONLY` の追加
* 以前は出力として出力されていた既存フィールドへの `INPUT_ONLY` の追加
* 以前は変更可能とみなされていた既存フィールドへの `IMMUTABLE` の追加
* 以前は入力として無視されていた既存フィールドからの `OUTPUT_ONLY` の削除
* 既存フィールドからの `IDENTIFIER` の削除。

以下のようないくつかの変更は後方互換性がある：

* 既存フィールドへの `OPTIONAL` の追加
* 既存の `name` フィールドへの `IDENTIFIER` の追加
* 既存フィールドでの `REQUIRED` から `OPTIONAL` への変更
* 既存フィールドでの `OUTPUT_ONLY` または `IMMUTABLE`（あるいはその両方）から
  `IDENTIFIER` への変更
* 既存フィールドからの `REQUIRED` の削除
* 以前はレスポンスから除外されていた既存フィールドからの `INPUT_ONLY` の削除
* 以前はimmutableとみなされていた既存フィールドからの `IMMUTABLE` の削除

## 根拠

### IDENTIFIER フィールド動作

準拠するリソースの主要な識別子であるリソース名は、作成時にユーザーによって
完全に構成されることはない。そのようなフィールドは通常、`OUTPUT_ONLY` field
behavior が割り当てられる。しかし、リソース自体が主要なリクエストペイロード
となるシナリオでは、主要な識別子としても消費されることが多い。そのような
フィールドは `OUTPUT_ONLY` とみなすことができ_ない_。さらに、標準Update
などの変更リクエストでは、主要な識別子としてのリソース名はその場で変更
できない。そのようなフィールドには通常、`IMMUTABLE` field behavior が
割り当てられる。これらの矛盾し文脈に依存する field behavior のために、
リソース名フィールドの動作を特定し伝えるための新しい値が必要となった。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれか
**でなければならない**（must）。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須またはオプションのいずれかであり、したがって
それぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを持つ**べき
である**（should）。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わら
ないため、`REQUIRED` または `OPTIONAL` のいずれかも指定する必要がある。

### field behavior の必須化

各フィールドに field behavior アノテーションを含めることで、リソースが示す
全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、
プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須化することは、API作成者がAPIの初期作成時に動作を明示的に
検討することも促す。

初期作成後に field behavior を変更すると、クライアントで後方互換性のない変更
が発生する可能性がある。例えば、オプションフィールドを必須にすると、RPCや
[宣言的クライアント][Declarative client]のリソースのメソッドシグネチャに後方
互換性のない変更が生じる。より詳細な互換性ガイダンスについては、
[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023年5月に field_behavior が必須化された。この変更以前は、アノテーションは
しばしば省略されていた。その値は、高品質なクライアントを生成するために依存
されている。さらに、メジャーバージョン内で事後に一部の field_behavior 値を
追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性
ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

API作成時に field_behavior を必須化することの利点は、そうしない場合の
クライアントとAPIユーザーへのコストを上回る。
