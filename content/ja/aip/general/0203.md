# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作の特定の側面（必須かオプショナルかなど）をユーザーに説明することが慣例である。さらに、他のツールがこの動作を理解することは（例えば、クライアント ライブラリのシグネチャを最適化するために）有用である。

## ガイダンス

APIは、フィールドが必須やimmutableであるなど、よく理解されたフィールド動作を記述するために `google.api.field_behavior` アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の `etag` フィールドは、どの `google.api.field_behavior` も割り当てる**べきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合は特定の動作をコメントに文書化**すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する [google.api.FieldBehavior][] の値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` は使用**してはならない**（must not）。
- APIは最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的に確認し検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` として解釈される。それにもかかわらず、このアノテーションは省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は*記述*目的のみであり、それ自体が検証を追加するものではない。目的は、クライアントに対してこの動作を一貫して文書化することである。

### ネストされたメッセージのfield behavior

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージが `REQUIRED` のフィールド動作を持ち、親フィールドが `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されると、`text` フィールドは必須となる。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表現するフィールド][fields representing resource names]を参照）。

`IDENTIFIER` 値は、作成メソッドのコンテキストではフィールドが入力として受け付けられず（すなわち `OUTPUT_ONLY`）、また `IMMUTABLE` と見なされ、リソースを主要な入力として受け付ける変更メソッド（例：[標準Update][aip-134]）では入力として受け付けられることを伝達する。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、必須またはオプショナルのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受信した場合、たとえ更新マスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーを返す**べきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- アプリケーションのライフタイム中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドには、immutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールドまたはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、名前が通常 `Request` で終わるメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- AIP-214で説明されている `ttl` フィールド。

**警告:** input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数で、通常は `Request` で終わるメッセージ）またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

**注:** フィールド存在ラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何もせず（サーバーはこのフィールドの値をすべてクリア**しなければならず**（must）、入力に値が存在してもエラーをスロー**してはならない**（must not））、同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（AIP-161を参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはさらに下のメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常 `Response` で終わるメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして記述**すべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在しなければならず（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーがどこかで入力として提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでフィールドの値が提供され**なければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在しない場合に限り、フィールドを省略してもよい（これはフィールドに変更がないことを示す）。そうでない場合は提供**しなければならない**（must）。
- リクエストメッセージ（RPCの引数で、名前が通常 `Request` で終わるメッセージ）上のフィールドである。この場合、リクエストの一部として値が提供**されなければならず**（must）、提供されない場合はエラー（通常は `INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/バイト、`false` 以外の値
- 繰り返しフィールドとマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つメッセージ

以下のことを示すためにフィールドをrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 特定の状況で条件付きで必須となるフィールド。
- ユーザー入力として決して使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enumの未指定値など）は未設定値と区別できないため、必須フィールドに falsy な値を設定するとエラーが発生する。これの当然の帰結として、必須のブール値は `true` に設定しなければならない。

### Unordered List

リソースの繰り返しフィールドに `UNORDERED_LIST` を使用することは、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、unordered listとして記述**すべきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味的な変更を表す可能性がある。以下は `google.api.field_behavior` に関する後方互換性のない変更の例である：

* 以前 `OPTIONAL`（暗黙的またはその他）と見なされていた既存のフィールドに `REQUIRED` を追加する
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加する
* 以前入力として受け付けられていた既存のフィールドに `OUTPUT_ONLY` を追加する
* 以前出力として発行されていた既存のフィールドに `INPUT_ONLY` を追加する
* 以前変更可能と見なされていた既存のフィールドに `IMMUTABLE` を追加する
* 以前入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除する
* 既存のフィールドから `IDENTIFIER` を削除する。

後方互換性の*ある*変更もあり、以下の通りである：

* 既存のフィールドに `OPTIONAL` を追加する
* 既存の `name` フィールドに `IDENTIFIER` を追加する
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更する
* 既存のフィールドで `OUTPUT_ONLY` および/または `IMMUTABLE` から `IDENTIFIER` に変更する
* 既存のフィールドから `REQUIRED` を削除する
* 以前レスポンスで除外されていた既存のフィールドから `INPUT_ONLY` を削除する
* 以前immutableと見なされていた既存のフィールドから `IMMUTABLE` を削除する

## 根拠

### Identifierフィールド動作

リソース名は、準拠するすべてのリソースの主要な識別子であり、作成時にユーザーが完全に構築することは決してない。そのようなフィールドは通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードであるシナリオでは、主要な識別子としても消費される。そのようなフィールドは `OUTPUT_ONLY` と見なすことが*できなかった*。さらに、標準Updateのような変更リクエストでは、主要な識別子としてのリソース名をその場で変更することはできない。そのようなフィールドは通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの相反するコンテキスト依存のフィールド動作は、リソース名フィールドの動作を単独で抽出し伝達するために新しい値が必要であることを意味した。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須またはオプショナルのいずれかであり、したがって少なくともそれぞれ `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須化することは、API作成者にAPIの初期作成時に動作を明示的に検討させることにもなる。

初期作成後にフィールド動作を変更すると、クライアントで後方互換性のない変更が発生する可能性がある。例えば、オプショナルフィールドを必須にすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースで後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023-05にfield_behaviorが必須化された。この変更以前は、アノテーションはしばしば省略されていた。その値は、高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後にfield_behavior値を追加または変更することは、後方互換性がない可能性がある。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを必須化することの利点は、そうしない場合のクライアントやAPIユーザーへのコストを上回る。
