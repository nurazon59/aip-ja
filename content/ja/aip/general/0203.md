# フィールド動作の文書化

Protocol Buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（必須かオプショナルかなど）をユーザーに説明するのが慣例である。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは、必須やimmutableなどのよく理解されたフィールド動作を記述するために`google.api.field_behavior`アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに`google.api.field_behavior`アノテーションを**適用しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の`etag`フィールドは、`google.api.field_behavior`を**割り当てるべきではない**（should not）。
  - さらに、`oneof`フィールドは`google.api.field_behavior`を**省略してもよい**（may）が、この場合、特定の動作をコメントで**文書化すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する[google.api.FieldBehavior][]値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`は**使用してはならない**（must not）。
- APIは、少なくとも`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれか1つを**使用しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作には影響しないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的に検討し考慮すること。

アノテーションのないフィールドは、後方互換性のため`OPTIONAL`として解釈される。それでもなお、このアノテーションは**省略してはならない**（must not）。

**注:** このドキュメントで示す語彙は*記述的*な目的のみであり、それ自体が検証を追加するものではない。目的は、クライアントに対してこの動作を一貫して文書化することである。

### ネストされたメッセージのfield_behavior

ネストされたメッセージ上の`google.api.field_behavior`アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージが`REQUIRED`のフィールド動作を持ち、親フィールドが`OPTIONAL`であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されていれば、`text`フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは`name`フィールドに**付与しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、作成メソッドのコンテキストではフィールドが入力として受け入れられない（つまり`OUTPUT_ONLY`）ことを伝える一方で、`IMMUTABLE`ともみなされ、リソースを主な入力として受け入れる変更メソッド（例：[標準Update][aip-134]）では入力として受け入れられる。

このアノテーションは、メッセージ内の他のリソースへの参照に**適用してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力フィールドまたは出力フィールド、必須またはオプショナルのいずれにも適用できる。

サービスが更新リクエスト（または同様のもの）でimmutableフィールドを受信した場合、更新マスクに含まれていても、値が一致する場合はフィールドを**無視すべきであり**（should）、変更が要求された場合は`INVALID_ARGUMENT`で**エラーを返すべきである**（should）。

immutableフィールドの潜在的なユースケースは（これは網羅的なリストではない）：

- アプリケーションのライフタイム中に変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドには、immutableアノテーションを**付与してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして**記述されるべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、名前が通常`Request`で終わるメッセージ）内のフィールドは、既に暗黙的であるため、input onlyとして記述**されるべきではない**（should not）。

input onlyフィールドの潜在的なユースケースは（これは網羅的なリストではない）：

- AIP-214で説明されている`ttl`フィールド。

**警告:** Input onlyフィールドはまれであり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常`Request`で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして**記述してもよい**（may）。

**注:** フィールドプレゼンスラベル`optional`とフィールド動作`OPTIONAL`は相互排他的ではない。詳細はAIP-149を参照。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにフィールドを含めても何も行われないことを示す（サーバーはこのフィールドの値を**クリアしなければならず**（must）、入力での値の存在を理由にエラーを**スローしてはならない**（must not））。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を**無視しなければならない**（must）（AIP-161を参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはより下位のメッセージのフィールドである場合にのみ、output onlyとして**記述されるべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常`Response`で終わるメッセージ）内のフィールドは、既に暗黙的であるため、output onlyとして記述**されるべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば空の値に**設定してもよい**（may）。

output onlyフィールドの潜在的なユースケースは（これは網羅的なリストではない）：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- 変更不可能なサービスによって割り当てられたリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソースに（非空の値に設定されて）**存在しなければならない**（must）ことを示す。

フィールドは、*次のいずれか*の場合にのみrequiredとして**記述されるべきである**（should）：

- ユーザーが入力として提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースの[作成][aip-133]時に、作成リクエストでフィールドの値を**提供しなければならない**（must）。
  - リソースの[更新][aip-134]時に、フィールドマスクにもフィールドが存在しない場合（フィールドの変更がないことを示す）、ユーザーはフィールドを**省略してもよく**（may）、そうでない場合は**提供しなければならない**（must）。
- リクエストメッセージ（RPCの引数であり、名前は通常`Request`で終わるメッセージ）上のフィールドである。この場合、リクエストの一部として値を**提供しなければならず**（must）、提供しない場合はエラー（通常は`INVALID_ARGUMENT`）を**発生させなければならない**（must）。

上記で「truthy」という用語を次のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false`以外の値
- 繰り返しフィールドやマップの場合、少なくとも1つのエントリがある値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つメッセージ

フィールドは、以下を示すためにrequiredとして**記述されるべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として使用されることのない（リソースであるメッセージを含む）メッセージ上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定値と区別がつかないため、requiredフィールドにfalsyな値を設定するとエラーになる。この帰結として、requiredなブール値は`true`に**設定しなければならない**（must）。

### Unordered List

リソースの繰り返しフィールドでの`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスが要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、unordered listとして**記述されるべきである**（should）。

unordered listを持つリソースは、リストを安定した順序で**返してもよい**（may）し、ランダム化された不安定な順序で**返してもよい**（may）。

## 後方互換性

`google.api.field_behavior`値の追加や変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味的変更を表す可能性がある。以下は、`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前に（暗黙的またはその他で）`OPTIONAL`とみなされていた既存フィールドへの`REQUIRED`の追加
* 既存のリクエストメッセージへの`REQUIRED`とアノテーションされた新しいフィールドの追加
* 以前に入力として受け入れられていた既存フィールドへの`OUTPUT_ONLY`の追加
* 以前に出力として発行されていた既存フィールドへの`INPUT_ONLY`の追加
* 以前に可変とみなされていた既存フィールドへの`IMMUTABLE`の追加
* 以前に入力として無視されていた既存フィールドからの`OUTPUT_ONLY`の削除
* 既存フィールドからの`IDENTIFIER`の削除。

*後方互換性がある*変更もあり、以下の通りである：

* 既存フィールドへの`OPTIONAL`の追加
* 既存の`name`フィールドへの`IDENTIFIER`の追加
* 既存フィールドでの`REQUIRED`から`OPTIONAL`への変更
* 既存フィールドでの`OUTPUT_ONLY` や `IMMUTABLE` から `IDENTIFIER` への変更
* 既存フィールドからの`REQUIRED`の削除
* 以前にレスポンスで除外されていた既存フィールドからの`INPUT_ONLY`の削除
* 以前にimmutableとみなされていた既存フィールドからの`IMMUTABLE`の削除

## 根拠

### Identifierフィールド動作

リソース名は、準拠するリソースの主識別子であり、作成時にユーザーが完全に構築することはない。このようなフィールドは通常`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、これらはリソース自体が主なリクエストペイロードであるシナリオで主識別子としてもよく利用される。そのようなフィールドは`OUTPUT_ONLY`と*みなすことはできない*。さらに、標準Updateのような変更リクエストでは、主識別子としてのリソース名はその場で変更できない。このようなフィールドは通常`IMMUTABLE`フィールド動作が割り当てられる。これらの矛盾しコンテキストに依存するフィールド動作のため、リソース名フィールドの動作を特定して伝達するために新しい値が必要であった。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力か出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドは必須かオプショナルのいずれかであるため、それぞれ少なくとも`REQUIRED`または`OPTIONAL`アノテーションを**持つべきである**（should）。`INPUT_ONLY`だけを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須化することで、API作成者はAPIの初回作成時に動作を明示的に検討せざるを得なくなる。

初回作成後にフィールド動作を変更すると、クライアントで後方互換性のない変更が生じる可能性がある。例えば、オプショナルフィールドを必須にすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースにおいて後方互換性のない変更が生じる。詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023-05にfield_behaviorは必須化された。この変更以前は、アノテーションはしばしば省略されていた。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後にfield_behavior値の一部を追加または変更すると、後方互換性がなくなる可能性がある。詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

API作成時にfield_behaviorを必須化することの利点は、そうしないことによるクライアントやAPIユーザーへのコストを上回る。
