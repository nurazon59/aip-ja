# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作の特定の側面（必須か任意かなど）をユーザーに説明するのが慣例である。さらに、他のツールがこの動作を理解することも有用である（例えば、クライアントライブラリのシグネチャを最適化するためなど）。

## ガイダンス

APIは、必須やimmutableなど、よく理解されたフィールド動作を記述するために`google.api.field_behavior`アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - これに対する例外は、リソースメッセージ上のAIP-154の`etag`フィールドであり、いかなる`google.api.field_behavior`も割り当て**るべきではない**（should not）。
  - さらに、`oneof`フィールドは`google.api.field_behavior`を省略**してもよい**（may）が、この場合、特定の動作をコメントに**文書化すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する任意の[google.api.FieldBehavior][]値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは最低限、`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成にこれに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的にレビューし検討すること。

アノテーションのないフィールドは、後方互換性のために`OPTIONAL`として解釈される。それでも、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで示す語彙は*記述的*な目的のみであり、それ自体は検証を追加しない。目的は、この動作をクライアント向けに一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージの`google.api.field_behavior`アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージは`REQUIRED`のフィールド動作を持ち、親フィールドは`OPTIONAL`であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されている場合、`text`フィールドは必須である。

## 語彙

### 識別子

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは`name`フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、フィールドが作成メソッドのコンテキストでは入力として受け付けられない（すなわち`OUTPUT_ONLY`）一方で、`IMMUTABLE`とみなされ、リソースを主入力として受け付ける変更メソッド（例：[標準Update][aip-134]）の入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または同様のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はフィールドを**無視すべきであり**（should）、変更が要求された場合は`INVALID_ARGUMENT`で**エラーとすべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- アプリケーションのライフタイム中に変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドには、immutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、Input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、名前が通常`Request`で終わるメッセージ）内のフィールドは、既に暗黙的であるため、Input onlyとして記述**すべきではない**（should not）。

Input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- AIP-214で説明されている`ttl`フィールド。

**警告:** Input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、名前が通常`Request`で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合に、optionalとして記述**してもよい**（may）。

**注:** フィールド存在ラベル`optional`とフィールド動作`OPTIONAL`は相互に排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにフィールドを含めても何も起こらないことを示す（サーバーはこのフィールドの値を**クリアしなければならず**（must）、入力時にこのフィールドに値が存在する結果としてエラーを**発生させてはならない**（must not））。同様に、サービスは更新フィールドマスクにOutput onlyフィールドが存在することを**無視しなければならない**（must）（AIP-161参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーの下位にあるメッセージのフィールドである場合にのみ、Output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、名前が通常`Response`で終わるメッセージ）内のフィールドは、既に暗黙的であるため、Output onlyとして記述**すべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

Output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソース上に存在し（かつ空でない値に設定され）**なければならない**（must）ことを示す。

フィールドは、次のいずれかの場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである場合。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、フィールドがフィールドマスクにも存在しない場合（フィールドに変更がないことを示す）、ユーザーはフィールドを**省略してもよい**（may）（それ以外の場合は値を提供**しなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、名前が通常`Request`で終わるメッセージ）上のフィールドである場合。この場合、リクエストの一部として値を提供**しなければならず**（must）、そうしないとエラー（通常は`INVALID_ARGUMENT`）が**発生しなければならない**（must）。

上記の「truthy」という用語を次のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false`以外の値
- repeatedフィールドおよびマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つ任意のメッセージ

以下のことを示すためにフィールドをrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として使用されない任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブーリアンの`false`、整数の`0`、enumの未指定値など）は未設定の値と区別できないため、requiredフィールドをfalsyな値に設定するとエラーが発生する。これの帰結として、requiredなブーリアンは`true`に設定**しなければならない**。

### 順序なしリスト

リソースのrepeatedフィールドでの`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、フィールドは順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返し**てもよく**（may）、ランダム化された不安定な順序で**返してもよい**（may）。

## 後方互換性

`google.api.field_behavior`値の追加または変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味的変更を表す可能性がある。以下は、`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前`OPTIONAL`とみなされていた（暗黙的かどうかにかかわらず）既存フィールドへの`REQUIRED`の追加
* 既存のリクエストメッセージへの`REQUIRED`としてアノテーションされた新しいフィールドの追加
* 以前入力として受け付けられていた既存フィールドへの`OUTPUT_ONLY`の追加
* 以前出力として出力されていた既存フィールドへの`INPUT_ONLY`の追加
* 以前mutableとみなされていた既存フィールドへの`IMMUTABLE`の追加
* 以前入力として無視されていた既存フィールドからの`OUTPUT_ONLY`の削除
* 既存フィールドからの`IDENTIFIER`の削除

後方互換性が*ある*変更もいくつかあり、以下のとおりである：

* 既存フィールドへの`OPTIONAL`の追加
* 既存の`name`フィールドへの`IDENTIFIER`の追加
* 既存フィールドの`REQUIRED`から`OPTIONAL`への変更
* 既存フィールドの`OUTPUT_ONLY`または`IMMUTABLE`（あるいはその両方）から`IDENTIFIER`への変更
* 既存フィールドからの`REQUIRED`の削除
* 以前レスポンスで除外されていた既存フィールドからの`INPUT_ONLY`の削除
* 以前immutableとみなされていた既存フィールドからの`IMMUTABLE`の削除

## 根拠

### 識別子フィールド動作

リソース名は、準拠するリソースの主識別子であり、作成時にユーザーによって完全に構築されることはない。このようなフィールドは通常、`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、リソース自体が主リクエストペイロードであるシナリオでは、主識別子としてもよく使われる。このようなフィールドは`OUTPUT_ONLY`とみなすことが*できなかった*。さらに、標準Updateのような変更リクエストでは、主識別子としてのリソース名はその場で変更できない。このようなフィールドは通常、`IMMUTABLE`フィールド動作が割り当てられる。これらの相反し文脈に依存するフィールド動作のため、リソース名フィールドの動作を特定して伝えるための新しい値が必要であった。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力か出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドはrequiredかoptionalのいずれかであり、したがって少なくともそれぞれ`REQUIRED`または`OPTIONAL`のアノテーションを持つべきである。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかの指定が依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須とすることで、API作成者はAPIの初期作成時に動作を明示的に検討せざるを得なくなる。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更をもたらす可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]内のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023-05にfield_behaviorが必須になった。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後にいくつかのfield_behavior値を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを必須とすることの利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
