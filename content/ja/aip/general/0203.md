# フィールド動作の文書化

Protocol Buffers でフィールドを定義する際、フィールドの動作の特定の側面（required か optional かなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解することは有用である（たとえば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

API は `google.api.field_behavior` アノテーションを使用して、フィールドが required や immutable であるなど、十分に理解されているフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- API は、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外は、リソースメッセージ上の AIP-154 の `etag` フィールドであり、これにはいかなる `google.api.field_behavior` も割り当て**るべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合、特定の動作をコメントに文書化**すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する任意の [google.api.FieldBehavior][] 値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- API は、最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` は proto レベルの動作には影響しないが、多くのクライアント（CLI や SDK など）はコード生成のためにこれに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的にレビューし、検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` として解釈される。それでもなお、このアノテーションを省略**してはならない**（must not）。

**注:** この文書で示される語彙は*説明的*目的のためのみであり、それ自体がバリデーションを追加するものではない。目的は、クライアント向けにこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションから独立している。

たとえば、ネストされたメッセージが `REQUIRED` のフィールド動作を持ち、親フィールドが `OPTIONAL` であることができる:

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定された場合、`text` フィールドは必須である。

## 語彙

### 識別子

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは `name` フィールドに付与**しなければならない**（must）かつ、他のいかなるフィールドにも付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names] を参照）。

`IDENTIFIER` 値は、作成メソッドのコンテキストではそのフィールドが入力として受け付けられない（すなわち `OUTPUT_ONLY`）ことを伝えるとともに、リソースを主入力として受け付ける変更メソッド（例: [Standard Update][aip-134]）では `IMMUTABLE` とも見なされ、入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、required または optional のいずれのフィールドにも適用できる。

サービスが更新リクエスト（または同様のもの）で immutable フィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーと**すべきである**（should）。

immutable フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り:

- アプリケーションの存続期間中に変更できないリソースの属性（例: ディスクタイプ）。

**注:** 「条件付きで immutable」なフィールドには、immutable アノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールドまたはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input only として記述**すべきである**（should）。特に、リクエストメッセージ（RPC の引数としてのみ機能し、名前が通常 `Request` で終わるメッセージ）内のフィールドは、すでに暗黙的であるため、input only として記述**すべきではない**（should not）。

input only フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り:

- AIP-214 で説明されている `ttl` フィールド。

**警告:** input only フィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須ではないことを示す。

フィールドは、リクエストメッセージ（RPC の引数であり、通常 `Request` で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optional として記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細は AIP-149 を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにそのフィールドを含めても何も起こらない（サーバーはこのフィールドの値をクリア**しなければならない**（must）かつ、入力にこのフィールドの値が存在する結果としてエラーを投げ**てはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスクにおける output only フィールドの存在を無視**しなければならない**（must）（参照: AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーのより下位のメッセージのフィールドである場合にのみ、output only として記述**すべきである**（should）。特に、レスポンスメッセージ（RPC の戻り値としてのみ機能し、通常 `Response` で終わるメッセージ）内のフィールドは、すでに暗黙的であるため、output only として記述**すべきではない**（should not）。

output only フィールドは、API に適切であれば空の値に設定**してもよい**（may）。

output only フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り:

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在**しなければならない**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみ required として記述**すべきである**（should）:

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは "truthy" な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでそのフィールドに値が提供され**なければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーは、そのフィールドがフィールドマスクにも存在せず、フィールドに変更がないことを示す場合に限り、フィールドを省略**してもよい**（may）（そうでない場合は提供され**なければならない**（must））。
- RPC の引数であり、名前が通常 `Request` で終わるリクエストメッセージ上のフィールドである。この場合、リクエストの一部として値が提供され**なければならない**（must）かつ、提供されない場合はエラー（通常 `INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の "truthy" という用語を以下のように定義する:

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト列、`false` 以外の値
- 繰り返しフィールドやマップの場合、少なくとも1つのエントリがある値
- メッセージの場合、少なくとも1つの "truthy" フィールドを持つメッセージ

以下のことを示すためにフィールドを required として記述**すべきではない**（should not）:

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで required となるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enum の未指定値など）は未設定の値と区別がつかないため、required フィールドを falsy な値に設定するとエラーが発生する。この帰結として、required なブール値は `true` に設定されなければならない。

### 順序なしリスト

リソースの繰り返しフィールドにおける `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスが要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダムで不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントにとって互換性がないと認識される API の意味的な変更を表す可能性がある。以下は `google.api.field_behavior` に関する後方互換性のない変更の例である:

* 以前に `OPTIONAL`（暗黙的またはその他で）と見なされていた既存のフィールドへの `REQUIRED` の追加
* 既存のリクエストメッセージへの `REQUIRED` アノテーション付きの新しいフィールドの追加
* 以前に入力として受け付けられていた既存のフィールドへの `OUTPUT_ONLY` の追加
* 以前に出力として出力されていた既存のフィールドへの `INPUT_ONLY` の追加
* 以前に mutable と見なされていた既存のフィールドへの `IMMUTABLE` の追加
* 以前に入力として無視されていた既存のフィールドからの `OUTPUT_ONLY` の削除
* 既存のフィールドからの `IDENTIFIER` の削除

後方互換性の*ある*変更もあり、それは以下の通りである:

* 既存のフィールドへの `OPTIONAL` の追加
* 既存の `name` フィールドへの `IDENTIFIER` の追加
* 既存のフィールドでの `REQUIRED` から `OPTIONAL` への変更
* 既存のフィールドでの `OUTPUT_ONLY` または `IMMUTABLE`（あるいはその両方）から `IDENTIFIER` への変更
* 既存のフィールドからの `REQUIRED` の削除
* 以前にレスポンスから除外されていた既存のフィールドからの `INPUT_ONLY` の削除
* 以前に immutable と見なされていた既存のフィールドからの `IMMUTABLE` の削除

## 根拠

### 識別子フィールド動作

リソース名は、準拠するリソースの主識別子であり、作成時にユーザーによって完全に構築されることはない。そのようなフィールドは通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、それらはリソース自体が主リクエストペイロードであるシナリオでは主識別子としても使用されることが多い。そのようなフィールドは `OUTPUT_ONLY` と見なすことが*できなかった*。さらに、Standard Update のような変更リクエストでは、主識別子としてのリソース名をその場で変更することはできない。そのようなフィールドは通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの矛盾しコンテキスト依存のフィールド動作は、リソース名フィールドの動作を単独で抽出し伝達するために新しい値が必要であることを意味した。

### 必須アノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは required または optional のいずれかであり、したがって最低限 `REQUIRED` または `OPTIONAL` アノテーションをそれぞれ持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須化することで、API 作成者は API の初期作成時に動作を明示的に検討せざるを得なくなる。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更をもたらす可能性がある。たとえば、optional フィールドを required にすると、RPC のメソッドシグネチャや[宣言的クライアント][Declarative client]におけるリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては[後方互換性](#後方互換性)のセクションを参照。

## 履歴

2023-05 に field_behavior が必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後に field_behavior 値の一部を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては[後方互換性](#後方互換性)のセクションを参照。

API の作成時に field_behavior を必須化することの利点は、そうしない場合のクライアントと API ユーザーへのコストを上回る。
