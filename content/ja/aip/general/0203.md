# フィールド動作の文書化

Protocol Buffers でフィールドを定義する際には、ユーザーに対してフィールドの動作の特定の側面（必須か任意かなど）を説明することが慣例である。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアント ライブラリのシグネチャの最適化のため）。

## ガイダンス

API は、`google.api.field_behavior` アノテーションを使用して、フィールドが必須や immutable であるといった、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- API は、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - これの例外は、リソースメッセージ上の AIP-154 の `etag` フィールドであり、これにはいかなる `google.api.field_behavior` も割り当て**るべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合、コメント内で特定の動作を文書化**すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する [google.api.FieldBehavior][] の値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- API は、最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` は proto レベルの動作には影響しないが、多くのクライアント（CLI や SDK など）はコード生成にこれらを利用している。新しいフィールドを追加する際には、どの値が適切かを徹底的に確認し検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` と解釈される。それでも、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで示される語彙は _記述的_ な目的のためのみであり、それ自体が検証を追加するものではない。目的は、クライアント向けにこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージが `REQUIRED` のフィールド動作を持つ一方で、親フィールドが `OPTIONAL` であってもよい:

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記のケースでは、`title` が指定された場合、`text` フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに付与**しなければならない**（must）し、他のいかなるフィールドにも付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names] を参照）。

`IDENTIFIER` の値は、作成メソッドのコンテキストではそのフィールドが入力として受け付けられない（つまり `OUTPUT_ONLY`）こと、また、リソースを主入力として受け付ける変更メソッド（例: [標準更新][aip-134]）では `IMMUTABLE` と見なされ入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照には適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、必須または任意のいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）で immutable なフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーに**すべきである**（should）。

immutable なフィールドの潜在的なユースケース（これは網羅的なリストではない）:

- アプリケーションの存続期間中変更できないリソースの属性（例: ディスクタイプ）。

**注:** 「条件付きで immutable」なフィールドには、immutable アノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドが input only として記述**されるべきである**（should）のは、それがリソースメッセージ内のフィールドであるか、リソースメッセージ内に含まれるメッセージのフィールドである場合のみである。特に、リクエストメッセージ（RPC の引数としてのみ機能し、通常 `Request` で終わる名前を持つメッセージ）内のフィールドは、input only として記述**すべきではない**（should not）。これはすでに暗黙的だからである。

input only フィールドの潜在的なユースケース（これは網羅的なリストではない）:

- AIP-214 で説明されている `ttl` フィールド。

**警告:** input only フィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須ではないことを示す。

フィールドは、リクエストメッセージ（RPC の引数であり、通常 `Request` で終わる名前を持つメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optional として記述**してもよい**（may）。

**注:** フィールド存在ラベル `optional` とフィールド動作 `OPTIONAL` は相互に排他的ではない。詳細は AIP-149 を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も起こらない（サーバーはこのフィールドの値をクリア**しなければならない**（must）し、入力時にこのフィールドに値が存在することを理由にエラーをスロー**してはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスク内の output only フィールドの存在を無視**しなければならない**（must）（参照: AIP-161）。

さらに、フィールドが output only として記述**されるべきである**（should）のは、それがリソースメッセージ内のフィールドであるか、ツリーのより深い位置にあるメッセージのフィールドである場合のみである。特に、レスポンスメッセージ（RPC の戻り値としてのみ機能し、通常 `Response` で終わる名前を持つメッセージ）内のフィールドは、output only として記述**すべきではない**（should not）。これはすでに暗黙的だからである。

output only フィールドは、API にとって適切であれば空の値に設定**してもよい**（may）。

output only フィールドの潜在的なユースケース（これは網羅的なリストではない）:

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在**しなければならない**（must）こと（かつ空でない値に設定されていること）を示す。

フィールドが required として記述**されるべきである**（should）のは、_次のいずれか_ の場合のみである:

- ユーザーがどこかで入力として提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が _格納されている_ 場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエスト上でそのフィールドの値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドを省略**してもよい**（may）。ただし、フィールドマスクからもそのフィールドが省略されており、フィールドに変更がないことを示している場合に限る（そうでない場合は提供**しなければならない**（must））。
- リクエストメッセージ（RPC の引数であり、通常 `Request` で終わる名前を持つメッセージ）上のフィールドである。この場合、リクエストの一部として値を提供**しなければならない**（must）し、そうしない場合はエラー（通常 `INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「truthy」という用語を次のように定義する:

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false` 以外の値
- 繰り返しフィールドとマップの場合、少なくとも 1 つのエントリを持つ値
- メッセージの場合、少なくとも 1 つの「truthy」なフィールドを持つすべてのメッセージ

次のことを示すために required として記述**すべきではない**（should not）:

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として決して使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enum の未指定値など）は未設定値と区別できないため、必須フィールドに falsy な値を設定するとエラーが発生する。この帰結として、必須のブール値は `true` に設定されなければならない。

### Unordered List

リソースの繰り返しフィールドに対する `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、リスト内の要素の順序がユーザーが送信した順序と一致することをサービスが保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、unordered list として記述**すべきである**（should）。

unordered list を持つリソースは、安定した順序でリストを返し**てもよい**（may）し、ランダムで不安定な順序でリストを返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` の値の追加や変更は、既存のクライアントにとって非互換と認識される API の意味上の変更を表す可能性がある。以下は、`google.api.field_behavior` に関する後方非互換な変更の例である:

* 以前 `OPTIONAL` と見なされていた（暗黙的または明示的に）既存のフィールドに `REQUIRED` を追加すること
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加すること
* 以前入力として受け付けられていた既存のフィールドに `OUTPUT_ONLY` を追加すること
* 以前出力として出力されていた既存のフィールドに `INPUT_ONLY` を追加すること
* 以前 mutable と見なされていた既存のフィールドに `IMMUTABLE` を追加すること
* 以前入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除すること
* 既存のフィールドから `IDENTIFIER` を削除すること

後方互換性の _ある_ 変更もあり、次のとおりである:

* 既存のフィールドに `OPTIONAL` を追加すること
* 既存の `name` フィールドに `IDENTIFIER` を追加すること
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更すること
* 既存のフィールドで `OUTPUT_ONLY` や `IMMUTABLE` から `IDENTIFIER` に変更すること
* 既存のフィールドから `REQUIRED` を削除すること
* 以前レスポンスから除外されていた既存のフィールドから `INPUT_ONLY` を削除すること
* 以前 immutable と見なされていた既存のフィールドから `IMMUTABLE` を削除すること

## 根拠

### Identifier フィールド動作

リソース名は、準拠するすべてのリソースの主識別子であり、作成時にユーザーによって完全に構築されることは決してない。そのようなフィールドには通常 `OUTPUT_ONLY` のフィールド動作が割り当てられる。しかし、リソース自体が主リクエストペイロードであるシナリオでは、主識別子としてしばしば使用される。そのようなフィールドは `OUTPUT_ONLY` とは見なせ _ない_。さらに、標準更新のような変更リクエストでは、主識別子としてのリソース名をその場で変更することはできない。そのようなフィールドには通常 `IMMUTABLE` のフィールド動作が割り当てられる。これらの相反しコンテキスト依存のフィールド動作により、リソース名フィールドの動作を区別して伝えるために新しい値が必要となった。

### 必要なアノテーションのセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須または任意のいずれかであり、したがって少なくともそれぞれ `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の要求

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを要求することは、API の作成時に API 作成者が動作を明示的に検討することも強制する。

初期作成後にフィールド動作を変更すると、クライアントに後方非互換な変更をもたらす可能性がある。例えば、任意フィールドを必須にすると、RPC のメソッドシグネチャや[宣言的クライアント][Declarative client]内のリソースに後方非互換な変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 背景

2023-05 に field_behavior が必須化された。この変更以前は、アノテーションがしばしば省略されていた。その値は高品質なクライアントを生成するために利用されている。さらに、メジャーバージョン内で事後に一部の field_behavior 値を追加または変更すると、後方非互換になる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

API 作成時に field_behavior を要求することの利点は、そうしないことによるクライアントと API ユーザーへのコストを上回る。
