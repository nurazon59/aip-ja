# フィールド動作の文書化

Protocol Buffersでフィールドを定義する際には、フィールドの動作に関する特定の側面（requiredかoptionalかなど）をユーザーに説明することが慣例である。さらに、この動作を他のツールが理解することも有用である（例えば、クライアントライブラリのシグネチャを最適化するためなど）。

## ガイダンス

APIは、`google.api.field_behavior` アノテーションを使用して、フィールドがrequiredやimmutableであるなど、十分に理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上の AIP-154 の `etag` フィールドがあり、これにはいかなる `google.api.field_behavior` も割り当てる**べきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合の特定の動作はコメントに文書化**すべきである**（should）。
- アノテーションは、フィールドの動作を正確に記述する任意の [google.api.FieldBehavior][] 値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- APIは、最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれか1つを使用**しなければならない**（must）。

**警告:** `field_behavior` は proto レベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれに依存している。新しいフィールドを追加する際には、どの値が関連するかを十分に検討し、考慮すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` と解釈される。それでもなお、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は_記述_目的にのみ使用され、それ自体がバリデーションを追加するものではない。目的は、クライアント向けにこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージのフィールド動作を `REQUIRED` とし、親フィールドを `OPTIONAL` とすることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記のケースでは、`title` が指定された場合、`text` フィールドはrequiredである。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは `name` フィールドに付与**しなければならず**（must）、他のいかなるフィールドにも付与**してはならない**（must not）（[リソース名を表現するフィールド][fields representing resource names] を参照）。

`IDENTIFIER` 値は、createメソッドのコンテキストではそのフィールドが入力として受け入れられない（すなわち `OUTPUT_ONLY`）ことを伝えるが、同時に `IMMUTABLE` とみなされ、リソースを主入力として受け入れる変更メソッド（例：[標準 Update][aip-134]）では入力として受け入れられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力フィールドと出力フィールドのいずれにも、requiredとoptionalのいずれにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableなフィールドを受け取った場合、それが更新マスクに含まれていても、値が一致すればサービスはそのフィールドを無視**すべきであり**（should）、変更が要求された場合は `INVALID_ARGUMENT` エラーを返す**べきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- アプリケーションの存続期間中に変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、そのフィールドがリクエストで提供され、対応するフィールドが出力には含まれないことを示す。

さらに、フィールドを input only と記述**すべきである**（should）のは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合のみである。特に、リクエストメッセージ（RPCの引数としてのみ機能し、名前が通常 `Request` で終わるメッセージ）内のフィールドは、既に暗黙的にそうであるため、input only と記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- AIP-214 で説明されている `ttl` フィールド。

**警告:** Input only フィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常 `Request` で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optional と記述**してもよい**（may）。

**注:** フィールドの存在ラベル `optional` とフィールド動作 `OPTIONAL` は相互に排他的ではない。詳細については AIP-149 を参照。

### Output only

`OUTPUT_ONLY` の使用は、そのフィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も行われないことを示す（サーバーは、このフィールドのすべての値をクリア**しなければならず**（must）、入力時にこのフィールドに値が存在することを理由にエラーをスロー**してはならない**（must not））。同様に、サービスは更新フィールドマスクにおけるoutput onlyフィールドの存在を無視**しなければならない**（must）（AIP-161 を参照）。

さらに、フィールドを output only と記述**すべきである**（should）のは、リソースメッセージ内のフィールド、またはツリーのさらに下のメッセージのフィールドである場合のみである。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常 `Response` で終わるメッセージ）内のフィールドは、既に暗黙的にそうであるため、output only と記述**すべきではない**（should not）。

Output only フィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在し、かつ空でない値に設定され**なければならない**（must）ことを示す。

フィールドを required と記述**すべきである**（should）のは、以下の_いずれか_の場合のみである：

- リソース上のフィールドであり、ユーザーが入力としてどこかで提供する場合。この場合、リソースは「truthy」な値が_格納_されている場合にのみ有効である。
  - リソースを[作成][aip-133]する際には、createリクエストでそのフィールドの値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際に、ユーザーがそのフィールドを省略**してもよい**（may）のは、フィールドがフィールドマスクにも存在せず、フィールドに変更がないことを示す場合である（そうでない場合は提供**されなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、名前が通常 `Request` で終わるメッセージ）上のフィールドである場合。この場合、値がリクエストの一部として提供**されなければならず**（must）、提供されない場合はエラー（通常 `INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false` 以外の値
- 繰り返しフィールドマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つ任意のメッセージ。

以下のことを示すためにフィールドを required と記述**すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで必要となるフィールド。
- ユーザー入力として決して使用されない、任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブーリアンの `false`、整数の `0`、enumの未指定値など）は未設定値と区別がつかないため、requiredフィールドにfalsyな値を設定するとエラーが発生する。この帰結として、requiredなブーリアンは `true` に設定しなければならない。

### 順序なしリスト

リソースの繰り返しフィールドにおける `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

サービスが、リスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、フィールドを順序なしリストと記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返し**てもよく**（may）、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントにとって非互換と認識されるAPIの意味的変更を表す可能性がある。以下は、`google.api.field_behavior` に関する後方互換性のない変更の例である：

* 以前に `OPTIONAL` とみなされていた（暗黙的または明示的に）既存のフィールドに `REQUIRED` を追加すること
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加すること
* 以前に入力として受け入れられていた既存のフィールドに `OUTPUT_ONLY` を追加すること
* 以前に出力として生成されていた既存のフィールドに `INPUT_ONLY` を追加すること
* 以前に変更可能とみなされていた既存のフィールドに `IMMUTABLE` を追加すること
* 以前に入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除すること
* 既存のフィールドから `IDENTIFIER` を削除すること。

後方互換性が_ある_変更も存在し、以下のとおりである：

* 既存のフィールドに `OPTIONAL` を追加すること
* 既存の `name` フィールドに `IDENTIFIER` を追加すること
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更すること
* 既存のフィールドで `OUTPUT_ONLY` や `IMMUTABLE` から `IDENTIFIER` に変更すること
* 既存のフィールドから `REQUIRED` を削除すること
* 以前にレスポンスで除外されていた既存のフィールドから `INPUT_ONLY` を削除すること
* 以前にimmutableとみなされていた既存のフィールドから `IMMUTABLE` を削除すること

## 根拠

### Identifier フィールド動作

準拠したリソースの主識別子であるリソース名は、作成時にユーザーによって完全に構築されることは決してない。このようなフィールドには通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかしながら、リソース自体が主リクエストペイロードとなるシナリオでは、主識別子としてもよく使用される。そのようなフィールドは `OUTPUT_ONLY` とはみなせ*ない*。さらに、標準Updateのような変更リクエストでは、主識別子としてのリソース名はその場で変更できない。このようなフィールドには通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの相反しコンテキストに依存するフィールド動作により、リソース名フィールドの動作を特定して伝えるために新しい値が必要になった。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須か任意のいずれかであり、したがってそれぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須化することで、API作成者はAPIの初期作成時に動作を明示的に考慮せざるを得なくなる。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更が生じる可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023年5月に field_behavior が必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は、高品質なクライアントを生成するために依存されている。さらに、事後にメジャーバージョン内で field_behavior 値を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

API作成時に field_behavior を必須化する利点は、そうしない場合にクライアントやAPIユーザーが被るコストを上回る。
