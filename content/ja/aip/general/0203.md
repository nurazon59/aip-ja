# フィールド動作のドキュメント

Protocol Buffersでフィールドを定義する際、フィールドの動作の特定の側面（requiredかoptionalかなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解することも有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは、フィールドがrequiredまたはimmutableであるなど、よく理解されたフィールド動作を説明するために `google.api.field_behavior` アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の `etag` フィールドには、どの `google.api.field_behavior` も割り当て**るべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合コメントで特定の動作を文書化**すべきである**（should）。
- アノテーションは、フィールドの動作を正確に説明する [google.api.FieldBehavior][] の値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- APIは、最低限 `REQUIRED`、`OPTIONAL`、または `OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを十分に検討し確認すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` と解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は _記述的_ 目的のみのためのものであり、それ自体はバリデーションを追加しない。目的は、クライアント向けにこの動作を一貫してドキュメント化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージが `REQUIRED` のフィールド動作を持ち、親フィールドが `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定された場合、`text` フィールドは必須である。

## 語彙

### 識別子

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは `name` フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER` 値は、Createメソッドのコンテキストではフィールドが入力として受け付けられない（すなわち `OUTPUT_ONLY`）ことを伝える一方、リソースを主要入力として受け付ける変更メソッド（例：[標準Update][aip-134]）では `IMMUTABLE` と見なされ、かつ入力として受け付けられることも伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はフィールドを無視**すべきであり**（should）、変更が要求された場合は `INVALID_ARGUMENT` エラーを返**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- アプリケーションの存続期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドには、immutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールドまたはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、名前が通常 `Request` で終わるメッセージ）内のフィールドは、これがすでに暗黙的であるため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- AIP-214で説明されている `ttl` フィールド。

**警告:** Input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須ではないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常 `Request` で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細はAIP-149を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにフィールドを含めても何も起こらない（サーバーはこのフィールドの値をクリア**しなければならず**（must）、入力時にこのフィールドに値が存在してもエラーをスロー**してはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーのより下位のメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常 `Response` で終わるメッセージ）内のフィールドは、これがすでに暗黙的であるため、output onlyとして記述**すべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生または構造化された情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソースに存在**しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、次の _いずれか_ の場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が _保存されている_ 場合にのみ有効である。
  - リソースを[作成][aip-133]する際、Createリクエストでフィールドに値が提供**されなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在しない場合（フィールドに変更がないことを示す）に限り、フィールドを省略**してもよい**（may）（それ以外の場合は提供**されなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、名前が通常 `Request` で終わるメッセージ）上のフィールドである。この場合、値がリクエストの一部として提供**されなければならず**（must）、提供しない場合はエラー（通常 `INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/バイト、`false` 以外の値
- 繰り返しフィールドおよびマップの場合、少なくとも1つのエントリがある値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つメッセージ

フィールドは、以下を示すためにrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きでrequiredなフィールド。
- ユーザー入力として決して使用されない任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enumの未指定値など）は未設定の値と区別できず、そのためrequiredフィールドにfalsyな値を設定するとエラーが発生する。これの系として、requiredなブール値は `true` に設定しなければならない。

### 順序なしリスト

リソースの繰り返しフィールドでの `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、リスト内の要素の順序がユーザーが送信した順序と一致することをサービスが保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返し**てもよく**（may）、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` の値を追加または変更することは、既存のクライアントにとって互換性がないと認識されるAPIの意味的な変更を表す場合がある。以下は `google.api.field_behavior` に関する後方互換性のない変更の例である：

* 以前に（暗黙的または明示的に）`OPTIONAL` と見なされていた既存のフィールドに `REQUIRED` を追加すること
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加すること
* 以前に入力として受け付けられていた既存のフィールドに `OUTPUT_ONLY` を追加すること
* 以前に出力として生成されていた既存のフィールドに `INPUT_ONLY` を追加すること
* 以前に可変と見なされていた既存のフィールドに `IMMUTABLE` を追加すること
* 以前に入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除すること
* 既存のフィールドから `IDENTIFIER` を削除すること

後方互換性が _ある_ 変更もあり、以下の通りである：

* 既存のフィールドに `OPTIONAL` を追加すること
* 既存の `name` フィールドに `IDENTIFIER` を追加すること
* 既存のフィールドを `REQUIRED` から `OPTIONAL` に変更すること
* 既存のフィールドで `OUTPUT_ONLY` および/または `IMMUTABLE` から `IDENTIFIER` に変更すること
* 既存のフィールドから `REQUIRED` を削除すること
* 以前にレスポンスで除外されていた既存のフィールドから `INPUT_ONLY` を削除すること
* 以前にimmutableと見なされていた既存のフィールドから `IMMUTABLE` を削除すること

## 根拠

### 識別子フィールド動作

リソース名は、あらゆる準拠リソースの主要識別子であり、Create時にユーザーによって完全に構築されることはない。このようなフィールドには通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、これらはリソース自体が主要なリクエストペイロードとなるシナリオでは、主要識別子として消費されることも多い。このようなフィールドは `OUTPUT_ONLY` とは見なせ_なかった_。さらに、標準Updateのような変更リクエストでは、主要識別子としてのリソース名はその場で変更できない。このようなフィールドには通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの矛盾したコンテキスト依存のフィールド動作は、リソース名フィールドの動作を抽出して伝えるために新しい値が必要であることを意味していた。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドはrequiredまたはoptionalのいずれかであり、したがって少なくともそれぞれ `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の強制

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを要求することは、API作成者がAPIの初期作成時に動作を明示的に検討することも強いる。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更をもたらす可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]でのリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023年5月に、field_behaviorが必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後にfield_behaviorの値の一部を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを要求することの利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
