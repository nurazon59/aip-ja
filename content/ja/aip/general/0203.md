# フィールドの振る舞いの説明

Protocol Buffers でフィールドを定義する際、フィールドの振る舞いに関する特定の側面（required か optional かなど）をユーザーに説明するのが通例である。さらに、他のツールがこの振る舞いを理解できることは有用である（たとえば、クライアント ライブラリのシグネチャを最適化するため）。

## ガイダンス

API は `google.api.field_behavior` アノテーションを使用して、フィールドが required か immutable かなど、よく理解されたフィールドの振る舞いを記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- API は、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の `etag` フィールドには、いかなる `google.api.field_behavior` も割り当てる**べきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合、特定の振る舞いをコメントに文書化**すべきである**（should）。
- アノテーションは、フィールドの振る舞いを正確に記述するすべての [google.api.FieldBehavior][] 値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- API は最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれか 1 つを使用**しなければならない**（must）。

**警告:** `field_behavior` は proto レベルの動作に影響を与えないが、多くのクライアント（CLI や SDK など）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを十分に確認し検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` と解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで示す語彙は _記述的_ な目的のみであり、それ自体がバリデーションを追加するものではない。目的は、クライアント向けにこの振る舞いを一貫して文書化することである。

### ネストされたメッセージのフィールドの振る舞い

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

たとえば、ネストされたメッセージのフィールドの振る舞いが `REQUIRED` であり、親フィールドが `OPTIONAL` であることができる:

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されると、`text` フィールドは required である。

## 語彙

### identifier

`IDENTIFIER` の使用は、リソース メッセージ内のフィールドがリソースの識別に使用されることを示す。`name` フィールドに付与**しなければならず**（must）、他のフィールドには付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names] を参照）。

`IDENTIFIER` 値は、作成メソッドのコンテキストではそのフィールドが入力として受け付けられない（すなわち `OUTPUT_ONLY`）ことを伝える一方で、`IMMUTABLE` とも見なされ、リソースを主入力として受け付ける変更メソッド（例: [標準更新][aip-134]）では入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、required または optional のいずれのフィールドにも適用できる。

サービスが更新リクエスト（または同様のもの）で immutable フィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はサービスはフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` エラーを返す**べきである**（should）。

immutable フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである:

- アプリケーションの存続期間中に変更できないリソースの属性（例: ディスクタイプ）。

**注:** 「条件付きで immutable」なフィールドに immutable アノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソース メッセージ内のフィールドか、リソース メッセージに含まれるメッセージのフィールドである場合にのみ、input only と記述**すべきである**（should）。特に、リクエスト メッセージ（RPC の引数としてのみ機能し、名前が通常 `Request` で終わるメッセージ）内のフィールドは、それが既に自明であるため、input only と記述**すべきではない**（should not）。

input only フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである:

- AIP-214 で説明されている `ttl` フィールド。

**警告:** input only フィールドは稀であり、使用前に慎重に検討すべきである。

### optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエスト メッセージ（RPC の引数で、名前が通常 `Request` で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合に、optional と記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互に排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにそのフィールドを含めても何も起こらないことを示す（サーバーはこのフィールドの値をすべてクリア**しなければならず**（must）、入力時にこのフィールドに値が存在することを理由にエラーを送出**してはならない**（must not））。同様に、サービスは更新フィールド マスク内の output only フィールドの存在を無視**しなければならない**（must）（AIP-161 を参照）。

さらに、フィールドは、リソース メッセージ内のフィールドか、ツリーの下位にあるメッセージのフィールドである場合にのみ、output only と記述**すべきである**（should）。特に、レスポンス メッセージ（RPC の戻り値としてのみ機能し、名前が通常 `Response` で終わるメッセージ）内のフィールドは、それが既に自明であるため、output only と記述**すべきではない**（should not）。

Output only フィールドは、API にとって適切であれば空の値に設定**してもよい**（may）。

output only フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである:

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）（かつ空でない値に設定**されなければならない**（must））ことを示す。

フィールドは、以下の _いずれか_ の場合にのみ required と記述**すべきである**（should）:

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が _格納_ されている場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエスト上でフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールド マスクにも存在しない場合に限りそのフィールドを省略**してもよい**（may）（フィールドに変更がないことを示す）。そうでなければ、提供**しなければならない**（must）。
- リクエスト メッセージ（RPC の引数で、名前が通常 `Request` で終わるメッセージ）上のフィールドである。この場合、リクエストの一部として値を提供**しなければならず**（must）、そうしない場合、エラー（通常は `INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する:

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト列、`false` 以外の値
- repeated フィールドや map の場合、少なくとも 1 つのエントリを持つ値
- メッセージの場合、少なくとも 1 つの「truthy」なフィールドを持つすべてのメッセージ

フィールドは以下のことを示すために required と記述**すべきではない**（should not）:

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで required となるフィールド。
- ユーザー入力として使用されることのない、任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enum の未指定値など）は未設定の値と区別できず、そのため required フィールドに falsy な値を設定するとエラーになる。この帰結として、required なブール値は `true` に設定しなければならない。

### 順序なしリスト

リソースの repeated フィールドにおける `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーの送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）に、順序なしリストと記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返却**してもよい**（may）し、ランダム化された不安定な順序で返却**してもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントにとって互換性がないと認識される API の意味上の変更を表す可能性がある。以下は `google.api.field_behavior` に関する後方互換性のない変更の例である:

* 以前に `OPTIONAL` と見なされていた（明示的または暗黙的に）既存のフィールドへの `REQUIRED` の追加
* `REQUIRED` とアノテーションされた新しいフィールドの既存のリクエスト メッセージへの追加
* 以前に入力として受け付けられていた既存のフィールドへの `OUTPUT_ONLY` の追加
* 以前に出力として送出されていた既存のフィールドへの `INPUT_ONLY` の追加
* 以前に変更可能と見なされていた既存のフィールドへの `IMMUTABLE` の追加
* 以前に入力として無視されていた既存のフィールドからの `OUTPUT_ONLY` の削除
* 既存のフィールドからの `IDENTIFIER` の削除。

以下は後方互換性の _ある_ 変更である:

* 既存のフィールドへの `OPTIONAL` の追加
* 既存の `name` フィールドへの `IDENTIFIER` の追加
* 既存のフィールドにおける `REQUIRED` から `OPTIONAL` への変更
* 既存のフィールドにおける `OUTPUT_ONLY` または `IMMUTABLE`、あるいはその両方からの `IDENTIFIER` への変更
* 既存のフィールドからの `REQUIRED` の削除
* 以前にレスポンスで除外されていた既存のフィールドからの `INPUT_ONLY` の削除
* 以前に immutable と見なされていた既存のフィールドからの `IMMUTABLE` の削除

## 根拠

### identifier フィールドの振る舞い

リソース名（任意の準拠リソースの主要識別子）は、作成時にユーザーが完全に構築することは決してない。そのようなフィールドは通常 `OUTPUT_ONLY` フィールドの振る舞いが割り当てられる。しかしながら、リソース自体が主要なリクエストペイロードとなるシナリオでは、主要識別子として使用されることも多い。そのようなフィールドは `OUTPUT_ONLY` と見なすことが _できなかった_。さらに、標準更新のような変更リクエストでは、主要識別子としてのリソース名をその場で変更することはできない。そのようなフィールドには通常 `IMMUTABLE` フィールドの振る舞いが割り当てられる。これらの競合しコンテキストに依存するフィールドの振る舞いは、リソース名フィールドの振る舞いを抽出して伝えるために新しい値が必要であることを意味していた。

### 必須のアノテーションセット

リクエスト メッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは required か optional のいずれかであり、したがって少なくともそれぞれ `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールドの振る舞いの必須化

各フィールドにフィールドの振る舞いアノテーションを含めることで、リソースが示す全体的な振る舞いがより明確に定義される。明確に定義されたフィールドの振る舞いは、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須とすることで、API 作成者は API の初期作成時に振る舞いを明示的に検討せざるを得なくなる。

初期作成後にフィールドの振る舞いを変更すると、クライアントに後方互換性のない変更が生じる可能性がある。たとえば、optional フィールドを required にすると、RPC のメソッド シグネチャや[宣言的クライアント][Declarative client]におけるリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

## 経緯

2023年5月に field_behavior が必須となった。この変更以前は、アノテーションはしばしば省略されていた。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後に field_behavior 値を追加または変更すると、後方互換性が損なわれる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

API 作成時に field_behavior を必須とすることの利点は、そうしない場合のクライアントと API ユーザーへのコストを上回る。
