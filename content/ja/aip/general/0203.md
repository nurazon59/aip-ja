# フィールド動作のドキュメント化

protocol buffersでフィールドを定義する際、そのフィールドの動作に関する特定の側面（必須かオプショナルかなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解することは（例えば、クライアントライブラリのシグネチャを最適化するために）有用である。

## ガイダンス

APIは、`google.api.field_behavior` アノテーションを使用して、フィールドが必須であるかimmutableであるかなど、十分に理解されているフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - AIP-154のリソースメッセージ上の `etag` フィールドはこの例外であり、`google.api.field_behavior` を割り当て**るべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を**省略してもよい**（may）が、この場合、特定の動作をコメントで**文書化すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する任意の [google.api.FieldBehavior][] 値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- APIは少なくとも `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` はプロトコルレベルの動作に影響を与えないが、多くのクライアント（例：CLIやSDK）はコード生成のためにこれらに依存している。新しいフィールドを追加する際には、関連する値を十分に確認し、検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` として解釈される。とはいえ、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は*記述的*な目的のためのみであり、それ自体がバリデーションを追加するものではない。目的は、クライアントのためにこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージの `google.api.field_behavior` アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージは `REQUIRED` のフィールド動作を持ち、親フィールドは `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記のケースでは、`title` が指定された場合、`text` フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER` 値は、createメソッドのコンテキストではフィールドが入力として受け付けられない（すなわち `OUTPUT_ONLY`）ことを伝えると同時に、リソースを主入力として受け付ける変更メソッド（例：[標準Update][aip-134]）では `IMMUTABLE` とみなされ、入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更不可能であることを示す。これは、入力または出力、必須またはオプショナルのどちらのフィールドにも適用できる。

サービスが更新リクエスト（または同様のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを**無視すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` で**エラーとすべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- アプリケーションの存続期間中に変更不可能なリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドには、immutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして**記述されるべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常は `Request` で終わる名前を持つメッセージ）内のフィールドは、すでにそれが暗示されているため、input onlyとして**記述されるべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- AIP-214で説明されている `ttl` フィールド。

**警告:** Input onlyフィールドは稀であり、使用前に慎重に検討する必要がある。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であるメッセージで、通常は `Request` で終わる名前を持つ）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして**記述してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにそのフィールドを含めても何も行われない（サーバーはこのフィールドの値を**クリアしなければならず**（must）、入力時にこのフィールドに値が存在することによるエラーを**発生させてはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を**無視しなければならない**（must）（AIP-161を参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーのより深い位置にあるメッセージのフィールドである場合にのみ、output onlyとして**記述されるべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常は `Response` で終わる名前を持つメッセージ）内のフィールドは、すでにそれが暗示されているため、output onlyとして**記述されるべきではない**（should not）。

Output onlyフィールドは、APIに適切であれば空の値に**設定してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生または構造化された情報。
- 変更不可能なサービスによって割り当てられたリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソースに**存在しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下のいずれかの場合にのみrequiredとして**記述されるべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、createリクエストでフィールドに値が**提供されなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在しない場合に限り、そのフィールドを**省略してもよい**（may）（フィールドに変更がないことを示す）（そうでない場合は**提供しなければならない**（must））。
- リクエストメッセージ（RPCの引数であるメッセージで、通常は `Request` で終わる名前を持つ）上のフィールドである。この場合、値がリクエストの一部として**提供されなければならず**（must）、提供されない場合はエラー（通常は`INVALID_ARGUMENT`）を**発生させなければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false` 以外の値
- repeatedフィールドやマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つ任意のメッセージ

以下のことを示すためにフィールドをrequiredとして**記述すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として使用されない任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enumの未指定値など）は未設定値と区別できないため、requiredフィールドにfalsyな値を設定するとエラーが発生する。この帰結として、requiredなブール値は `true` に設定しなければならない。

### Unordered List

リソースのrepeatedフィールドでの `UNORDERED_LIST` の使用は、サービスがリスト内のアイテムの順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、unordered listとして**記述されるべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で**返してもよい**（may）し、ランダム化された不安定な順序で**返してもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加または変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味上の変更を表す可能性がある。以下は `google.api.field_behavior` に関する後方互換性のない変更の例である：

* 以前に `OPTIONAL` とみなされていた（暗黙的または明示的な）既存のフィールドへの `REQUIRED` の追加
* `REQUIRED` とアノテーションされた新しいフィールドの既存のリクエストメッセージへの追加
* 以前に入力として受け付けられていた既存のフィールドへの `OUTPUT_ONLY` の追加
* 以前に出力として出力されていた既存のフィールドへの `INPUT_ONLY` の追加
* 以前に変更可能とみなされていた既存のフィールドへの `IMMUTABLE` の追加
* 以前に入力として無視されていた既存のフィールドからの `OUTPUT_ONLY` の削除
* 既存のフィールドからの `IDENTIFIER` の削除

後方互換性が*ある*変更もあり、以下の通り：

* 既存のフィールドへの `OPTIONAL` の追加
* 既存の `name` フィールドへの `IDENTIFIER` の追加
* 既存のフィールドの `REQUIRED` から `OPTIONAL` への変更
* 既存のフィールドの `OUTPUT_ONLY` または `IMMUTABLE` またはその両方から `IDENTIFIER` への変更
* 既存のフィールドからの `REQUIRED` の削除
* 以前にレスポンスから除外されていた既存のフィールドからの `INPUT_ONLY` の削除
* 以前にimmutableとみなされていた既存のフィールドからの `IMMUTABLE` の削除

## 根拠

### Identifierフィールド動作

リソース名（あらゆる準拠リソースの主要な識別子）は、作成時にユーザーによって完全に構築されることはない。そのようなフィールドは通常、`OUTPUT_ONLY` フィールド動作を割り当てられる。しかし、それらはリソース自体が主要なリクエストペイロードであるシナリオでは、主要な識別子として利用されることも多い。そのようなフィールドは `OUTPUT_ONLY` とは*みなせない*。さらに、標準Updateのような変更リクエストでは、主要な識別子としてのリソース名はその場で変更できない。そのようなフィールドは通常、`IMMUTABLE` フィールド動作を割り当てられる。これらの競合しコンテキストに依存するフィールド動作は、リソース名フィールドの動作を特定して伝えるための新しい値が必要であることを意味した。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須かオプショナルかのいずれかであり、したがってそれぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを**持つべきである**（should）。`INPUT_ONLY` だけを提供してもフィールドの必要性を伝えることはできないため、`REQUIRED` または `OPTIONAL` の指定が依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須にすることで、API作成者はAPIの最初の作成時に動作を明示的に検討するよう求められる。

最初の作成後にフィールド動作を変更すると、クライアントにおける後方互換性のない変更につながる可能性がある。例えば、オプショナルフィールドを必須にすると、[宣言的クライアント][Declarative client]のRPCのメソッドシグネチャやリソースにおける後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023-05にfield_behaviorが必須になった。この変更以前は、アノテーションはしばしば省略されていた。その値は高品質なクライアントを生成するために依存されている。さらに、主要バージョン内で後からfield_behaviorの値を追加または変更することは、後方互換性がない場合がある。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

API作成時にfield_behaviorを要求することで得られる利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
