# フィールド動作の文書化

protocol buffersでフィールドを定義する際、フィールドの動作の特定の側面（requiredかoptionalかなど）をユーザーに説明することが慣例である。さらに、他のツールがこの動作を理解できることは有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは`google.api.field_behavior`アノテーションを使用して、フィールドがrequiredやimmutableであるといった、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージのすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の`etag`フィールドには、いかなる`google.api.field_behavior`も割り当てる**べきではない**（should not）。
- アノテーションには、フィールドの動作を正確に記述する任意の[google.api.FieldBehavior][]値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは最低限、`REQUIRED`、`OPTIONAL`、または`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存する。新しいフィールドを追加する際は、どの値が関連するかを徹底的にレビューし検討する。

アノテーションのないフィールドは、後方互換性のために`OPTIONAL`として解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は*説明的*な目的のみであり、それ自体は検証を追加しない。目的は、クライアントに対してこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の`google.api.field_behavior`アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージが`REQUIRED`のフィールド動作を持ち、親フィールドが`OPTIONAL`であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されていれば、`text`フィールドはrequiredである。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。`name`フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、作成メソッドのコンテキストではフィールドが入力として受け付けられない（すなわち`OUTPUT_ONLY`）ことを伝える一方で、リソースを主要な入力として受け付ける変更メソッド（例：[Standard Update][aip-134]）では`IMMUTABLE`とみなされ、入力として受け付けられる。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はフィールドを無視する**べきである**（should）が、変更が要求された場合は`INVALID_ARGUMENT`でエラー**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- アプリケーションの存続期間中に変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドがリソースメッセージ内のフィールドまたはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして記述する**べきである**（should）。特に、リクエストメッセージ（通常`Request`で終わる名前を持ち、RPCの引数としてのみ機能するメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして記述する**べきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- AIP-214で説明されている`ttl`フィールド。

**警告:** input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドがrequiredではないことを示す。

フィールドがリクエストメッセージ（RPCの引数であるメッセージで、通常`Request`で終わる）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにフィールドを含めても何も起こらないことを示す（サーバーはこのフィールドのいかなる値もクリア**しなければならず**（must）、入力時にこのフィールドの値が存在する結果としてエラーをスロー**してはならない**（must not））。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（AIP-161を参照）。

さらに、フィールドがリソースメッセージ内のフィールド、またはツリーのさらに下のメッセージのフィールドである場合にのみ、output onlyとして記述する**べきである**（should）。特に、レスポンスメッセージ（通常`Response`で終わる名前を持ち、RPCの戻り値としてのみ機能するメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして記述する**べきではない**（should not）。

output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）（かつ非空の値に設定されていること）を示す。

フィールドは、以下のいずれかの場合にのみrequiredとして記述する**べきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストのフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドを省略**してもよい**（may）。ただし、フィールドがフィールドマスクにも存在せず、フィールドに変更がないことを示す場合に限る（そうでない場合は提供**しなければならない**（must））。
- リクエストメッセージ（RPCの引数であるメッセージで、通常`Request`で終わる名前）上のフィールドである。この場合、リクエストの一部として値を提供**しなければならず**（must）、提供しない場合はエラー（通常`INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false`以外の値
- repeatedフィールドとマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つ任意のメッセージ

以下のことを示すためにフィールドをrequiredとして記述する**べきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きでrequiredとなるフィールド。
- ユーザー入力として使用されない任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定値と区別がつかないため、requiredフィールドをfalsyな値に設定するとエラーが発生する。この帰結として、requiredブール値は`true`に設定**しなければならない**（must）。

### Unordered List

リソースのrepeatedフィールドでの`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、フィールドをunordered listとして記述する**べきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよく**（may）、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`値の追加または変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味的変更を表す可能性がある。以下は`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前は（暗黙的または明示的に）`OPTIONAL`とみなされていた既存フィールドへの`REQUIRED`の追加
* 既存のリクエストメッセージへの`REQUIRED`とアノテーションされた新しいフィールドの追加
* 以前は入力として受け付けられていた既存フィールドへの`OUTPUT_ONLY`の追加
* 以前は出力として出力されていた既存フィールドへの`INPUT_ONLY`の追加
* 以前は変更可能とみなされていた既存フィールドへの`IMMUTABLE`の追加
* 以前は入力として無視されていた既存フィールドからの`OUTPUT_ONLY`の削除
* 既存フィールドからの`IDENTIFIER`の削除

以下のような後方互換性が*ある*変更もある：

* 既存フィールドへの`OPTIONAL`の追加
* 既存の`name`フィールドへの`IDENTIFIER`の追加
* 既存フィールドでの`REQUIRED`から`OPTIONAL`への変更
* 既存フィールドでの`OUTPUT_ONLY`および/または`IMMUTABLE`から`IDENTIFIER`への変更
* 既存フィールドからの`REQUIRED`の削除
* 以前はレスポンスで除外されていた既存フィールドからの`INPUT_ONLY`の削除
* 以前はimmutableとみなされていた既存フィールドからの`IMMUTABLE`の削除

## 根拠

### Identifierフィールド動作

リソース名は、準拠するあらゆるリソースの主要な識別子であり、作成時にユーザーが完全に構築することは決してない。このようなフィールドには通常`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードであるシナリオでは、主要な識別子としても頻繁に使用される。このようなフィールドは`OUTPUT_ONLY`とはみなせ*ない*。さらに、Standard Updateのような変更リクエストでは、主要な識別子としてのリソース名はその場で変更できない。このようなフィールドには通常`IMMUTABLE`フィールド動作が割り当てられる。これらの相反する文脈依存のフィールド動作は、リソース名フィールドの動作を選別して伝えるために新しい値が必要であることを意味した。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれか**でなければならない**（must）。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドはrequiredまたはoptionalのいずれかであり、したがってそれぞれ少なくとも`REQUIRED`または`OPTIONAL`アノテーションを持つ**べきである**（should）。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須化することは、API作成者がAPIの初期作成時に動作を明示的に検討することも強制する。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更をもたらす可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後的に一部のfield_behavior値を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを必須化することの利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
