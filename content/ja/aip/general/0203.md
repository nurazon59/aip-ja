# フィールド動作の文書化

Protocol Buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（必須かオプショナルかなど）をユーザーに説明するのが慣例である。さらに、他のツールがこの動作を理解できることは有用である（例えば、クライアントライブラリのシグネチャを最適化するためなど）。

## ガイダンス

APIは`google.api.field_behavior`アノテーションを使用して、フィールドが必須であるかimmutableであるかなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIはリクエストで使用されるメッセージまたはサブメッセージのすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
- アノテーションには、フィールドの動作を正確に記述する[google.api.FieldBehavior][]の値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは最低限、`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**Warning:** `field_behavior`はprotoレベルの動作には影響しないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれに依存している。新しいフィールドを追加する際には、どの値が関連するかを徹底的にレビューおよび検討すること。

アノテーションのないフィールドは、後方互換性のために`OPTIONAL`として解釈される。それでも、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで示される語彙は*記述的*な目的のみのためのものであり、それ自体が検証を追加するものではない。目的は、この動作をクライアント向けに一貫して文書化することである。

### field behavior of nested messages

ネストされたメッセージの`google.api.field_behavior`アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージは`REQUIRED`のフィールド動作を持つことができるが、親フィールドは`OPTIONAL`にできる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記のケースでは、`title`が指定されている場合、`text`フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは`name`フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、作成メソッドの文脈ではフィールドが入力として受け入れられない（すなわち`OUTPUT_ONLY`）ことを伝える一方で、リソースを主入力として受け取る変更メソッド（例：[標準Update][aip-134]）では`IMMUTABLE`とみなされ入力として受け入れられることも伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、必須またはオプショナルのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視する**べきである**（should）が、変更が要求された場合は`INVALID_ARGUMENT`でエラーに**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- アプリケーションのライフタイムを通じて変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージのフィールドまたはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして記述する**べきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常`Request`で終わる名前のメッセージ）内のフィールドは、すでにそれが暗示されているため、input onlyとして記述する**べきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- AIP-214で説明されている`ttl`フィールド。

**Warning:** Input onlyフィールドは稀であり、使用前に入念に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドが必須ではないことを示す。

フィールドがリクエストメッセージ（RPCの引数であり、通常`Request`で終わるメッセージ）のフィールド、またはサブメッセージのフィールドである場合、optionalとして記述し**てもよい**（may）。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も行われない（サーバーはこのフィールドの値をすべてクリア**しなければならず**（must）、入力にこのフィールドの値が存在することによるエラーをスロー**してはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージのフィールド、またはツリーのさらに下位のメッセージのフィールドである場合にのみ、output onlyとして記述する**べきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常`Response`で終わるメッセージ）内のフィールドは、すでにそれが暗示されているため、output onlyとして記述する**べきではない**（should not）。

Output onlyフィールドは、APIに適切な場合、空の値に設定し**てもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生または構造化された情報。
- 変更できない、サービスによって割り当てられたリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソースに存在**しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして記述する**べきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでそのフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在しない場合に限りそのフィールドを省略し**てもよい**（may）。これはフィールドに変更がないことを示す（そうでない場合は提供**しなければならない**（must））。
- RPCの引数であり、通常`Request`で終わる名前のリクエストメッセージのフィールドである。この場合、リクエストの一部として値を提供**しなければならず**（must）、提供しない場合はエラー（通常は`INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false`以外の値
- repeatedフィールドやマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つ任意のメッセージ

以下のことを示すために、フィールドをrequiredとして記述する**べきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定値と区別がつかないため、requiredフィールドにfalsyな値を設定するとエラーになる。この当然の帰結として、requiredなブール値は`true`に設定されなければならない。

### Unordered List

リソースのrepeatedフィールドでの`UNORDERED_LIST`の使用は、サービスがリスト内のアイテムの順序を保証しないことを示す。

サービスが、ユーザーが送信した順序とリスト内の要素の順序が一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、フィールドはunordered listとして記述する**べきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`値の追加または変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味論的な変更を表す場合がある。以下は`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前`OPTIONAL`（暗黙的または明示的に）とみなされていた既存フィールドへの`REQUIRED`の追加
* 既存のリクエストメッセージへの`REQUIRED`とアノテーションされた新しいフィールドの追加
* 以前入力として受け入れられていた既存フィールドへの`OUTPUT_ONLY`の追加
* 以前出力として出力されていた既存フィールドへの`INPUT_ONLY`の追加
* 以前mutableとみなされていた既存フィールドへの`IMMUTABLE`の追加
* 以前入力として無視されていた既存フィールドからの`OUTPUT_ONLY`の削除
* 既存フィールドからの`IDENTIFIER`の削除。

後方互換性が*ある*変更もあり、それは以下の通りである：

* 既存フィールドへの`OPTIONAL`の追加
* 既存の`name`フィールドへの`IDENTIFIER`の追加
* 既存フィールドの`REQUIRED`から`OPTIONAL`への変更
* 既存フィールドの`OUTPUT_ONLY`および/または`IMMUTABLE`から`IDENTIFIER`への変更
* 既存フィールドからの`REQUIRED`の削除
* 以前レスポンスで除外されていた既存フィールドからの`INPUT_ONLY`の削除
* 以前immutableとみなされていた既存フィールドからの`IMMUTABLE`の削除

## 根拠

### Identifierフィールド動作

リソース名（あらゆる準拠リソースの主識別子）は、作成時にユーザーによって完全に構築されることは決してない。このようなフィールドには通常`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、リソース自体が主リクエストペイロードとなるシナリオでは、主識別子として消費されることも多い。このようなフィールドは`OUTPUT_ONLY`とみなすことが*できなかった*。さらに、標準Updateのような変更リクエストでは、主識別子としてのリソース名をその場で変更することはできない。このようなフィールドには通常`IMMUTABLE`フィールド動作が割り当てられる。これらの競合し文脈依存のフィールド動作は、リソース名フィールドの動作を特定し伝達するために新しい値が必要であることを意味した。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力か出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドは必須かオプショナルのいずれかであり、したがってそれぞれ最低限`REQUIRED`または`OPTIONAL`アノテーションを持つべきである。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラマティッククライアントとユーザーの理解を向上させる。

アノテーションを必須化することは、APIの初期作成時にAPI作成者が動作を明示的に検討することも強制する。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更をもたらす可能性がある。例えば、オプショナルフィールドを必須にすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023-05にfield_behaviorが必須化された。この変更以前は、アノテーションはしばしば省略されていた。その値は高品質なクライアントを生成するために使用される。さらに、メジャーバージョン内で事後にfield_behaviorの値を追加・変更することは、後方互換性がない場合がある。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを必須化することの利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
