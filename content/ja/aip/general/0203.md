# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作の特定の側面（必須かオプショナルかなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解すること（例えば、クライアント ライブラリのシグネチャを最適化するため）も有用である。

## ガイダンス

APIは `google.api.field_behavior` アノテーションを使用して、フィールドがrequiredかimmutableかなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを**適用しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154 `etag` フィールドには、いかなる `google.api.field_behavior` も割り当て**るべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を**省略してもよい**（may）が、この場合コメントに特定の動作を**文書化すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する [google.api.FieldBehavior][] の値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` は使用**してはならない**（must not）。
- APIは最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作には影響しないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれに依存している。新しいフィールドを追加する際は、どの値が関連するかを十分に検討し、判断すること。

アノテーションのないフィールドは後方互換性のため `OPTIONAL` と解釈される。それでもなお、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで示される語彙は*記述的*な目的のみであり、それ自体でバリデーションを追加するものではない。目的は、この動作をクライアント向けに一貫して文書化することである。

### ネストされたメッセージのfield behavior

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージのフィールド動作が `REQUIRED` であっても、親フィールドが `OPTIONAL` である場合がある：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されていれば、`text` フィールドはrequiredである。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは `name` フィールドに**付加しなければならず**（must）、他のフィールドに付加**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER` 値は、作成メソッドのコンテキストではそのフィールドが入力として受け付けられない（すなわち `OUTPUT_ONLY`）ことを伝える一方で、[標準Update][aip-134]のようにリソースを主要な入力として受け付ける変更メソッドでは `IMMUTABLE` とみなされ入力として受け付けられる。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、requiredまたはoptionalのいずれにも適用される。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致していればそのフィールドを**無視すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` で**エラーとすべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- アプリケーションの有効期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにはimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（通常 `Request` で終わる名前で、RPCの引数としてのみ動作するメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- AIP-214で説明されている `ttl` フィールド。

**警告:** Input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須ではないことを示す。

フィールドは、リクエストメッセージ（通常 `Request` で終わる、RPCの引数であるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

**注:** フィールド存在ラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細はAIP-149を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにそのフィールドを含めても何も起こらない（サーバーはこのフィールドの値をクリアしなければならず、入力にこのフィールドの値が存在する結果としてエラーを**投げてはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を**無視しなければならない**（must）（AIP-161参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーのより深い位置にあるメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（通常 `Response` で終わる、RPCの戻り値としてのみ動作するメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして記述**すべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在しなければならず（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、次の*いずれか*の場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでそのフィールドに値を**提供しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在しない場合に限り、そのフィールドを**省略してもよい**（may）（フィールドに変更がないことを示す）。そうでない場合は値が**提供されなければならない**（must）。
- リクエストメッセージ（通常 `Request` で終わる名前の、RPCの引数であるメッセージ）上のフィールドである。この場合、リクエストの一部として値が**提供されなければならず**（must）、提供されない場合はエラー（通常 `INVALID_ARGUMENT`）を**引き起こさなければならない**（must）。

上記で「truthy」という用語を次のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false` 以外の値
- 繰り返しフィールドやマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

以下のことを示すためにフィールドをrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きでrequiredとなるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enumの未指定値など）は未設定値と区別できないため、requiredフィールドをfalsyな値に設定するとエラーが発生する。このことから、requiredブール値は `true` に設定しなければならないという帰結が導かれる。

### Unordered List

リソースの繰り返しフィールドに対する `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合、またはサービスがユーザーの代わりにリストをソートする状況を含めて、順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、安定した順序でリストを返し**てもよく**（may）、ランダム化された不安定な順序でリストを返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味的変更を表す可能性がある。以下は `google.api.field_behavior` に関する後方互換性のない変更の例である：

* 既存の（暗黙的または明示的に）`OPTIONAL` とみなされていたフィールドへの `REQUIRED` の追加
* 既存のリクエストメッセージへの `REQUIRED` アノテーション付きの新しいフィールドの追加
* 以前入力として受け付けられていた既存フィールドへの `OUTPUT_ONLY` の追加
* 以前出力として出力されていた既存フィールドへの `INPUT_ONLY` の追加
* 以前mutableとみなされていた既存フィールドへの `IMMUTABLE` の追加
* 以前入力として無視されていた既存フィールドからの `OUTPUT_ONLY` の削除
* 既存フィールドからの `IDENTIFIER` の削除。

後方互換性の*ある*変更もあり、以下がそれに該当する：

* 既存フィールドへの `OPTIONAL` の追加
* 既存の `name` フィールドへの `IDENTIFIER` の追加
* 既存フィールドの `REQUIRED` から `OPTIONAL` への変更
* 既存フィールドの `OUTPUT_ONLY` や `IMMUTABLE` から `IDENTIFIER` への変更
* 既存フィールドからの `REQUIRED` の削除
* 以前レスポンスから除外されていた既存フィールドからの `INPUT_ONLY` の削除
* 以前immutableとみなされていた既存フィールドからの `IMMUTABLE` の削除

## 根拠

### Identifierフィールド動作

リソース名は、あらゆる準拠リソースの主要な識別子であり、作成時にユーザーが完全に構成することは決してない。このようなフィールドは通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードであるシナリオでは主要な識別子としても消費される。このようなフィールドは `OUTPUT_ONLY` とは*みなせない*。さらに、標準Updateのような変更リクエストでは、主要な識別子としてのリソース名をその場で変更することはできない。このようなフィールドは通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの矛盾するコンテキスト依存のフィールド動作により、リソース名フィールドの動作を選別して伝える新しい値が必要となった。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドはrequiredまたはoptionalのいずれかであり、したがって少なくともそれぞれ `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### field_behaviorの必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須にすることで、API作成者はAPIの初期作成時に動作を明示的に検討せざるを得なくなる。

初期作成後にフィールド動作を変更すると、クライアントで後方互換性のない変更が生じる可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]におけるリソースに後方互換性のない変更が生じる。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須化された。この変更以前は、アノテーションがしばしば省略されていた。その値は高品質なクライアントを作成するために依存されている。さらに、メジャーバージョン内で事後に一部のfield_behavior値を追加または変更することは後方互換性を損なう可能性がある。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

API作成時にfield_behaviorを必須化することの利点は、それをしないことのクライアントやAPI利用者へのコストを上回る。
