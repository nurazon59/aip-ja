# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作の特定の側面（requiredかoptionalかなど）をユーザーに説明するのが慣例である。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリの署名を最適化するため）。

## ガイダンス

APIは、フィールドがrequiredかimmutableであるかなど、十分に理解されているフィールド動作を記述するために `google.api.field_behavior` アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - このルールの例外として、リソースメッセージ上のAIP-154の `etag` フィールドがあり、これにはいかなる `google.api.field_behavior` も割り当てる**べきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、その場合は特定の動作をコメントにドキュメント化**すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する任意の [google.api.FieldBehavior][] の値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` は使用**してはならない**（must not）。
- APIは最低限 `REQUIRED`、`OPTIONAL`、または `OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作には影響しないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的にレビューし、検討すること。

アノテーションのないフィールドは、後方互換性のため `OPTIONAL` として解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで示されるボキャブラリーは _記述_ 目的のみであり、それ自体がバリデーションを追加するものではない。目的は、クライアントに対してこの動作を一貫してドキュメント化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージのフィールド動作が `REQUIRED` であり、親フィールドが `OPTIONAL` であることが可能である:

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記のケースでは、`title` が指定された場合、`text` フィールドは必須である。

## ボキャブラリー

### 識別子

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは `name` フィールドに付与**しなければならない**（must）し、他のフィールドには付与**してはならない**（must not）（[fields representing resource names]を参照）。

`IDENTIFIER` の値は、createメソッドのコンテキストではそのフィールドが入力として受け入れられない（すなわち `OUTPUT_ONLY`）一方で、`IMMUTABLE` とみなされ、リソースを主入力として受け取る変更メソッド（例: [標準Update][aip-134]）では入力として受け入れられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照には適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、そのフィールドがアップデートマスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーを返す**べきである**（should）。

immutableフィールドの可能性のあるユースケース（これは網羅的なリストではない）:

- アプリケーションの存続期間中変更できないリソースの属性（例: ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドには、immutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールドであるか、リソースメッセージに含まれるメッセージのフィールドである場合に限り、Input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（常にRPCの引数としてのみ機能し、名前が通常 `Request` で終わるメッセージ）内のフィールドは、Input onlyとして記述**すべきではない**（should not）。なぜなら、それは既に暗黙的に示されているからである。

Input onlyフィールドの可能性のあるユースケース（これは網羅的なリストではない）:

- AIP-214で説明されている `ttl` フィールド。

**警告:** Input onlyフィールドは稀であり、使用前に慎重に検討する必要がある。

### Optional

`OPTIONAL` の使用は、フィールドが必須ではないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常 `Request` で終わるメッセージ）上のフィールドであるか、サブメッセージ上のフィールドである場合、Optionalとして記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も起こらない（サーバーはこのフィールドの値をすべてクリア**しなければならない**（must）し、入力時にこのフィールドの値が存在することによるエラーをスロー**してはならない**（must not））ことを示す。同様に、サービスはアップデートのフィールドマスクにおけるOutput onlyフィールドの存在を無視**しなければならない**（must）（参照: AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールドであるか、ツリーの下位のメッセージのフィールドである場合に限り、Output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（常にRPCの戻り値としてのみ機能し、名前が通常 `Response` で終わるメッセージ）内のフィールドは、Output onlyとして記述**すべきではない**（should not）。なぜなら、それは既に暗黙的に示されているからである。

Output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

Output onlyフィールドの可能性のあるユースケース（これは網羅的なリストではない）:

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生または構造化された情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在**しなければならない**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の _いずれか_ の場合に限り、requiredとして記述**すべきである**（should）:

- ユーザーが入力としてどこかで提供するリソース上のフィールドである場合。この場合、リソースは "truthy" な値が _格納されている_ 場合にのみ有効である。
  - リソースを[作成する][aip-133]場合、createリクエストのフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新する][aip-134]場合、そのフィールドがフィールドマスクにも含まれていない（フィールドに変更がないことを示す）場合に限り、ユーザーはそのフィールドを省略**してもよい**（may）（それ以外の場合は提供**しなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、通常 `Request` で終わる名前を持つメッセージ）上のフィールドである場合。この場合、値はリクエストの一部として提供**しなければならない**（must）し、提供しない場合はエラー（通常は `INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の "truthy" という用語を以下のように定義する:

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false` 以外の値
- 繰り返しフィールドとマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの "truthy" なフィールドを持つメッセージ

以下を示すために、フィールドをrequiredとして記述**すべきではない**（should not）:

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として決して使用されない、任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enumの未指定の値など）は未設定の値と区別がつかないため、requiredフィールドにfalsyな値を設定するとエラーになる。この帰結として、requiredなブール値は `true` に設定しなければならない。

### 順序なしリスト

リソースの繰り返しフィールドにおける `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` の値の追加や変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味的な変更を表す可能性がある。以下は `google.api.field_behavior` に関する後方互換性のない変更の例である:

* 以前 `OPTIONAL` とみなされていた（暗黙的または明示的に）既存のフィールドに `REQUIRED` を追加すること
* 既存のリクエストメッセージに `REQUIRED` としてアノテーションされた新しいフィールドを追加すること
* 以前入力として受け入れられていた既存のフィールドに `OUTPUT_ONLY` を追加すること
* 以前出力として送信されていた既存のフィールドに `INPUT_ONLY` を追加すること
* 以前可変とみなされていた既存のフィールドに `IMMUTABLE` を追加すること
* 以前入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除すること
* 既存のフィールドから `IDENTIFIER` を削除すること

後方互換性が*ある*変更もいくつかあり、以下の通りである:

* 既存のフィールドに `OPTIONAL` を追加すること
* 既存の `name` フィールドに `IDENTIFIER` を追加すること
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更すること
* 既存のフィールドで `OUTPUT_ONLY` または `IMMUTABLE`（あるいはその両方）から `IDENTIFIER` に変更すること
* 既存のフィールドから `REQUIRED` を削除すること
* 以前レスポンスで除外されていた既存のフィールドから `INPUT_ONLY` を削除すること
* 以前immutableとみなされていた既存のフィールドから `IMMUTABLE` を削除すること

## 根拠

### Identifierフィールド動作

リソース名（準拠するリソースの主識別子）は、create時にユーザーによって完全に構築されることはない。そのようなフィールドは通常 `OUTPUT_ONLY` のフィールド動作が割り当てられる。しかし、リソース自体が主たるリクエストペイロードであるシナリオでは、主識別子としても頻繁に使用される。そのようなフィールドは `OUTPUT_ONLY` とみなすことが*できなかった*。さらに、標準Updateのような変更リクエストでは、主識別子としてのリソース名をその場で変更することはできない。そのようなフィールドは通常 `IMMUTABLE` のフィールド動作が割り当てられる。これらの相反しコンテキスト依存するフィールド動作は、リソース名フィールドの動作を特定して伝達するために新しい値が必要であることを意味した。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須またはオプションであり、したがってそれぞれ少なくとも `REQUIRED` または `OPTIONAL` のアノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須とすることで、API作成者はAPIの初期作成時に動作を明示的に検討せざるを得なくなる。

初期作成後にフィールド動作を変更すると、クライアントにおいて後方互換性のない変更が生じる可能性がある。例えば、オプションフィールドを必須にすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023年5月に field_behavior が必須化された。この変更以前は、アノテーションはしばしば省略されていた。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で後から field_behavior の値を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

API作成時に field_behavior を必須化することのメリットは、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
