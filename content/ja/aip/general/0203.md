# フィールド動作のドキュメント化

プロトコルバッファでフィールドを定義する際、ユーザーに対してフィールドの動作の特定の側面（requiredかoptionalかなど）を説明することが慣例となっている。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリシグネチャの最適化のため）。

## ガイダンス

APIは、フィールドがrequiredかimmutableかなど、よく理解されたフィールド動作を記述するために `google.api.field_behavior` アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外は、リソースメッセージ上のAIP-154の `etag` フィールドであり、これにはいかなる `google.api.field_behavior` も割り当てる**べきではない**（should not）。
- アノテーションには、フィールドの動作を正確に記述する [google.api.FieldBehavior][] 値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- APIは最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作には影響しないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれを利用している。新しいフィールドを追加する際には、どの値が関連するかを十分に確認し検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` として解釈される。それでも、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで示される語彙は _記述的_ な目的のみのものであり、それ自体でバリデーションを追加するものではない。目的は、クライアントに対してこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージが `REQUIRED` のフィールド動作を持ち、親フィールドが `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されていれば、`text` フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER` の値は、フィールドが作成メソッドのコンテキストでは入力として受け付けられず（すなわち `OUTPUT_ONLY`）、同時に `IMMUTABLE` と見なされ、リソースを主入力として受け取る変更メソッド（例：[標準Update][aip-134]）では入力として受け入れられることを伝達する。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドがその作成後に変更できないことを示す。これは、入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラー**にすべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- アプリケーションの存続期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドには、immutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常 `Request` で終わる名前を持つメッセージ）内のフィールドは、これが既に暗黙的に示されているため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- AIP-214で説明されている `ttl` フィールド。

**警告:** input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常 `Request` で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合に、optionalとして記述し**てもよい**（may）。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにそのフィールドを含めても何も起こらないことを示す（サーバーはこのフィールド内のすべての値をクリア**しなければならず**（must）、入力時にこのフィールドに値が存在することによるエラーをスロー**してはならない**（must not））。同様に、サービスは更新フィールドマスクにoutput onlyフィールドが含まれることを無視**しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーの下方にあるメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常 `Response` で終わるメッセージ）内のフィールドは、これが既に暗黙的に示されているため、output onlyとして記述**すべきではない**（should not）。

output onlyフィールドは、APIにとって適切であれば空の値に設定し**てもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在しなければならない（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の _いずれか_ の場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーがどこかで入力として提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が _保存されている_ 場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエスト上のフィールドに値が提供され**なければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドを省略し**てもよい**（may）。ただし、そのフィールドがフィールドマスクからも省略されており、フィールドに変更がないことを示している場合に限る（そうでない場合は提供**されなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、通常 `Request` で終わる名前を持つメッセージ）上のフィールドである。この場合、リクエストの一部として値が提供**されなければならず**（must）、そうしない場合はエラー（通常は `INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/バイト、`false` 以外の値
- repeatedフィールドとマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

以下のことを示すためにフィールドをrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きでrequiredとなるフィールド。
- ユーザー入力として使用されることのない、任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enumの未指定値など）は未設定の値と区別できないため、requiredフィールドにfalsyな値を設定するとエラーが発生する。これの帰結として、requiredのブール値は `true` に設定しなければならない。

### Unordered List

リソースのrepeatedフィールドでの `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、unordered listとして記述**すべきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントに対して非互換として認識される意味上の変更を表す可能性がある。以下は `google.api.field_behavior` における後方互換性のない変更の例である：

* 以前に（暗黙的またはその他の方法で）`OPTIONAL` と見なされていた既存のフィールドに `REQUIRED` を追加する
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加する
* 以前に入力として受け入れられていた既存のフィールドに `OUTPUT_ONLY` を追加する
* 以前に出力として出力されていた既存のフィールドに `INPUT_ONLY` を追加する
* 以前に変更可能と見なされていた既存のフィールドに `IMMUTABLE` を追加する
* 以前に入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除する
* 既存のフィールドから `IDENTIFIER` を削除する

後方互換性が _ある_ 変更もあり、それは以下の通り：

* 既存のフィールドに `OPTIONAL` を追加する
* 既存の `name` フィールドに `IDENTIFIER` を追加する
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更する
* 既存のフィールドで `OUTPUT_ONLY` および/または `IMMUTABLE` から `IDENTIFIER` に変更する
* 既存のフィールドから `REQUIRED` を削除する
* 以前にレスポンスで除外されていた既存のフィールドから `INPUT_ONLY` を削除する
* 以前にimmutableと見なされていた既存のフィールドから `IMMUTABLE` を削除する

## 根拠

### Identifierフィールド動作

リソース名は、あらゆる準拠リソースの主識別子であり、作成時にユーザーによって完全に構築されることはない。このようなフィールドには通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、これらはリソース自体が主リクエストペイロードとなるシナリオでも主識別子として消費されることが多い。このようなフィールドは `OUTPUT_ONLY` とは見なせ _ない_。さらに、標準Updateのような変更リクエストでは、主識別子としてのリソース名はその場で変更できない。このようなフィールドには通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの相反する文脈依存のフィールド動作は、リソース名フィールドの動作を選び出して伝達するために新しい値が必要であることを意味した。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドはrequiredまたはoptionalのいずれかであり、したがって少なくともそれぞれ `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションの必須化はまた、API作成者がAPIの初期作成時に動作を明示的に考慮することを強制する。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更が生じる可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須になった。この変更以前は、アノテーションはしばしば省略されていた。その値は高品質なクライアントを生成するために利用されている。さらに、事後にメジャーバージョン内で一部のfield_behavior値を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを要求することの利点は、そうしないことによるクライアントとAPIユーザーへのコストを上回る。
