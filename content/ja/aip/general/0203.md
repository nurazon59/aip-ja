# フィールド動作の文書化

Protocol Buffersでフィールドを定義する際、フィールドの動作の特定の側面（必須かオプショナルかなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解することも有用である（例えば、クライアントライブラリのシグネチャを最適化するためなど）。

## ガイダンス

APIは、フィールドが必須かimmutableかなど、よく理解されたフィールド動作を記述するために`google.api.field_behavior`アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の`etag`フィールドがあり、これには`google.api.field_behavior`を割り当て**るべきではない**（should not）。
  - さらに、`oneof`フィールドは`google.api.field_behavior`を省略**してもよい**（may）が、この場合コメント内で特定の動作を文書化**すべきである**（should）。
- アノテーションは、フィールドの動作を正確に記述する任意の[google.api.FieldBehavior][]値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは最低限`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作には影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存している。新しいフィールドを追加する際には、どの値が適切かをよく確認し検討すること。

アノテーションのないフィールドは、後方互換性のため`OPTIONAL`と解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は*記述的*な目的のみのものであり、それ自体でバリデーションを追加するものではない。目的はこの動作をクライアント向けに一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の`google.api.field_behavior`アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージのフィールド動作が`REQUIRED`であり、親フィールドが`OPTIONAL`である場合がある：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されていれば、`text`フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは`name`フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、作成メソッドのコンテキストではフィールドが入力として受け付けられない（すなわち`OUTPUT_ONLY`）ことを伝え、同時にリソースを主入力として受け付ける変更メソッド（例：[標準Update][aip-134]）では`IMMUTABLE`とみなされ入力として受け付けられる。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はフィールドを無視**すべきである**（should）が、変更が要求された場合は`INVALID_ARGUMENT`でエラーに**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- アプリケーションの存続期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドはimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常`Request`で終わる名前を持つメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- AIP-214で説明されている`ttl`フィールド。

**警告:** input onlyフィールドはまれであり、使用前に慎重に検討**すべきである**（should）。

### Optional

`OPTIONAL`の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数となるメッセージで、通常`Request`で終わる名前を持つ）上のフィールド、またはサブメッセージ上のフィールドである場合にoptionalとして記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル`optional`とフィールド動作`OPTIONAL`は相互排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も行われないことを示す（サーバーはこのフィールドの値をクリア**しなければならず**（must）、入力にこのフィールドの値が存在することによるエラーをスロー**してはならない**（must not））。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（AIP-161参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーの下位のメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常`Response`で終わる名前を持つメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして記述**すべきではない**（should not）。

output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）（かつ空でない値に設定され**なければならない**（must））ことを示す。

フィールドは、_以下のいずれか_の場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでフィールドの値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、フィールドがフィールドマスクにも存在しない場合はフィールドを省略**してもよい**（may）（フィールドに変更がないことを示す）。そうでない場合は提供**しなければならない**（must）。
- リクエストメッセージ（RPCの引数となるメッセージで、通常`Request`で終わる名前を持つ）上のフィールドである。この場合、リクエストの一部として値を提供**しなければならず**（must）、提供しない場合はエラー（通常`INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

「truthy」という用語を上記で以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/バイト、`false`以外の値
- 繰り返しフィールドやマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

以下のことを示すためにフィールドをrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定値と区別できないため、requiredフィールドにfalsyな値を設定するとエラーになる。この帰結として、requiredなブール値は`true`に設定**しなければならない**（must）。

### 順序なしリスト

リソースの繰り返しフィールドに`UNORDERED_LIST`を使用することは、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、安定した順序でリストを返し**てもよい**（may）し、ランダム化された不安定な順序でリストを返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`の値の追加や変更は、既存のクライアントにとって非互換と認識されるAPIの意味上の変更を表す可能性がある。以下は、`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前`OPTIONAL`（暗黙的またはそれ以外）と見なされていた既存フィールドへの`REQUIRED`の追加
* 既存のリクエストメッセージへの`REQUIRED`とアノテーションされた新しいフィールドの追加
* 以前入力として受け付けられていた既存フィールドへの`OUTPUT_ONLY`の追加
* 以前出力として出力されていた既存フィールドへの`INPUT_ONLY`の追加
* 以前可変と見なされていた既存フィールドへの`IMMUTABLE`の追加
* 以前入力として無視されていた既存フィールドからの`OUTPUT_ONLY`の削除
* 既存フィールドからの`IDENTIFIER`の削除

*後方互換性がある*変更もあり、以下の通りである：

* 既存フィールドへの`OPTIONAL`の追加
* 既存の`name`フィールドへの`IDENTIFIER`の追加
* 既存フィールドの`REQUIRED`から`OPTIONAL`への変更
* 既存フィールドの`OUTPUT_ONLY`および/または`IMMUTABLE`から`IDENTIFIER`への変更
* 既存フィールドからの`REQUIRED`の削除
* 以前レスポンスで除外されていた既存フィールドからの`INPUT_ONLY`の削除
* 以前immutableと見なされていた既存フィールドからの`IMMUTABLE`の削除

## 根拠

### Identifierフィールド動作

リソース名は、準拠するすべてのリソースの主識別子であり、作成時にユーザーが完全に構築することはない。このようなフィールドは通常`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、リソース自体が主リクエストペイロードとなるシナリオでは、主識別子として利用されることも多い。このようなフィールドは`OUTPUT_ONLY`とは見なせ*なかった*。さらに、標準Updateのような変更リクエストでは、主識別子としてのリソース名をその場で変更することはできない。このようなフィールドには通常`IMMUTABLE`フィールド動作が割り当てられる。これらの相反するコンテキスト依存のフィールド動作により、リソース名フィールドの動作を特定し伝達するために新しい値が必要となった。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力か出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドは必須かオプショナルのいずれかであり、したがってそれぞれ少なくとも`REQUIRED`または`OPTIONAL`アノテーションを持つ**べきである**（should）。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラム的なクライアントとユーザーの理解を向上させる。

アノテーションを必須化することで、API作成者はAPIの初期作成時に動作を明示的に検討することも強制される。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更をもたらす可能性がある。例えば、オプショナルフィールドを必須にすると、[宣言的クライアント][Declarative client]におけるRPCのメソッドシグネチャやリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023-05にfield_behaviorが必須となった。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後にfield_behaviorの値を追加または変更することは、後方互換性がない場合がある。より詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。
