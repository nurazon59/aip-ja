# フィールド動作のドキュメント化

プロトコルバッファでフィールドを定義する際、フィールドの動作の特定の側面（必須かオプショナルかなど）をユーザーに説明することが通例である。さらに、他のツールがこの動作を理解できることは有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは `google.api.field_behavior` アノテーションを使用して、フィールドが必須かimmutableかなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージのすべてのフィールドに `google.api.field_behavior` アノテーションを**適用しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の `etag` フィールドは、`google.api.field_behavior` を**割り当てられるべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を**省略してもよい**（may）が、この場合、コメント内で特定の動作を**文書化すべきである**（should）。
- アノテーションには、フィールドの動作を正確に説明する任意の [google.api.FieldBehavior][] 値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を**使用してはならない**（must not）。
- APIは最低でも `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを**使用しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作には影響しないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的に確認し検討すること。

アノテーションのないフィールドは、後方互換性のため `OPTIONAL` と解釈される。それにもかかわらず、このアノテーションを**省略してはならない**（must not）。

**注:** このドキュメントで示されている語彙は*説明*目的のみであり、それ自体は検証を追加するものではない。目的は、クライアントに対してこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージは `REQUIRED` のフィールド動作を持ち、親フィールドは `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されていれば、`text` フィールドは必須である。

## 語彙

### 識別子

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに**付与しなければならず**（must）、他のフィールドに**付与してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER` 値は、作成メソッドのコンテキストではフィールドが入力として受け入れられない（つまり `OUTPUT_ONLY`）ことを伝えつつ、リソースを主入力として受け入れる変更メソッド（例：[標準Update][aip-134]）では `IMMUTABLE` と見なされ、入力として受け入れられることも伝える。

このアノテーションは、メッセージ内の他のリソースへの参照には**適用してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、必須またはオプショナルのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受信した場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを**無視すべきであり**（should）、変更が要求された場合は `INVALID_ARGUMENT` で**エラーとすべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下のとおりである：

- アプリケーションの存続期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件的にimmutable」なフィールドには、immutableアノテーションを**付与してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして**記述されるべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常は名前が `Request` で終わるメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして**記述されるべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下のとおりである：

- AIP-214で説明されている `ttl` フィールド。

**警告:** Input onlyフィールドは稀であり、使用前に慎重に検討されるべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常は名前が `Request` で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして**記述してもよい**（may）。

**注:** フィールド存在ラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにそのフィールドを含めても何も行われない（サーバーはこのフィールド内のすべての値を**クリアしなければならず**（must）、入力時にこのフィールドに値が存在することによるエラーを**発生させてはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を**無視しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーの下位のメッセージのフィールドである場合にのみ、output onlyとして**記述されるべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常は名前が `Response` で終わるメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして**記述されるべきではない**（should not）。

Output onlyフィールドは、APIにとって適切な場合、空の値に**設定してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下のとおりである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に**存在しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして**記述されるべきである**（should）：

- ユーザーがどこかで入力として提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエスト上でそのフィールドに値を**提供しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在しない（フィールドへの変更がないことを示す）場合に限り、フィールドを**省略してもよい**（may）（そうでない場合は**提供しなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、通常は名前が `Request` で終わるメッセージ）上のフィールドである。この場合、リクエストの一部として値を**提供しなければならず**（must）、提供しない場合はエラー（通常は `INVALID_ARGUMENT`）を**発生させなければならない**（must）。

上記の「truthy」という用語を次のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false` 以外の値
- 繰り返しフィールドおよびマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つメッセージ

以下のことを示すためにフィールドをrequiredとして**記述すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enumの未指定値など）は未設定値と区別できないため、requiredフィールドをfalsyな値に設定するとエラーが発生する。これの当然の帰結として、requiredなブール値は `true` に**設定しなければならない**（must）。

### 順序なしリスト

リソースの繰り返しフィールドに `UNORDERED_LIST` を使用することは、サービスがリスト内の項目の順序を保証しないことを示す。

サービスが、リスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、フィールドは順序なしリストとして**記述されるべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で**返してもよい**（may）し、ランダム化された不安定な順序で**返してもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントにとって非互換と認識されるAPIの意味的な変更を表す可能性がある。以下は、`google.api.field_behavior` に関する後方非互換な変更の例である：

* 以前は `OPTIONAL`（暗黙的またはその他）と見なされていた既存のフィールドに `REQUIRED` を追加する
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加する
* 以前は入力として受け入れられていた既存のフィールドに `OUTPUT_ONLY` を追加する
* 以前は出力として発行されていた既存のフィールドに `INPUT_ONLY` を追加する
* 以前は可変と見なされていた既存のフィールドに `IMMUTABLE` を追加する
* 以前は入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除する
* 既存のフィールドから `IDENTIFIER` を削除する

後方互換性が*ある*変更もあり、それは以下のとおりである：

* 既存のフィールドに `OPTIONAL` を追加する
* 既存の `name` フィールドに `IDENTIFIER` を追加する
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更する
* 既存のフィールドで `OUTPUT_ONLY` かつ/または `IMMUTABLE` から `IDENTIFIER` に変更する
* 既存のフィールドから `REQUIRED` を削除する
* 以前はレスポンスで除外されていた既存のフィールドから `INPUT_ONLY` を削除する
* 以前はimmutableと見なされていた既存のフィールドから `IMMUTABLE` を削除する

## 根拠

### 識別子フィールド動作

リソース名（あらゆる準拠リソースの主要識別子）は、作成時にユーザーによって完全に構築されることはない。そのようなフィールドは通常、`OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードであるシナリオでは、主要識別子としても消費される。そのようなフィールドは `OUTPUT_ONLY` と*見なすことはできない*。さらに、標準Updateのような変更リクエストでは、主要識別子としてのリソース名はその場で変更できない。そのようなフィールドは通常、`IMMUTABLE` フィールド動作が割り当てられる。これらの相反するコンテキスト依存のフィールド動作により、リソース名フィールドの動作を特定して伝えるために新しい値が必要であった。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須またはオプショナルのいずれかであり、したがってそれぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを**持つべきである**（should）。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の要求

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラム的なクライアントとユーザーの理解を向上させる。

アノテーションを要求することは、API作成者がAPIの最初の作成時に動作を明示的に検討することも強制する。

最初の作成後にフィールド動作を変更すると、クライアントに後方非互換な変更をもたらす可能性がある。例えば、オプショナルフィールドを必須にすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方非互換な変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後にfield_behaviorの値の一部を追加または変更すると、後方非互換になる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを要求することの利点は、そうしない場合のクライアントおよびAPIユーザーへのコストを上回る。
