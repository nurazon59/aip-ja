# フィールド動作のドキュメント化

Protocol Buffers でフィールドを定義する際、フィールドの動作に関する特定の側面（必須か任意かなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリのシグネチャを最適化するためなど）。

## ガイダンス

API は `google.api.field_behavior` アノテーションを使用して、フィールドが必須または immutable であることなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- API は、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上の AIP-154 の `etag` フィールドには `google.api.field_behavior` を割り当て**るべきではない**（should not）。
  - さらに、`oneof` フィールドでは `google.api.field_behavior` を省略**してもよい**（may）が、この場合、特定の動作をコメントに文書化**すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述するすべての [google.api.FieldBehavior][] 値**を含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- API は最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` は proto レベルの動作に影響を与えないが、多くのクライアント（CLI や SDK など）はこれらに依存してコードを生成する。新しいフィールドを追加する際は、どの値が適切かを徹底的に確認し検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` として解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで示される語彙は*説明的*な目的のためのみに使用され、それ自体がバリデーションを追加するものではない。目的は、クライアント向けにこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージのフィールド動作が `REQUIRED` であり、親フィールドが `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されていれば、`text` フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names] を参照）。

`IDENTIFIER` 値は、作成メソッドの文脈ではそのフィールドが入力として受け付けられない（すなわち `OUTPUT_ONLY`）ことを示すが、同時に `IMMUTABLE` とみなされ、リソースを主要な入力として受け付ける変更メソッド（例：[標準 Update][aip-134]）では入力として受け付けられる。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、必須または任意のいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）で immutable フィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーに**すべきである**（should）。

immutable フィールドの潜在的なユースケース（これは網羅的なリストではない）：

- アプリケーションのライフタイムの間変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件的に immutable」なフィールドには、immutable アノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドが input only として記述されるのは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合に限定**すべきである**（should）。特に、リクエストメッセージ（RPC の引数としてのみ機能し、通常 `Request` で終わる名前を持つメッセージ）内のフィールドは、これがすでに暗黙的であるため、input only として記述**すべきではない**（should not）。

input only フィールドの潜在的なユースケース（これは網羅的なリストではない）：

- AIP-214 で説明されている `ttl` フィールド。

**警告:** input only フィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須ではないことを示す。

フィールドがリクエストメッセージ（RPC の引数であり、通常 `Request` で終わる名前を持つメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optional として記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細は AIP-149 を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにそのフィールドを含めても何も起こらないことを示す（サーバーはこのフィールドのすべての値をクリア**しなければならず**（must）、入力時にこのフィールドに値が存在することを理由にエラーを送出**してはならない**（must not））。同様に、サービスは更新フィールドマスク内の output only フィールドの存在を無視**しなければならない**（must）（AIP-161 を参照）。

さらに、フィールドが output only として記述されるのは、リソースメッセージ内のフィールド、またはツリーのさらに下位のメッセージのフィールドである場合に限定**すべきである**（should）。特に、レスポンスメッセージ（RPC の戻り値としてのみ機能し、通常 `Response` で終わる名前を持つメッセージ）内のフィールドは、これがすでに暗黙的であるため、output only として記述**すべきではない**（should not）。

output only フィールドは、API にとって適切であれば空の値に設定**してもよい**（may）。

output only フィールドの潜在的なユースケース（これは網羅的なリストではない）：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）、（かつ空でない値に設定されなければならない）ことを示す。

フィールドが required として記述されるのは、以下の*いずれか*の場合に限定**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「真と評価される（truthy）」値が*格納されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエスト上のフィールドに値が提供**されなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドマスクにもそのフィールドが存在せず、フィールドに変更がないことを示している場合に限り、そのフィールドを省略**してもよい**（may）（そうでない場合、値が提供**されなければならない**（must））。
- リクエストメッセージ（RPC の引数であり、通常 `Request` で終わる名前を持つメッセージ）上のフィールドである。この場合、値はリクエストの一部として提供**されなければならず**（must）、提供されなかった場合はエラー（通常 `INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「真と評価される（truthy）」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/バイト列、`false` 以外の値
- 繰り返しフィールドおよびマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「真と評価される（truthy）」フィールドを持つすべてのメッセージ

以下のことを示すために、フィールドを required として記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件的に必須となるフィールド。
- ユーザー入力として決して使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enum の未指定値など）は未設定の値と区別できないため、required フィールドを偽と評価される値に設定するとエラーになる。この帰結として、required なブール値は `true` に設定されなければならない。

### Unordered List

リソースの繰り返しフィールドにおける `UNORDERED_LIST` の使用は、サービスがリスト内のアイテムの順序を保証しないことを示す。

サービスがユーザーに代わってリストをソートする状況を含め、リスト内の要素の順序がユーザーの送信した順序と一致することをサービスが保証しない場合、フィールドは unordered list として記述**すべきである**（should）。

unordered list を持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントにとって互換性がないと認識される API の意味的な変更を表す可能性がある。以下は `google.api.field_behavior` における後方互換性のない変更の例である：

* 以前 `OPTIONAL`（暗黙的または明示的）とみなされていた既存のフィールドに `REQUIRED` を追加する
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加する
* 以前入力として受け付けられていた既存のフィールドに `OUTPUT_ONLY` を追加する
* 以前出力として送出されていた既存のフィールドに `INPUT_ONLY` を追加する
* 以前 mutable とみなされていた既存のフィールドに `IMMUTABLE` を追加する
* 以前入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除する
* 既存のフィールドから `IDENTIFIER` を削除する

後方互換性の*ある*変更もいくつかあり、以下のとおりである：

* 既存のフィールドに `OPTIONAL` を追加する
* 既存の `name` フィールドに `IDENTIFIER` を追加する
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更する
* 既存のフィールドで `OUTPUT_ONLY` または `IMMUTABLE`、あるいはその両方から `IDENTIFIER` に変更する
* 既存のフィールドから `REQUIRED` を削除する
* 以前レスポンスから除外されていた既存のフィールドから `INPUT_ONLY` を削除する
* 以前 immutable とみなされていた既存のフィールドから `IMMUTABLE` を削除する

## 理論的根拠

### Identifier フィールド動作

リソース名（準拠するすべてのリソースの主要な識別子）は、作成時にユーザーが完全に構成することは決してない。そのようなフィールドは通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードであるシナリオでは、主要な識別子として頻繁に使用される。そのようなフィールドは `OUTPUT_ONLY` とはみなされ*ない*。さらに、標準 Update のような変更リクエストでは、主要な識別子としてのリソース名はその場で変更できない。そのようなフィールドは通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの矛盾したコンテキスト依存のフィールド動作のため、リソース名フィールドの動作を特定して伝える新しい値が必要となった。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須または任意のいずれかであり、したがってそれぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもそのフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションの必須化はまた、API 作成者が API の初期作成時に動作を明示的に検討することを強制する。

初期作成後にフィールド動作を変更すると、クライアントにおける後方互換性のない変更につながる可能性がある。例えば、任意フィールドを必須にすると、RPC のメソッドシグネチャや[宣言的クライアント][Declarative client]におけるリソースに後方互換性のない変更が発生する。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023-05 に field_behavior が必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために信頼されている。さらに、メジャーバージョン内で事後に field_behavior の値の一部を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

API 作成時に field_behavior を必須化することの利点は、必須化しない場合にクライアントと API ユーザーが被るコストを上回る。
