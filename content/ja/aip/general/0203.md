# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作の特定の側面（必須かオプショナルかなど）をユーザーに説明するのが通例である。さらに、他のツールがこの動作を理解できることは有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは `google.api.field_behavior` アノテーションを使用して、フィールドが必須やimmutableであるなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージのすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - これに対する例外は、リソースメッセージ上のAIP-154の `etag` フィールドであり、これは `google.api.field_behavior` を一切割り当て**るべきではない**（should not）。
- アノテーションには、フィールドの動作を正確に記述する [google.api.FieldBehavior][] の値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- APIは最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作に影響を与えないが、多くのクライアント（例：CLIやSDK）はコード生成のためにこれに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的にレビューし検討すること。

アノテーションのないフィールドは後方互換性のため `OPTIONAL` と解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで与えられる語彙は*記述的*な目的のためのみであり、それ自体はバリデーションを追加しない。目的は、この動作をクライアント向けに一貫して文書化することである。

### ネストされたメッセージのfield behavior

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、親フィールドが `OPTIONAL` であっても、ネストされたメッセージは `REQUIRED` のfield behaviorを持つことができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されていれば、`text` フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに付与**しなければならず**（must）、他のいかなるフィールドにも付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER` の値は、作成メソッドのコンテキストではフィールドが入力として受け付けられない（すなわち `OUTPUT_ONLY`）ことを伝えつつ、同時に `IMMUTABLE` と見なされ、リソースを主たる入力として受け付ける変更メソッド（例：[標準Update][aip-134]）では入力として受け付けられる。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーに**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- アプリケーションの有効期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにはimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールドか、リソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常 `Request` で終わる名前を持つメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- AIP-214で説明されている `ttl` フィールド。

**警告:** Input onlyフィールドはまれであり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であるメッセージで、通常 `Request` で終わる）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も起こらないことを示す（サーバーはこのフィールドの値をクリア**しなければならず**（must）、入力時にこのフィールドに値が存在する結果としてエラーを投げ**てはならない**（must not））。同様に、サービスは更新フィールドマスクにoutput onlyフィールドが存在することを無視**しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールドか、ツリーの下位にあるメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常 `Response` で終わるメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして記述**すべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば空の値に設定され**てもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- 変更できない、サービスによって割り当てられるリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*に該当する場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエスト上でそのフィールドに値が**提供されなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在しない場合はそのフィールドを**省略してもよく**（may）（それ以外の場合は**提供されなければならない**（must））、これはフィールドに変更がないことを示す。
- リクエストメッセージ（RPCの引数であるメッセージで、通常 `Request` で終わる名前を持つ）上のフィールドである。この場合、値がリクエストの一部として**提供されなければならず**（must）、そうしない場合はエラー（通常は `INVALID_ARGUMENT`）を**発生させなければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/バイト、`false` 以外の値
- 繰り返しフィールドとマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

フィールドは以下のことを示すためにrequiredとして記述**すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として決して使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（booleanの `false`、整数の `0`、enumの未指定値など）は未設定値と区別がつかないため、requiredフィールドをfalsyな値に設定するとエラーになる。これの当然の帰結として、requiredなbooleanは `true` に設定されなければならない。

### Unordered List

リソースの繰り返しフィールドに `UNORDERED_LIST` を使用することは、サービスがリスト内の項目の順序を保証しないことを示す。

サービスが、ユーザーが送信した順序と要素の順序が一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、フィールドは順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、安定した順序でリストを返し**てもよく**（may）、ランダム化された不安定な順序でリストを返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` の値の追加や変更は、既存のクライアントにとって非互換と認識されるAPIの意味上の変更を表す可能性がある。以下は `google.api.field_behavior` に関する後方互換性のない変更の例である：

* 以前に（暗黙的またはそれ以外で）`OPTIONAL` と見なされていた既存のフィールドへの `REQUIRED` の追加
* 既存のリクエストメッセージへの `REQUIRED` とアノテーション付けされた新しいフィールドの追加
* 以前に入力として受け付けられていた既存のフィールドへの `OUTPUT_ONLY` の追加
* 以前に出力として送出されていた既存のフィールドへの `INPUT_ONLY` の追加
* 以前に変更可能と見なされていた既存のフィールドへの `IMMUTABLE` の追加
* 以前に入力として無視されていた既存のフィールドからの `OUTPUT_ONLY` の削除
* 既存のフィールドからの `IDENTIFIER` の削除。

後方互換性の*ある*変更もあり、それは以下の通りである：

* 既存のフィールドへの `OPTIONAL` の追加
* 既存の `name` フィールドへの `IDENTIFIER` の追加
* 既存のフィールドの `REQUIRED` から `OPTIONAL` への変更
* 既存のフィールドの `OUTPUT_ONLY` または `IMMUTABLE`（あるいはその両方）から `IDENTIFIER` への変更
* 既存のフィールドからの `REQUIRED` の削除
* 以前にレスポンスで除外されていた既存のフィールドからの `INPUT_ONLY` の削除
* 以前にimmutableと見なされていた既存のフィールドからの `IMMUTABLE` の削除

## 根拠

### Identifierフィールド動作

リソース名（任意の準拠リソースの主識別子）は、作成時にユーザーによって完全に構築されることは決してない。そのようなフィールドは通常 `OUTPUT_ONLY` フィールド動作を割り当てられる。しかし、これらはリソース自体が主たるリクエストペイロードであるシナリオでは主識別子として消費されることも多い。そのようなフィールドは `OUTPUT_ONLY` と見なすことができ*ない*。さらに、標準Updateのような変更リクエストでは、主識別子としてのリソース名はその場で変更できない。そのようなフィールドは通常 `IMMUTABLE` フィールド動作を割り当てられる。これらの相反する文脈依存のフィールド動作のため、リソース名フィールドの動作を特定して伝達するための新しい値が必要であった。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須かオプショナルのいずれかであり、したがって少なくとも `REQUIRED` または `OPTIONAL` アノテーションをそれぞれ持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### field behaviorの必須化

各フィールドにfield behaviorアノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須にすることで、API作成者はAPIの初期作成時に動作を明示的に検討せざるを得なくなる。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更をもたらす可能性がある。例えば、オプショナルフィールドを必須にすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後に一部のfield_behavior値を追加または変更することは後方互換性がない可能性がある。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

API作成時にfield_behaviorを必須化する利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
