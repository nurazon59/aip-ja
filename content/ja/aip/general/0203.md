# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作の特定の側面（必須かオプショナルかなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリのシグニチャを最適化するため）。

## ガイダンス

APIは`google.api.field_behavior`アノテーションを使用して、フィールドが必須かイミュータブルかなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIはリクエストで使用されるメッセージまたはサブメッセージのすべてのフィールドに`google.api.field_behavior`アノテーションを**適用しなければならない**（must）。
- アノテーションには、フィールドの動作を正確に記述する[google.api.FieldBehavior][]の値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を**使用してはならない**（must not）。
- APIは最低でも`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれか1つを**使用しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作には影響しないが、多くのクライアント（例：CLIやSDK）はコードを生成するためにこれらに依存している。新しいフィールドを追加する際には、どの値が関連するかを徹底的に確認し検討すること。

アノテーションのないフィールドは後方互換性のために`OPTIONAL`と解釈される。それでもなお、このアノテーションを**省略してはならない**（must not）。

**注:** このドキュメントで与えられる語彙は*記述的*な目的のみのものであり、それ自体がバリデーションを追加するものではない。目的は、クライアントのためにこの動作を一貫して文書化することである。

### ネストされたメッセージのfield behavior

`google.api.field_behavior`アノテーションは、ネストされたメッセージ上のものと親のものは独立している。

例えば、ネストされたメッセージは親フィールドが`OPTIONAL`である一方で、`REQUIRED`のフィールド動作を持つことができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されていれば、`text`フィールドは必須である。

## 語彙

### 識別子

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。`name`フィールドに**付けなければならず**（must）、他のフィールドには**付けてはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、作成メソッドのコンテキストではフィールドが入力として受け入れられない（すなわち`OUTPUT_ONLY`）こと、また[標準Update][aip-134]のようにリソースを主たる入力として受け入れる変更メソッドでは`IMMUTABLE`と見なされつつ入力として受け入れられることを伝える。

このアノテーションはメッセージ内の他のリソースへの参照に**適用してはならない**（must not）。

### イミュータブル

`IMMUTABLE`の使用は、リソースのフィールドが作成後に変更できないことを示す。これは、入力または出力、必須またはオプショナルのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でイミュータブルなフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを**無視すべきであり**（should）、変更が要求された場合は`INVALID_ARGUMENT`で**エラーにすべきである**（should）。

イミュータブルなフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- アプリケーションの存続期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでイミュータブル」なフィールドにイミュータブルアノテーションを**付けてはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドはリソースメッセージ内のフィールド、またはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして**記述されるべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常は名前が`Request`で終わるメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして**記述されるべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- AIP-214で説明されている`ttl`フィールド。

**警告:** input onlyフィールドはまれであり、使用前に慎重に検討すべきである。

### オプショナル

`OPTIONAL`の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常は`Request`で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、オプショナルとして**記述してもよい**（may）。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにフィールドを含めても何も起こらないことを示す（サーバーはこのフィールド内のすべての値を**クリアしなければならず**（must）、入力時にこのフィールドに値が存在した結果として**エラーをスローしてはならない**（must not））。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を**無視しなければならない**（must）（参照：AIP-161）。

さらに、フィールドはリソースメッセージ内のフィールド、またはツリーのより下位のメッセージのフィールドである場合にのみ、output onlyとして**記述されるべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常は`Response`で終わるメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして**記述されるべきではない**（should not）。

output onlyフィールドは、APIにとって適切であれば空の値に**設定してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生または構造化された情報。
- 変更できない、サービスによって割り当てられるリソースのプロパティ。

### 必須

`REQUIRED`の使用は、フィールドがリクエストまたはリソースに（空でない値で設定されて）**存在しなければならない**（must）ことを示す。

フィールドは、*以下のいずれか*の場合にのみ必須として**記述されるべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成する][aip-133]際には、作成リクエスト上のフィールドに値を**提供しなければならない**（must）。
  - リソースを[更新する][aip-134]際には、フィールドがフィールドマスクにも存在しない場合（フィールドへの変更がないことを示す）、ユーザーはフィールドを**省略してもよい**（may）（それ以外の場合は**提供しなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、通常は`Request`で終わる名前のメッセージ）上のフィールドである。この場合、リクエストの一部として値を**提供しなければならず**（must）、提供に失敗した場合は**エラーを引き起こさなければならない**（must）（通常は`INVALID_ARGUMENT`）。

上記の「truthy」という用語は以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false`以外の値
- repeatedフィールドやマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つ任意のメッセージ。

以下のことを示すためにフィールドを必須として**記述すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 一部の状況で条件付きで必須となるフィールド。
- ユーザー入力として使用されることが決してないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定の値と区別がつかないため、必須フィールドをfalsyな値に設定するとエラーが発生する。このことの帰結として、必須のブール値は`true`に設定**しなければならない**（must）。

### 順序なしリスト

リソースのrepeatedフィールドに`UNORDERED_LIST`を使用することは、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合、サービスがユーザーに代わってリストをソートする状況を含めて、順序なしリストとして**記述されるべきである**（should）。

順序なしリストを持つリソースは、安定した順序でリストを**返してもよく**（may）、ランダム化された不安定な順序でリストを**返してもよい**（may）。

## 後方互換性

`google.api.field_behavior`値の追加や変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味論的な変更を表す可能性がある。以下は`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前は（暗黙的または明示的に）`OPTIONAL`と見なされていた既存のフィールドに`REQUIRED`を追加する
* 既存のリクエストメッセージに`REQUIRED`とアノテーションされた新しいフィールドを追加する
* 以前は入力として受け入れられていた既存のフィールドに`OUTPUT_ONLY`を追加する
* 以前は出力として発行されていた既存のフィールドに`INPUT_ONLY`を追加する
* 以前はミュータブルと見なされていた既存のフィールドに`IMMUTABLE`を追加する
* 以前は入力として無視されていた既存のフィールドから`OUTPUT_ONLY`を削除する
* 既存のフィールドから`IDENTIFIER`を削除する

後方互換性が*ある*変更もいくつかあり、以下の通りである：

* 既存のフィールドに`OPTIONAL`を追加する
* 既存の`name`フィールドに`IDENTIFIER`を追加する
* 既存のフィールドで`REQUIRED`から`OPTIONAL`に変更する
* 既存のフィールドで`OUTPUT_ONLY`や`IMMUTABLE`から`IDENTIFIER`に変更する
* 既存のフィールドから`REQUIRED`を削除する
* 以前はレスポンスから除外されていた既存のフィールドから`INPUT_ONLY`を削除する
* 以前はイミュータブルと見なされていた既存のフィールドから`IMMUTABLE`を削除する

## 根拠

### 識別子フィールド動作

リソース名は、あらゆる準拠したリソースの主識別子であり、作成時にユーザーによって完全に構築されることはない。このようなフィールドは通常`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、リソース自体が主たるリクエストペイロードであるシナリオでは、主識別子としても利用される。このようなフィールドは`OUTPUT_ONLY`とは見なせ*なかった*。さらに、標準Updateのような変更リクエストでは、主識別子としてのリソース名はその場で変更できない。このようなフィールドは通常`IMMUTABLE`フィールド動作が割り当てられる。これらの相反しコンテキスト依存のフィールド動作は、リソース名フィールドの動作を抽出して伝達するために新しい値が必要であることを意味した。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれか**でなければならない**（must）。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドは必須またはオプショナルのいずれかであり、したがってそれぞれ少なくとも`REQUIRED`または`OPTIONAL`アノテーションを**持つべきである**（should）。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかの指定が依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラム的なクライアントとユーザーの理解を向上させる。

アノテーションを必須にすることで、API作成者はAPIの初期作成時に動作を明示的に検討せざるを得なくなる。

初期作成後にフィールド動作を変更すると、クライアントで後方互換性のない変更が生じる可能性がある。例えば、オプショナルフィールドを必須にすると、RPCのメソッドシグニチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023-05にfield_behaviorが必須化された。この変更以前は、アノテーションはしばしば省略されていた。その値は高品質なクライアントを生成するために信頼されている。さらに、メジャーバージョン内で後からいくつかのfield_behavior値を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを必須化することの利点は、そうしない場合のクライアントやAPIユーザーへのコストを上回る。
