# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（requiredかoptionalかなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解できると有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは`google.api.field_behavior`アノテーションを使用して、フィールドがrequiredかimmutableかなど、十分に理解されているフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154 `etag` フィールドには `google.api.field_behavior` を割り当てる**べきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合、コメントで特定の動作を文書化**すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する任意の[google.api.FieldBehavior][]値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは少なくとも`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれか1つを使用**しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作には影響しないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が適切かを十分に確認し検討すること。

アノテーションのないフィールドは後方互換性のために`OPTIONAL`と解釈される。それでもなお、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで示す用語は_説明的_な目的のためのみであり、それ自体が検証を追加するわけではない。目的は、クライアント向けにこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の`google.api.field_behavior`アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージのフィールド動作が`REQUIRED`である一方で、親フィールドは`OPTIONAL`とすることができる:

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記のケースでは、`title`が指定されている場合、`text`フィールドはrequiredである。

## 用語

### IDENTIFIER

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは`name`フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、createメソッドのコンテキストではフィールドが入力として受け付けられない（つまり`OUTPUT_ONLY`）ことを伝える一方で、リソースを主入力として受け付ける変更メソッド（例：[標準更新][aip-134]）では`IMMUTABLE`と見なされ、入力として受け付けられる。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### IMMUTABLE

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は`INVALID_ARGUMENT`でエラーに**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）:

- アプリケーションの存続期間中変更できないリソースの属性（例: ディスクタイプ）。

**注:** 「条件的にimmutable」なフィールドにはimmutableアノテーションを付与**してはならない**（must not）。

### INPUT_ONLY

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドはリソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、名前が通常`Request`で終わるメッセージ）内のフィールドは、これがすでに暗黙的であるため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）:

- AIP-214で記述されている`ttl`フィールド。

**警告:** Input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### OPTIONAL

`OPTIONAL`の使用は、フィールドが必須ではないことを示す。

フィールドは、リクエストメッセージ（RPCの引数となるメッセージで、通常`Request`で終わる）、またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互に排他的ではない。詳細についてはAIP-149を参照。

### OUTPUT_ONLY

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにそのフィールドを含めても何も起こらないこと（サーバーはこのフィールドの値を消去**しなければならず**（must）、入力にこのフィールドの値が存在することによるエラーを送出**してはならない**（must not））を示す。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（AIP-161を参照）。

さらに、フィールドはリソースメッセージ内のフィールド、またはツリーのより深い位置にあるメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常`Response`で終わるメッセージ）内のフィールドは、これがすでに暗黙的であるため、output onlyとして記述**すべきではない**（should not）。

Output onlyフィールドは、APIに適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）:

- 作成または更新タイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### REQUIRED

`REQUIRED`の使用は、フィールドがリクエストまたはリソース上に存在**しなければならない**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の_いずれか_に該当する場合にのみrequiredとして記述**すべきである**（should）:

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が_保存されている_場合にのみ有効である。
  - リソースを[作成][aip-133]する際、createリクエスト上でそのフィールドの値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーは、フィールドマスクにもそのフィールドが含まれておらず、フィールドに変更がないことを示す場合に限り、そのフィールドを省略**してもよい**（may）（そうでない場合は提供**しなければならない**（must））。
- リクエストメッセージ（RPCの引数となるメッセージで、通常`Request`で終わる名前を持つ）上のフィールドである。この場合、値はリクエストの一部として提供**しなければならず**（must）、提供しなかった場合はエラー（通常`INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する:

- プリミティブの場合、`0`、`0.0`、空文字列/空バイト、`false`以外の値
- 繰り返しフィールドおよびマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つ任意のメッセージ。

以下を示すためにフィールドをrequiredとして記述**すべきではない**（should not）:

- レスポンスに常に存在するフィールド。
- 状況によって条件的にrequiredとなるフィールド。
- ユーザー入力として使用されることのない任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定の値と区別がつかないため、requiredフィールドにfalsyな値を設定するとエラーが発生する。このことから必然的に、requiredなブール値は`true`に設定しなければならない。

### UNORDERED_LIST

リソースの繰り返しフィールドに`UNORDERED_LIST`を使用することは、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）に、unordered listとして記述**すべきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよく**（may）、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`値の追加または変更は、既存のクライアントにとって互換性がないと認識されるAPIのセマンティックな変更を表す可能性がある。以下は`google.api.field_behavior`に関する後方互換性のない変更の例である:

* 以前に（暗黙的または明示的に）`OPTIONAL`と見なされていた既存のフィールドへの`REQUIRED`の追加
* 既存のリクエストメッセージへの`REQUIRED`としてアノテーションされた新しいフィールドの追加
* 以前に入力として受け付けられていた既存のフィールドへの`OUTPUT_ONLY`の追加
* 以前に出力として送出されていた既存のフィールドへの`INPUT_ONLY`の追加
* 以前に可変と見なされていた既存のフィールドへの`IMMUTABLE`の追加
* 以前に入力として無視されていた既存のフィールドからの`OUTPUT_ONLY`の削除
* 既存のフィールドからの`IDENTIFIER`の削除。

後方互換性の_ある_変更もいくつかあり、以下の通りである:

* 既存のフィールドへの`OPTIONAL`の追加
* 既存の`name`フィールドへの`IDENTIFIER`の追加
* 既存のフィールドの`REQUIRED`から`OPTIONAL`への変更
* 既存のフィールドの`OUTPUT_ONLY`および/または`IMMUTABLE`から`IDENTIFIER`への変更
* 既存のフィールドからの`REQUIRED`の削除
* 以前にレスポンスで除外されていた既存のフィールドからの`INPUT_ONLY`の削除
* 以前にimmutableと見なされていた既存のフィールドからの`IMMUTABLE`の削除

## 根拠

### IDENTIFIERのフィールド動作

リソース名は、準拠するリソースの主識別子であり、create時にユーザーが完全に構築することはない。そのようなフィールドには通常`OUTPUT_ONLY`のフィールド動作が割り当てられる。しかし、リソース自体が主リクエストペイロードとなるシナリオでは、主識別子としても使用されることが多い。そのようなフィールドは`OUTPUT_ONLY`とは見なせ_ない_。さらに、標準更新のような変更リクエストでは、主識別子としてのリソース名をその場で変更することはできない。そのようなフィールドには通常`IMMUTABLE`のフィールド動作が割り当てられる。これらの相反しコンテキストに依存するフィールド動作に対処するために、リソース名フィールドの動作を特定し伝達するための新しい値が必要であった。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力か出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドはrequiredかoptionalのいずれかであり、したがって少なくともそれぞれ`REQUIRED`か`OPTIONAL`のアノテーションを持つべきである。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`か`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の要求

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを要求することで、API作成者はAPIの初期作成時に動作を明示的に検討することを余儀なくされる。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更が生じる可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須化された。この変更以前は、アノテーションがしばしば省略されていた。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後的に一部のfield_behavior値を追加または変更すると、後方互換性が損なわれる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを要求する利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
