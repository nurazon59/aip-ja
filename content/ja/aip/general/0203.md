# フィールド動作のドキュメント化

protocol buffersでフィールドを定義する際、フィールドの動作の特定の側面（必須かオプショナルかなど）をユーザーに説明するのが通例である。さらに、他のツールがこの動作を理解すること（例えばクライアントライブラリのシグネチャを最適化するため）も有用である。

## ガイダンス

APIは `google.api.field_behavior` アノテーションを使用して、フィールドが必須やimmutableであるといった、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージのすべてのフィールドに `google.api.field_behavior` アノテーションを**適用しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154 `etag` フィールドは、`google.api.field_behavior` を**割り当てるべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を**省略してもよい**（may）が、この場合コメントで特定の動作を**文書化すべきである**（should）。
- アノテーションは、フィールドの動作を正確に記述する任意の [google.api.FieldBehavior][] 値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- APIは最低限、`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを**使用しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的にレビューし検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` と解釈される。それでも、このアノテーションを**省略してはならない**（must not）。

**注:** このドキュメントで示される語彙は*記述的*な目的のためのものであり、それ自体がバリデーションを追加するものではない。目的は、この動作をクライアント向けに一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージに対する `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージは `REQUIRED` のフィールド動作を持つことができ、親フィールドは `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定された場合、`text` フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに**付けなければならず**（must）、他のフィールドに**付けてはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER` 値は、作成メソッドのコンテキストではフィールドが入力として受け付けられない（すなわち `OUTPUT_ONLY`）ことを伝えつつ、リソースを主要入力として受け付ける変更メソッド（例：[標準Update][aip-134]）では `IMMUTABLE` と見なされ入力として受け付けられることも伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に**適用してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、必須またはオプショナルのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを**無視すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` で**エラーにすべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- アプリケーションの存続期間中に変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにimmutableアノテーションを**付けてはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールドか、リソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして**記述すべきである**（should）。特に、リクエストメッセージ（通常 `Request` で終わる名前を持ち、RPCの引数としてのみ機能するメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして**記述すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- AIP-214で説明されている `ttl` フィールド。

**警告:** input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（通常 `Request` で終わる名前を持ち、RPCの引数であるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして**記述してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細はAIP-149を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も起こらない（サーバーはこのフィールドの値を**クリアしなければならず**（must）、入力でこのフィールドに値が存在する結果として**エラーを投げてはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスクにおけるoutput onlyフィールドの存在を**無視しなければならない**（must）（AIP-161参照）。

さらに、フィールドは、リソースメッセージ内のフィールドか、ツリーのより深い位置にあるメッセージのフィールドである場合にのみ、output onlyとして**記述すべきである**（should）。特に、レスポンスメッセージ（通常 `Response` で終わる名前を持ち、RPCの戻り値としてのみ機能するメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして**記述すべきではない**（should not）。

output onlyフィールドは、APIに適切であれば**空の値に設定してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に**存在しなければならない**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして**記述すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでそのフィールドに値が**提供されなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドマスクにもそのフィールドが含まれていない場合、そのフィールドを**省略してもよい**（may）（そうでない場合は**提供されなければならない**（must））。
- リクエストメッセージ（通常 `Request` で終わる名前を持ち、RPCの引数であるメッセージ）上のフィールドである。この場合、値がリクエストの一部として**提供されなければならず**（must）、そうしない場合**エラーを引き起こさなければならない**（must）（通常は `INVALID_ARGUMENT`）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/バイト、`false` 以外の値
- repeatedフィールドやマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

フィールドは、以下を示すためにrequiredとして**記述すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 特定の状況で条件付きで必須となるフィールド。
- ユーザー入力として決して使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enumの未指定値など）は未設定の値と区別がつかないため、requiredフィールドをfalsyな値に設定するとエラーになる。これの当然の帰結として、requiredなブール値は `true` に**設定しなければならない**。

### Unordered List

リソースのrepeatedフィールドに対する `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

サービスが、リスト内の要素の順序がユーザーが送信した順序と一致すること（サービスがユーザーに代わってリストをソートする状況を含む）を保証しない場合、フィールドをunordered listとして**記述すべきである**（should）。

unordered listを持つリソースは、リストを安定した順序で**返してもよい**（may）し、ランダム化された不安定な順序で**返してもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントにとって非互換と認識されるAPIの意味的な変更を表す可能性がある。以下は `google.api.field_behavior` における後方互換性のない変更の例である：

* 以前 `OPTIONAL`（暗黙的またはその他）と見なされていた既存のフィールドに `REQUIRED` を追加すること
* 既存のリクエストメッセージに `REQUIRED` としてアノテーションされた新しいフィールドを追加すること
* 以前入力として受け付けられていた既存のフィールドに `OUTPUT_ONLY` を追加すること
* 以前出力として送出されていた既存のフィールドに `INPUT_ONLY` を追加すること
* 以前変更可能と見なされていた既存のフィールドに `IMMUTABLE` を追加すること
* 以前入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除すること
* 既存のフィールドから `IDENTIFIER` を削除すること

後方互換性が*ある*変更もあり、以下の通りである：

* 既存のフィールドに `OPTIONAL` を追加すること
* 既存の `name` フィールドに `IDENTIFIER` を追加すること
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更すること
* 既存のフィールドで `OUTPUT_ONLY` や `IMMUTABLE` から `IDENTIFIER` に変更すること
* 既存のフィールドから `REQUIRED` を削除すること
* 以前レスポンスで除外されていた既存のフィールドから `INPUT_ONLY` を削除すること
* 以前immutableと見なされていた既存のフィールドから `IMMUTABLE` を削除すること

## 根拠

### Identifierフィールド動作

リソース名は、準拠するすべてのリソースの主要識別子であり、ユーザーが作成時に完全に構築することは決してない。このようなフィールドは通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、これらはリソース自体が主要なリクエストペイロードであるシナリオでも主要識別子としてよく利用される。このようなフィールドは `OUTPUT_ONLY` と見なすことが*できなかった*。さらに、標準Updateのような変更リクエストでは、主要識別子としてのリソース名はその場で変更できない。このようなフィールドは通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの相反しコンテキスト依存のフィールド動作は、リソース名フィールドの動作を特定して伝えるために新しい値が必要であることを意味した。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力か出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須かオプショナルのいずれかであり、したがってそれぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の要求

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラム的なクライアントとユーザーの理解を向上させる。

アノテーションを要求することは、API作成者がAPIの初期設計時に動作を明示的に検討することも強制する。

初期設計後にフィールド動作を変更すると、クライアントにおいて後方互換性のない変更が生じる可能性がある。例えば、オプショナルフィールドを必須にすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

## 歴史

2023年5月、field_behaviorが必須になった。この変更以前は、アノテーションはしばしば省略されていた。その値は高品質なクライアントを生成するために依存されている。さらに、一部のfield_behavior値を事後にメジャーバージョン内で追加または変更することは後方互換性がない可能性がある。より詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

API設計時にfield_behaviorを要求することの利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
