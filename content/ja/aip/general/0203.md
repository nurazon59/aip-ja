# フィールド動作のドキュメント化

protocol buffers でフィールドを定義する際、フィールドの動作に関する特定の側面（必須かオプションかなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

API は、`google.api.field_behavior` アノテーションを使用して、フィールドが必須であるか immutable であるかなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- API は、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外はリソースメッセージ上の AIP-154 の `etag` フィールドであり、`google.api.field_behavior` を割り当て**るべきではない**（should not）。
- アノテーションは、フィールドの動作を正確に記述する [google.api.FieldBehavior][] 値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- API は最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` は proto レベルの動作に影響を与えないが、多くのクライアント（例: CLI や SDK）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的に確認し検討すること。

アノテーションのないフィールドは、後方互換性のため `OPTIONAL` と解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで示される用語は*記述的*な目的のみであり、それ自体が検証を追加するものではない。目的は、クライアントに対してこの動作を一貫してドキュメント化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージが `REQUIRED` のフィールド動作を持ち、親フィールドが `OPTIONAL` であることができる:

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されている場合、`text` フィールドは必須である。

## 語彙

### 識別子

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER` 値は、create メソッドの文脈ではそのフィールドが入力として受け付けられない（つまり `OUTPUT_ONLY`）ことを伝え、同時に `IMMUTABLE` と見なされ、リソースを主要入力として受け付ける変更メソッド（例: [標準 Update][aip-134]）では入力として受け付けられる。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、必須またはオプションのいずれのフィールドにも適用される。

サービスが更新リクエスト（または類似のもの）で immutable フィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーに**すべきである**（should）。

immutable フィールドの潜在的なユースケース（これは網羅的なリストではない）:

- アプリケーションの存続期間中に変更できないリソースの属性（例: ディスクタイプ）。

**注:** 「条件付きで immutable」なフィールドには、immutable アノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールドまたはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input only として記述**すべきである**（should）。特に、リクエストメッセージ（RPC の引数としてのみ機能し、通常 `Request` で終わる名前を持つメッセージ）内のフィールドは、これがすでに暗黙的であるため、input only として記述**すべきではない**（should not）。

input only フィールドの潜在的なユースケース（これは網羅的なリストではない）:

- AIP-214 で説明されている `ttl` フィールド。

**警告:** input only フィールドは稀であり、使用前に慎重に検討**すべきである**（should）。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPC の引数であるメッセージで、通常 `Request` で終わる）上のフィールド、またはサブメッセージ上のフィールドである場合、optional として記述**してもよい**（may）。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストでメッセージにそのフィールドを含めても何も起こらないことを示す（サーバーはこのフィールドの値をクリア**しなければならず**（must）、入力にこのフィールドの値が存在する結果としてエラーを送出**してはならない**（must not））。同様に、サービスは更新フィールドマスク内の output only フィールドの存在を無視**しなければならない**（must）（参照: AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーのより深い位置にあるメッセージのフィールドである場合にのみ、output only として記述**すべきである**（should）。特に、レスポンスメッセージ（RPC の戻り値としてのみ機能し、通常 `Response` で終わるメッセージ）内のフィールドは、これがすでに暗黙的であるため、output only として記述**すべきではない**（should not）。

output only フィールドは、API にとって適切であれば空の値に設定**してもよい**（may）。

output only フィールドの潜在的なユースケース（これは網羅的なリストではない）:

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- 変更できない、サービスによって割り当てられたリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）、空でない値に設定**しなければならない**（must）ことを示す。

フィールドは、以下の*いずれか*の場合にのみ required として記述**すべきである**（should）:

- ユーザーがどこかで入力として提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、create リクエスト上でそのフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドを省略**してもよい**（may）。ただし、そのフィールドがフィールドマスクにも存在せず、フィールドへの変更がないことを示す場合に限る（そうでない場合、値を提供**しなければならない**（must））。
- RPC の引数であるリクエストメッセージ（通常 `Request` で終わる名前を持つ）上のフィールドである。この場合、リクエストの一部として値を提供**しなければならず**（must）、提供しない場合はエラー（通常 `INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する:

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false` 以外の値
- repeated フィールドや map の場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

以下のことを示すために required として記述**すべきではない**（should not）:

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（真偽値の `false`、整数の `0`、enum の未指定値など）は未設定の値と区別がつかないため、required フィールドに falsy な値を設定するとエラーになる。このことから、required な真偽値は `true` に設定**しなければならない**（must）という結果が導かれる。

### 順序なしリスト

リソースの repeated フィールドにおける `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返し**てもよく**（may）、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加または変更は、既存のクライアントにとって互換性がないと認識される意味上の API の変更を表す可能性がある。以下は `google.api.field_behavior` に関する後方互換性のない変更の例である:

* 以前に（暗黙的または明示的に）`OPTIONAL` と見なされていた既存のフィールドへの `REQUIRED` の追加
* 既存のリクエストメッセージへの `REQUIRED` とアノテーションされた新しいフィールドの追加
* 以前に入力として受け付けられていた既存のフィールドへの `OUTPUT_ONLY` の追加
* 以前に出力として送出されていた既存のフィールドへの `INPUT_ONLY` の追加
* 以前に mutable と見なされていた既存のフィールドへの `IMMUTABLE` の追加
* 以前に入力として無視されていた既存のフィールドからの `OUTPUT_ONLY` の削除
* 既存のフィールドからの `IDENTIFIER` の削除

*後方互換性がある*変更もあり、以下の通りである:

* 既存のフィールドへの `OPTIONAL` の追加
* 既存の `name` フィールドへの `IDENTIFIER` の追加
* 既存のフィールドにおける `REQUIRED` から `OPTIONAL` への変更
* 既存のフィールドにおける `OUTPUT_ONLY` または `IMMUTABLE`（あるいはその両方）から `IDENTIFIER` への変更
* 既存のフィールドからの `REQUIRED` の削除
* 以前にレスポンスで除外されていた既存のフィールドからの `INPUT_ONLY` の削除
* 以前に immutable と見なされていた既存のフィールドからの `IMMUTABLE` の削除

## 根拠

### 識別子フィールド動作

リソース名は、あらゆる準拠リソースの主識別子であり、作成時にユーザーが完全に構築することは決してない。そのようなフィールドは通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードであるシナリオでは、主識別子として消費されることも多い。そのようなフィールドは `OUTPUT_ONLY` とは見なせ*なかった*。さらに、標準 Update のような変更リクエストでは、主識別子としてのリソース名はその場で変更できない。そのようなフィールドは通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの矛盾し文脈依存のフィールド動作は、リソース名フィールドの動作を特定して伝えるために新しい値が必要であることを意味していた。

### 注釈の必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須またはオプションのいずれかであるため、それぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを持つ**べきである**（should）。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須化することは、API 作成者が API の初期作成時に動作を明示的に検討することを強制する。

初期作成後にフィールド動作を変更すると、クライアントにおいて後方互換性のない変更が生じる可能性がある。例えば、オプショナルフィールドを必須にすると、RPC や[宣言的クライアント][Declarative client]におけるリソースのメソッドシグネチャに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023年5月に field_behavior が必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後に一部の field_behavior 値を追加または変更すると、後方互換性が損なわれる可能性がある。より詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

API の作成時に field_behavior を必須化することの利点は、そうしないことによるクライアントおよび API ユーザーへのコストを上回る。
