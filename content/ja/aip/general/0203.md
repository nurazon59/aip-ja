# フィールド動作のドキュメント化

プロトコルバッファでフィールドを定義する際、フィールドの動作に関する特定の側面（必須かオプショナルかなど）をユーザーに説明するのが慣例である。さらに、他のツールがこの動作を理解できることは有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは `google.api.field_behavior` アノテーションを使用して、フィールドが必須かimmutableかなど、よく理解されているフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージのすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - 例外として、リソースメッセージのAIP-154の `etag` フィールドには、いかなる `google.api.field_behavior` も割り当てる**べきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合、特定の動作をコメントに文書化**すべきである**（should）。
- アノテーションは、フィールドの動作を正確に記述する任意の [google.api.FieldBehavior][] 値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用して**はならない**（must not）。
- APIは、最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成に依存している。新しいフィールドを追加する際は、どの値が関連するかを十分にレビューし検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` と解釈される。それにもかかわらず、このアノテーションを省略して**はならない**（must not）。

**注:** このドキュメントで提供される語彙は*記述的*な目的のみであり、それ自体でバリデーションを追加するものではない。その目的は、この動作をクライアントに対して一貫して文書化することである。

### ネストされたメッセージのfield_behavior

ネストされたメッセージの `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージが `REQUIRED` のフィールド動作を持ち、親フィールドが `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されると、`text` フィールドは必須となる。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに付与**されなければならず**（must）、他のフィールドに付与して**はならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER` 値は、作成メソッドのコンテキストではフィールドが入力として受け入れられない（すなわち `OUTPUT_ONLY`）一方で、リソースを主な入力として受け入れる変更メソッド（例：[標準Update][aip-134]）では `IMMUTABLE` と見なされ入力として受け入れられることを伝達する。

このアノテーションは、メッセージ内の他のリソースへの参照に適用して**はならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソースのフィールドが作成後に変更できないことを示す。これは、入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableなフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーと**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- アプリケーションのライフタイムにわたって変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにはimmutableアノテーションを付与して**はならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージのフィールドまたはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特筆すべきは、リクエストメッセージ（RPCの引数としてのみ機能し、通常 `Request` で終わる名前を持つメッセージ）のフィールドは、これが既に暗黙的であるため、input onlyとして記述**すべきではない**（should not）ことである。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- AIP-214で説明されている `ttl` フィールド。

**警告:** Input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であるメッセージで、通常 `Request` で終わる）のフィールド、またはサブメッセージのフィールドである場合に、optionalとして記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も起こらないことを示す（サーバーはこのフィールドの値をすべてクリア**しなければならず**（must）、入力にこのフィールドの値が存在するためにエラーをスローして**はならない**（must not））。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージのフィールド、またはツリーの下位のメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特筆すべきは、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常 `Response` で終わるメッセージ）のフィールドは、これが既に暗黙的であるため、output onlyとして記述**すべきではない**（should not）ことである。

Output onlyフィールドは、APIに適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーがどこかで入力として提供するリソースのフィールドである。この場合、リソースは「truthy」な値が*保存されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでそのフィールドの値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドを省略**してもよい**（may）。ただしフィールドがフィールドマスクにも存在しない場合に限る。これはそのフィールドに変更がないことを示す（そうでない場合、値を提供**しなければならない**（must））。
- リクエストメッセージ（RPCの引数であるメッセージで、通常 `Request` で終わる名前を持つ）のフィールドである。この場合、リクエストの一部として値を提供**しなければならず**（must）、提供しない場合はエラー（通常 `INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false` 以外の値
- 繰り返しフィールドやマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つ任意のメッセージ

以下のことを示すためにフィールドをrequiredとして記述**すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 一部の状況で条件付きでrequiredとなるフィールド。
- ユーザー入力として使用されることのない、あらゆるメッセージ（リソースであるメッセージを含む）のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enumの未指定値など）は未設定の値と区別できないため、requiredフィールドをfalsyな値に設定するとエラーになる。このことの帰結として、requiredなブール値は `true` に設定しなければならない。

### Unordered List

リソースの繰り返しフィールドに `UNORDERED_LIST` を使用することは、サービスがリスト内の項目の順序を保証しないことを示す。

サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、フィールドはunordered listとして記述**すべきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよく**（may）、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加または変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味的変更を表す可能性がある。以下は `google.api.field_behavior` の後方互換性のない変更の例である：

* 以前に `OPTIONAL` と見なされていた既存フィールドへの `REQUIRED` の追加（暗黙的か明示的かを問わず）
* 既存のリクエストメッセージへの `REQUIRED` とアノテーションされた新しいフィールドの追加
* 以前に入力として受け入れられていた既存フィールドへの `OUTPUT_ONLY` の追加
* 以前に出力として発行されていた既存フィールドへの `INPUT_ONLY` の追加
* 以前に可変と見なされていた既存フィールドへの `IMMUTABLE` の追加
* 以前に入力として無視されていた既存フィールドからの `OUTPUT_ONLY` の削除
* 既存フィールドからの `IDENTIFIER` の削除。

後方互換性の*ある*変更もあり、以下の通りである：

* 既存フィールドへの `OPTIONAL` の追加
* 既存の `name` フィールドへの `IDENTIFIER` の追加
* 既存フィールドの `REQUIRED` から `OPTIONAL` への変更
* 既存フィールドの `OUTPUT_ONLY` および/または `IMMUTABLE` から `IDENTIFIER` への変更
* 既存フィールドからの `REQUIRED` の削除
* 以前にレスポンスで除外されていた既存フィールドからの `INPUT_ONLY` の削除
* 以前にimmutableと見なされていた既存フィールドからの `IMMUTABLE` の削除

## 根拠

### Identifierフィールド動作

リソース名（あらゆる準拠リソースの主識別子）は、作成時にユーザーが完全に構成することは決してない。このようなフィールドは通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、リソース自体が主なリクエストペイロードであるシナリオでは、主識別子としても消費される。このようなフィールドは `OUTPUT_ONLY` とは見なせ*ない*。さらに、標準Updateのような変更リクエストでは、主識別子としてのリソース名をその場で変更することはできない。このようなフィールドは通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの競合しコンテキスト依存のフィールド動作は、リソース名フィールドの動作を識別し伝達するために新しい値が必要であることを意味した。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドはrequiredまたはoptionalのいずれかであり、したがってそれぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかの指定が依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作のアノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須とすることで、API作成者はAPIの初期作成時に動作を明示的に検討せざるを得なくなる。

初期作成後にフィールド動作を変更すると、クライアントにおいて後方互換性のない変更をもたらす可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]におけるリソースの後方互換性のない変更につながる。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)のセクションを参照。

## 履歴

2023年5月にfield_behaviorが必須化された。この変更以前は、アノテーションはしばしば省略されていた。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で後からfield_behavior値の一部を追加または変更することは、後方互換性がない場合がある。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)のセクションを参照。

API作成時にfield_behaviorを必須とすることの利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
