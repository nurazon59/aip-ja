# フィールド動作の文書化

Protocol Buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（requiredかoptionalかなど）をユーザーに説明するのが慣例である。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは `google.api.field_behavior` アノテーションを使用して、フィールドがrequiredかimmutableかなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の `etag` フィールドは、`google.api.field_behavior` を割り当て**るべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合、特定の動作をコメントに文書化**すべきである**（should）。
- アノテーションは、フィールドの動作を正確に記述する任意の [google.api.FieldBehavior][] 値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- APIは最低限、`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれか1つを使用**しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成にこれらを依存している。新しいフィールドを追加する際は、どの値が関連するかを十分に確認し検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` として解釈される。それでもなお、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される用語は*記述的*な目的のみであり、それ自体は検証を追加するものではない。目的は、この動作をクライアントに対して一貫して文書化することである。

### ネストされたメッセージの field_behavior

ネストされたメッセージの `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージが `REQUIRED` のフィールド動作を持ち、親フィールドが `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されていれば、`text` フィールドはrequiredである。

## 用語

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは `name` フィールドに付加**しなければならず**（must）、他のフィールドに付加**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER` 値は、作成メソッドのコンテキストではフィールドが入力として受け入れられない（すなわち `OUTPUT_ONLY`）ことを伝えると同時に、`IMMUTABLE` と見なされ、リソースを主要な入力として受け入れる変更メソッド（例：[標準Update][aip-134]）では入力として受け入れられる。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableなフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーと**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- アプリケーションの存続期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールドまたはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（通常 `Request` で終わる名前で、RPCの引数としてのみ機能するメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- AIP-214で説明されている `ttl` フィールド。

**警告:** input onlyフィールドはまれであり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドがrequiredでないことを示す。

フィールドは、リクエストメッセージ（通常 `Request` で終わる名前で、RPCの引数であるメッセージ）またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細はAIP-149を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにフィールドを含めても何も起こらないことを示す（サーバーは、このフィールドのあらゆる値をクリア**しなければならず**（must）、入力に値が存在する結果としてエラーをスロー**してはならない**（must not））。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（AIP-161参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーの下位のメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（通常 `Response` で終わる名前で、RPCの戻り値としてのみ機能するメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして記述**すべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- 作成または更新タイムスタンプ。
- 元のユーザー入力に基づく派生または構造化情報。
- 変更できない、サービスによって割り当てられたリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在**しなければならない**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでフィールドに値が**提供されなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドマスクにもフィールドが存在しない場合に限りフィールドを省略**してもよい**（may）。これはフィールドに変更がないことを示す（そうでない場合、値が**提供されなければならない**（must））。
- リクエストメッセージ（通常 `Request` で終わる名前で、RPCの引数であるメッセージ）上のフィールドである。この場合、値がリクエストの一部として**提供されなければならず**（must）、提供されない場合はエラー（通常 `INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/空バイト、`false` 以外の値
- repeatedフィールドやマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

フィールドは、以下を示すためにrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きでrequiredとなるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（boolの `false`、整数の `0`、enumの未指定値など）は未設定値と区別がつかないため、requiredフィールドをfalsyな値に設定するとエラーになる。この系として、requiredなboolは `true` に設定**しなければならない**（must）。

### Unordered List

リソースのrepeatedフィールドでの `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、unordered listとして記述**すべきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよく**（may）、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値を追加または変更すると、既存のクライアントにとって互換性がないと認識されるAPIの意味的な変更を表す可能性がある。以下は、`google.api.field_behavior` に関する後方互換性のない変更の例である：

* 以前は（暗黙的または明示的に）`OPTIONAL` と見なされていた既存のフィールドに `REQUIRED` を追加する
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加する
* 以前に入力として受け入れられていた既存のフィールドに `OUTPUT_ONLY` を追加する
* 以前に出力として生成されていた既存のフィールドに `INPUT_ONLY` を追加する
* 以前は可変と見なされていた既存のフィールドに `IMMUTABLE` を追加する
* 以前に入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除する
* 既存のフィールドから `IDENTIFIER` を削除する

*後方互換性がある*変更もあり、以下の通り：

* 既存のフィールドに `OPTIONAL` を追加する
* 既存の `name` フィールドに `IDENTIFIER` を追加する
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更する
* 既存のフィールドで `OUTPUT_ONLY` または `IMMUTABLE`（あるいはその両方）から `IDENTIFIER` に変更する
* 既存のフィールドから `REQUIRED` を削除する
* 以前にレスポンスで除外されていた既存のフィールドから `INPUT_ONLY` を削除する
* 以前はimmutableと見なされていた既存のフィールドから `IMMUTABLE` を削除する

## 根拠

### Identifier フィールド動作

リソース名（任意の準拠リソースの主要識別子）は、作成時にユーザーによって完全に構築されることはない。このようなフィールドは通常、`OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードであるシナリオでは、主要識別子として消費されることも多い。このようなフィールドは `OUTPUT_ONLY` と見なすことが*できなかった*。さらに、標準Updateのような変更リクエストでは、主要識別子としてのリソース名をその場で変更することはできない。このようなフィールドは通常、`IMMUTABLE` フィールド動作が割り当てられる。これらの競合する文脈依存のフィールド動作は、リソース名フィールドの動作を特定して伝達するために新しい値が必要であることを意味した。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドはrequiredかoptionalのいずれかであり、したがってそれぞれ `REQUIRED` または `OPTIONAL` アノテーションを最低限持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の要求

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを要求することで、API作成者はAPIの初期作成時に動作を明示的に検討せざるを得なくなる。

初期作成後にフィールド動作を変更すると、クライアントにおいて後方互換性のない変更をもたらす可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]におけるリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須となった。この変更以前は、アノテーションはしばしば省略されていた。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後に一部のfield_behavior値を追加または変更することは、後方互換性のないものになり得る。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

API作成時にfield_behaviorを要求することの利点は、そうしないことによるクライアントとAPIユーザーへのコストを上回る。
