# フィールド動作のドキュメント化

protocol buffersでフィールドを定義する際、フィールドの動作の特定の側面（必須かオプショナルかなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解できることは有用である（例えば、クライアントライブラリのシグネチャを最適化するためなど）。

## ガイダンス

APIは、`google.api.field_behavior`アノテーションを使用して、必須やimmutableなど、よく理解されたフィールドの動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージのすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の`etag`フィールドは、`google.api.field_behavior`を割り当て**るべきではない**（should not）。
- アノテーションは、フィールドの動作を正確に記述する任意の[google.api.FieldBehavior][]値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは最低限、`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**重要:** `field_behavior`はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれに依存している。新しいフィールドを追加する際は、どの値が関連するかを十分に検討し、熟考すること。

アノテーションのないフィールドは、後方互換性のために`OPTIONAL`として解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで与えられる語彙は*記述的*な目的のみであり、それ自体が検証を追加するものではない。目的は、この動作をクライアントに対して一貫して文書化することである。

### ネストされたメッセージのfield_behavior

ネストされたメッセージに対する`google.api.field_behavior`アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージが`REQUIRED`のフィールド動作を持ち、親フィールドが`OPTIONAL`であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されている場合、`text`フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは`name`フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、作成メソッドのコンテキストではフィールドが入力として受け付けられず（すなわち`OUTPUT_ONLY`）、一方でリソースを主入力として受け付ける変更メソッド（例：[標準Update][aip-134]）では`IMMUTABLE`と見なされ入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、必須またはオプショナルのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または同様のもの）でimmutableフィールドを受信した場合、更新マスクに含まれていても、値が一致する場合はフィールドを無視する**べきであるが**（should）、変更がリクエストされた場合は`INVALID_ARGUMENT`でエラーと**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- アプリケーションの生存期間中に変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして記述される**べきである**（should）。特に、リクエストメッセージ（通常`Request`で終わる名前を持ち、RPCの引数としてのみ機能するメッセージ）内のフィールドは、既に暗黙的であるため、input onlyとして記述される**べきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- AIP-214で説明されている`ttl`フィールド。

**重要:** input onlyフィールドはまれであり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（通常`Request`で終わる、RPCの引数であるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにフィールドを含めても何も行われないことを示す（サーバーはこのフィールドの値をクリア**しなければならず**（must）、入力にこのフィールドの値が存在することによるエラーをスロー**してはならない**（must not））。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（AIP-161参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーの下方のメッセージのフィールドである場合にのみ、output onlyとして記述される**べきである**（should）。特に、レスポンスメッセージ（通常`Response`で終わる、RPCの戻り値としてのみ機能するメッセージ）内のフィールドは、既に暗黙的であるため、output onlyとして記述される**べきではない**（should not）。

Output onlyフィールドは、APIに適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通り：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生または構造化された情報。
- 変更できない、サービスによって割り当てられたリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）（かつ空でない値に設定され**なければならない**（must））ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして記述される**べきである**（should）：

- ユーザーがどこかで入力として提供するリソース上のフィールドである場合。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在せず、フィールドへの変更がないことを示す場合に限り、フィールドを省略**してもよい**（may）（そうでない場合は提供**しなければならない**（must））。
- リクエストメッセージ（通常`Request`で終わる名前を持ち、RPCの引数であるメッセージ）上のフィールドである場合。この場合、値はリクエストの一部として提供**しなければならず**（must）、提供しない場合はエラー（通常`INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/バイト、`false`以外の値
- repeatedフィールドおよびマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つ任意のメッセージ

以下のことを示すために、フィールドをrequiredとして記述する**べきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きでrequiredになるフィールド。
- ユーザー入力として使用されない任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定値と区別がつかないため、requiredフィールドに偽値を設定するとエラーが発生する。このことの帰結として、requiredなブール値は`true`に設定**しなければならない**（must）。

### Unordered List

リソースのrepeatedフィールドに対する`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

サービスが、リスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、フィールドはunordered listとして記述される**べきである**（should）。

unordered listを持つリソースは、安定した順序でリストを返し**てもよく**（may）、ランダム化された不安定な順序でリストを返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`値の追加や変更は、既存のクライアントにとって非互換と認識されるAPIの意味上の変更を表す可能性がある。以下は、`google.api.field_behavior`に関する後方非互換な変更の例である：

* 以前`OPTIONAL`と見なされていた（暗黙的または明示的に）既存のフィールドに`REQUIRED`を追加すること
* 既存のリクエストメッセージに`REQUIRED`とアノテーションされた新しいフィールドを追加すること
* 以前入力として受け付けられていた既存のフィールドに`OUTPUT_ONLY`を追加すること
* 以前出力として出力されていた既存のフィールドに`INPUT_ONLY`を追加すること
* 以前変更可能と見なされていた既存のフィールドに`IMMUTABLE`を追加すること
* 以前入力として無視されていた既存のフィールドから`OUTPUT_ONLY`を削除すること
* 既存のフィールドから`IDENTIFIER`を削除すること

後方互換性が*ある*変更もあり、以下の通りである：

* 既存のフィールドに`OPTIONAL`を追加すること
* 既存の`name`フィールドに`IDENTIFIER`を追加すること
* 既存のフィールドで`REQUIRED`から`OPTIONAL`に変更すること
* 既存のフィールドで`OUTPUT_ONLY`または`IMMUTABLE`（あるいはその両方）から`IDENTIFIER`に変更すること
* 既存のフィールドから`REQUIRED`を削除すること
* 以前レスポンスで除外されていた既存のフィールドから`INPUT_ONLY`を削除すること
* 以前immutableと見なされていた既存のフィールドから`IMMUTABLE`を削除すること

## 根拠

### Identifierフィールド動作

リソース名は、準拠するすべてのリソースの主要な識別子であり、作成時にユーザーが完全に構築することは決してない。このようなフィールドは通常、`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードとなるシナリオでは、主要な識別子としてもしばしば利用される。このようなフィールドは`OUTPUT_ONLY`とは見なせ*なかった*。さらに、標準Updateのような変更リクエストでは、主要な識別子としてのリソース名はその場で変更できない。このようなフィールドは通常、`IMMUTABLE`フィールド動作が割り当てられる。これらの競合しコンテキスト依存のフィールド動作により、リソース名フィールドの動作を特定して伝達するための新しい値が必要となった。

### 必要なアノテーションのセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドは必須かオプショナルのいずれかであり、したがってそれぞれ少なくとも`REQUIRED`または`OPTIONAL`アノテーションを持つべきである。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須化することで、API作成者はAPIの初期作成時に動作を明示的に考慮することも強制される。

初期作成後にフィールド動作を変更すると、クライアントに後方非互換な変更をもたらす可能性がある。例えば、オプショナルフィールドを必須にすると、[宣言的クライアント][Declarative client]におけるRPCのメソッドシグネチャやリソースに後方非互換な変更が生じる。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須化された。この変更以前は、アノテーションがしばしば省略されていた。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で後からfield_behavior値の一部を追加または変更すると、後方非互換になる可能性がある。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

API作成時にfield_behaviorを必須化することの利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
