# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（requiredかoptionalかなど）をユーザーに説明するのが慣例である。さらに、他のツールがこの動作を理解することも有用である（例えば、クライアント ライブラリのシグネチャを最適化するためなど）。

## ガイダンス

APIは`google.api.field_behavior`アノテーションを使用して、フィールドがrequiredやimmutableであるなど、よく理解されたフィールドの動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の`etag`フィールドには、いかなる`google.api.field_behavior`も割り当て**るべきではない**（should not）。
  - さらに、`oneof`フィールドは`google.api.field_behavior`を省略**してもよい**（may）が、この場合、コメントに特定の動作を文書化**すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する[google.api.FieldBehavior][]値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは、最低限`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作には影響しないが、多くのクライアント（CLIやSDKなど）はコード生成にこれらに依存している。新しいフィールドを追加する際には、どの値が関連するかを徹底的に確認し検討すること。

アノテーションのないフィールドは、後方互換性のために`OPTIONAL`と解釈される。それでも、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は_記述的_な目的のみのものであり、それ自体がバリデーションを追加するものではない。目的は、クライアント向けにこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の`google.api.field_behavior`アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージが`REQUIRED`のフィールド動作を持ち、親フィールドが`OPTIONAL`であってもよい：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されていれば、`text`フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは`name`フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、作成メソッドのコンテキストにおいてフィールドが入力として受け付けられない（すなわち`OUTPUT_ONLY`）ことを伝える一方、リソースを主要な入力として受け取る変更メソッド（例：[標準Update][aip-134]）では`IMMUTABLE`と見なされ、入力として受け付けられることも伝える。

このアノテーションを、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受信した場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は`INVALID_ARGUMENT`でエラーに**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- アプリケーションのライフタイムを通じて変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合に限り、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、名前が通常`Request`で終わるメッセージ）内のフィールドは、input onlyとして記述**すべきではない**（should not）。これは既に暗黙的にそうであるためである。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- AIP-214で説明されている`ttl`フィールド。

**警告:** Input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドが必須ではないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、名前が通常`Request`で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も起こらない（サーバーはこのフィールドの値をクリア**しなければならず**（must）、入力時にこのフィールドに値が存在することを理由にエラーをスロー**してはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（参照: AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーのより下位のメッセージのフィールドである場合に限り、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、名前が通常`Response`で終わるメッセージ）内のフィールドは、output onlyとして記述**すべきではない**（should not）。これは既に暗黙的にそうであるためである。

Output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は次のとおりである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の_いずれか_の場合に限り、requiredとして記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が_格納されている_場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエスト上のそのフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、フィールドマスクからもそのフィールドが除外されており、フィールドに変更がないことを示している場合、ユーザーはそのフィールドを省略**してもよい**（may）（そうでない場合は提供**しなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、名前が通常`Request`で終わるメッセージ）上のフィールドである。この場合、値がリクエストの一部として提供**されなければならず**（must）、提供されない場合はエラー（通常は`INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト列、`false`以外の値
- 繰り返しフィールドとマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ。

以下を示すために、フィールドをrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として使用されることのないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定値と区別できず、そのためrequiredフィールドにfalsyな値を設定するとエラーになる。この帰結として、requiredなブール値は`true`に設定されなければならない。

### Unordered List

リソースの繰り返しフィールドでの`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`の値の追加や変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味的変更を表す可能性がある。以下は、`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前は（暗黙的または明示的に）`OPTIONAL`と見なされていた既存のフィールドに`REQUIRED`を追加すること
* 既存のリクエストメッセージに`REQUIRED`のアノテーションが付いた新しいフィールドを追加すること
* 以前は入力として受け付けられていた既存のフィールドに`OUTPUT_ONLY`を追加すること
* 以前は出力として出力されていた既存のフィールドに`INPUT_ONLY`を追加すること
* 以前は変更可能と見なされていた既存のフィールドに`IMMUTABLE`を追加すること
* 以前は入力として無視されていた既存のフィールドから`OUTPUT_ONLY`を削除すること
* 既存のフィールドから`IDENTIFIER`を削除すること。

後方互換性の*ある*変更もあり、以下に示す：

* 既存のフィールドに`OPTIONAL`を追加すること
* 既存の`name`フィールドに`IDENTIFIER`を追加すること
* 既存のフィールドで`REQUIRED`から`OPTIONAL`に変更すること
* 既存のフィールドで`OUTPUT_ONLY`または`IMMUTABLE`（あるいはその両方）から`IDENTIFIER`に変更すること
* 既存のフィールドから`REQUIRED`を削除すること
* 以前はレスポンスから除外されていた既存のフィールドから`INPUT_ONLY`を削除すること
* 以前はimmutableと見なされていた既存のフィールドから`IMMUTABLE`を削除すること

## 根拠

### Identifierフィールド動作

リソース名は、あらゆる準拠リソースの主要な識別子であり、作成時にユーザーによって完全に構築されることはない。このようなフィールドは通常`OUTPUT_ONLY`のフィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードとなるシナリオでは、主要な識別子として使用されることも多い。このようなフィールドは`OUTPUT_ONLY`と見なすことが*できなかった*。さらに、標準Updateのような変更リクエストでは、主要な識別子としてのリソース名をその場で変更することはできない。このようなフィールドには通常`IMMUTABLE`のフィールド動作が割り当てられる。これらの相反しコンテキスト依存のフィールド動作により、リソース名フィールドの動作を特定して伝えるための新しい値が必要となった。

### 必要なアノテーションのセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドはrequiredまたはoptionalのいずれかであり、したがってそれぞれ少なくとも`REQUIRED`または`OPTIONAL`アノテーションを持つべきである。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の要求

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを要求することは、APIの初期作成時にAPI作成者が動作を明示的に考慮することも強制する。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更が生じる可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]におけるリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023年5月に、field_behaviorが必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後にfield_behaviorの値を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを要求することの利点は、要求しないことによるクライアントとAPIユーザーへのコストを上回る。
