# フィールド動作の文書化

Protocol Buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（必須かオプショナルかなど）をユーザーに説明するのが慣例である。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアント ライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは`google.api.field_behavior`アノテーションを使用して、フィールドがrequiredやimmutableであるといった、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージのすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージのAIP-154の`etag`フィールドがあり、これには`google.api.field_behavior`を割り当て**るべきではない**（should not）。
  - さらに、`oneof`フィールドは`google.api.field_behavior`を省略**してもよい**（may）が、この場合、特定の動作をコメントで**文書化すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する[google.api.FieldBehavior][]の値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは少なくとも`REQUIRED`、`OPTIONAL`、または`OUTPUT_ONLY`のいずれかを**使用しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコードの生成にこれらに依存している。新しいフィールドを追加する際には、どの値が関連するかを徹底的に確認し検討すること。

アノテーションのないフィールドは、後方互換性のため`OPTIONAL`として解釈される。それでも、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は*記述的*な目的のみのものであり、それ自体でバリデーションを追加するものではない。目的は、この動作をクライアントに対して一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージの`google.api.field_behavior`アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージが`REQUIRED`のフィールド動作を持ち、親フィールドが`OPTIONAL`であってもよい：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定された場合、`text`フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。`name`フィールドに付加**しなければならず**（must）、他のフィールドに付加**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]参照）。

`IDENTIFIER`値は、作成メソッドのコンテキストではフィールドが入力として受け入れられない（すなわち`OUTPUT_ONLY`）ことを伝えつつ、リソースを主入力として受け取る変更メソッド（例：[標準更新][aip-134]）では`IMMUTABLE`とみなされ入力として受け入れられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受信した場合、更新マスクに含まれていても、値が一致する場合はフィールドを**無視すべきである**（should）が、変更が要求された場合は`INVALID_ARGUMENT`で**エラーすべきである**（should）。

immutableフィールドの潜在的なユースケース（網羅的なリストではない）は以下の通りである：

- アプリケーションの存続期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きimmutable」であるフィールドにはimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージのフィールド、またはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常は名前が`Request`で終わるメッセージ）のフィールドは、これが既に暗黙的であるため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（網羅的なリストではない）は以下の通りである：

- AIP-214で説明されている`ttl`フィールド。

**警告:** input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常は`Request`で終わるメッセージ）のフィールド、またはサブメッセージのフィールドである場合に、optionalとして記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル`optional`とフィールド動作`OPTIONAL`は相互排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにフィールドを含めても何も行われない（サーバーはこのフィールドの値をすべて**クリアしなければならず**（must）、入力に値が存在することを理由にエラーを**スローしてはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を**無視しなければならない**（must）（AIP-161参照）。

さらに、フィールドは、リソースメッセージのフィールド、またはツリーのより下位のメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常は`Response`で終わるメッセージ）のフィールドは、これが既に暗黙的であるため、output onlyとして記述**すべきではない**（should not）。

output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（網羅的なリストではない）は以下の通りである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生または構造化された情報。
- 変更できない、サービスによって割り当てられたリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソースに存在**しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*格納*されている場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでフィールドに値を**提供しなければならない**（must）。
  - リソースを[更新][aip-134]する際、フィールドがフィールドマスクにも存在せず、フィールドに変更がないことを示している場合に限り、ユーザーはフィールドを**省略してもよい**（may）（そうでない場合は値を**提供しなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、通常は名前が`Request`で終わるメッセージ）のフィールドである。この場合、リクエストの一部として値を**提供しなければならず**（must）、提供しない場合はエラー（通常は`INVALID_ARGUMENT`）を**引き起こさなければならない**（must）。

上記で使用した「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/バイト、`false`以外の値
- 繰り返しフィールドやマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つメッセージ

以下のことを示すためにフィールドをrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きでrequiredになるフィールド。
- ユーザー入力として決して使用されない、任意のメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定値と区別できないため、requiredフィールドをfalsyな値に設定するとエラーが生じる。このことから、requiredなブール値は`true`に設定**しなければならない**（must）という結果が導かれる。

### 順序なしリスト

リソースの繰り返しフィールドにおける`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスが要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーのためにリストをソートする状況を含む）、順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、安定した順序でリストを**返してもよく**（may）、ランダム化された不安定な順序でリストを**返してもよい**（may）。

## 後方互換性

`google.api.field_behavior`の値を追加または変更することは、既存のクライアントにとって互換性のないものとして認識されるセマンティックな変更を意味する可能性がある。以下は`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前`OPTIONAL`とみなされていた（暗黙的または明示的に）既存フィールドへの`REQUIRED`の追加
* 既存のリクエストメッセージへの`REQUIRED`とアノテーションされた新しいフィールドの追加
* 以前入力として受け入れられていた既存フィールドへの`OUTPUT_ONLY`の追加
* 以前出力として出力されていた既存フィールドへの`INPUT_ONLY`の追加
* 以前mutableとみなされていた既存フィールドへの`IMMUTABLE`の追加
* 以前入力として無視されていた既存フィールドからの`OUTPUT_ONLY`の削除
* 既存フィールドからの`IDENTIFIER`の削除。

以下の変更は後方互換*である*：

* 既存フィールドへの`OPTIONAL`の追加
* 既存の`name`フィールドへの`IDENTIFIER`の追加
* 既存フィールドの`REQUIRED`から`OPTIONAL`への変更
* 既存フィールドの`OUTPUT_ONLY`および/または`IMMUTABLE`から`IDENTIFIER`への変更
* 既存フィールドからの`REQUIRED`の削除
* 以前レスポンスで除外されていた既存フィールドからの`INPUT_ONLY`の削除
* 以前immutableとみなされていた既存フィールドからの`IMMUTABLE`の削除

## 根拠

### Identifierフィールド動作

リソース名は、準拠する任意のリソースの主識別子であり、ユーザーが作成時に完全に構築することは決してない。このようなフィールドは通常`OUTPUT_ONLY`のフィールド動作が割り当てられる。しかし、リソース自体が主リクエストペイロードとなるシナリオでは主識別子としても消費される。そのようなフィールドは`OUTPUT_ONLY`とは*みなせない*。さらに、標準更新のような変更リクエストでは、主識別子としてのリソース名はその場で変更できない。このようなフィールドは通常`IMMUTABLE`のフィールド動作が割り当てられる。これらの矛盾するコンテキスト依存のフィールド動作は、リソース名フィールドの動作を特定し伝達するために新しい値が必要であることを意味した。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドはrequiredまたはoptionalのいずれかであり、したがって少なくともそれぞれ`REQUIRED`または`OPTIONAL`アノテーションを**持つべきである**（should）。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の要求

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須とすることで、APIの初回作成時にAPI作成者が明示的に動作を考慮することを強制する。

初回作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更が生じる可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023-05にfield_behaviorが必須になった。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために利用される。さらに、メジャーバージョン内で後からfield_behaviorの値の一部を追加または変更すると、後方互換性のないものになる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを必須とすることの利点は、それを実施しない場合のクライアントとAPIユーザーへのコストを上回る。
