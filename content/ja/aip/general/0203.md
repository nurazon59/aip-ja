# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（必須かオプションかなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアント ライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは、`google.api.field_behavior` アノテーションを使用して、フィールドが必須であるかimmutableであるかなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外は、リソースメッセージ上の AIP-154 の `etag` フィールドであり、これにはいかなる `google.api.field_behavior` も付与**すべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合コメントで特定の動作を文書化**すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する任意の [google.api.FieldBehavior][] 値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- APIは、最低限 `REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY` のいずれか1つを使用**しなければならない**（must）。

**警告:** `field_behavior` はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成のためにこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的にレビューし検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` として解釈される。それでもなお、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は、_記述的_な目的のみのものであり、それ自体はバリデーションを追加するものではない。目的は、クライアントのためにこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージは `REQUIRED` のフィールド動作を持ち、親フィールドは `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title` が指定されると、`text` フィールドは必須である。

## 語彙

### 識別子

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは `name` フィールドに付加**しなければならない**（must）し、他のいかなるフィールドにも付加**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names] を参照）。

`IDENTIFIER` の値は、作成メソッドのコンテキストではフィールドが入力として受け入れられない（すなわち `OUTPUT_ONLY`）ことを伝える一方で、`IMMUTABLE` とも見なされ、リソースを主要な入力として受け入れる変更メソッド（例：[標準更新][aip-134]）の入力としては受け入れられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### 不変

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、必須またはオプションのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーに**すべきである**（should）。

不変フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- アプリケーションの存続期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件的に不変」なフィールドに、immutableアノテーションを付与**してはならない**（must not）。

### 入力専用

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、入力専用として記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、名前が通常 `Request` で終わるメッセージ）内のフィールドは、これがすでに暗黙的であるため、入力専用として記述**すべきではない**（should not）。

入力専用フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- AIP-214で説明されている `ttl` フィールド。

**警告:** 入力専用フィールドはまれであり、使用前に慎重に検討すべきである。

### オプション

`OPTIONAL` の使用は、フィールドが必須ではないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常 `Request` で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、オプションとして記述**してもよい**（may）。

**注:** フィールド存在ラベル `optional` とフィールド動作 `OPTIONAL` は相互排他的ではない。詳細は AIP-149 を参照。

### 出力専用

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も行われないことを示す（サーバーはこのフィールドの値をクリア**しなければならない**（must）し、入力時にこのフィールドに値が存在する結果としてエラーをスロー**してはならない**（must not））。同様に、サービスは更新フィールドマスク内の出力専用フィールドの存在を無視**しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーの下位にあるメッセージのフィールドである場合にのみ、出力専用として記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、名前が通常 `Response` で終わるメッセージ）内のフィールドは、これがすでに暗黙的であるため、出力専用として記述**すべきではない**（should not）。

出力専用フィールドは、APIに適切であれば空の値に設定**してもよい**（may）。

出力専用フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### 必須

`REQUIRED` の使用は、フィールドがリクエストまたはリソース上に存在し（かつ空でない値に設定され）**なければならない**（must）ことを示す。

フィールドは、以下の_いずれか_の場合にのみ必須として記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、「truthy」な値が_保存されている_場合にのみ、リソースは有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでそのフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーは、フィールドマスクにもそのフィールドが含まれていない（フィールドに変更がないことを示す）場合に限り、フィールドを省略**してもよい**（may）（それ以外の場合は提供**しなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、名前が通常 `Request` で終わるメッセージ）上のフィールドである。この場合、リクエストの一部として値を提供**しなければならない**（must）し、提供しない場合はエラー（通常 `INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false` 以外の値
- 繰り返しフィールドとマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」フィールドを持つ任意のメッセージ

以下のことを示すために、フィールドを必須として記述**すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件的に必須となるフィールド。
- ユーザー入力として決して使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の `false`、整数の `0`、enumの未指定値など）は未設定値と区別できないため、必須フィールドにfalsyな値を設定するとエラーが発生する。この帰結として、必須のブール値は `true` に設定しなければならない。

### 順序付けられていないリスト

リソースの繰り返しフィールドでの `UNORDERED_LIST` の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、順序付けられていないリストとして記述**すべきである**（should）。

順序付けられていないリストを持つリソースは、安定した順序でリストを返し**てもよい**（may）し、ランダム化された不安定な順序でリストを返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加または変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味上の変更を表す可能性がある。以下は、`google.api.field_behavior` に関する後方互換性のない変更の例である：

* 以前に（暗黙的または明示的に）`OPTIONAL` と見なされていた既存フィールドへの `REQUIRED` の追加
* 既存のリクエストメッセージへの `REQUIRED` とアノテーションされた新しいフィールドの追加
* 以前に入力として受け入れられていた既存フィールドへの `OUTPUT_ONLY` の追加
* 以前に出力として出力されていた既存フィールドへの `INPUT_ONLY` の追加
* 以前に変更可能と見なされていた既存フィールドへの `IMMUTABLE` の追加
* 以前に入力として無視されていた既存フィールドからの `OUTPUT_ONLY` の削除
* 既存フィールドからの `IDENTIFIER` の削除

後方互換性の*ある*変更もあり、それは以下の通りである：

* 既存フィールドへの `OPTIONAL` の追加
* 既存の `name` フィールドへの `IDENTIFIER` の追加
* 既存フィールドでの `REQUIRED` から `OPTIONAL` への変更
* 既存フィールドでの `OUTPUT_ONLY` または `IMMUTABLE`（あるいはその両方）から `IDENTIFIER` への変更
* 既存フィールドからの `REQUIRED` の削除
* 以前にレスポンスで除外されていた既存フィールドからの `INPUT_ONLY` の削除
* 以前に不変と見なされていた既存フィールドからの `IMMUTABLE` の削除

## 根拠

### 識別子フィールド動作

リソース名（任意の準拠リソースの主要識別子）は、作成時にユーザーによって完全に構築されることは決してない。そのようなフィールドは通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードであるシナリオでは、主要識別子として使用されることも多い。そのようなフィールドは `OUTPUT_ONLY` とは見なせ*ない*。さらに、標準更新のような変更リクエストでは、主要識別子としてのリソース名をその場で変更することはできない。そのようなフィールドは通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの相反するコンテキスト依存のフィールド動作は、リソース名フィールドの動作を特定して伝達するために新しい値が必要であることを意味した。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須またはオプションのいずれかであるため、それぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを持つべきである。`INPUT_ONLY` のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED` または `OPTIONAL` のいずれかを指定することが依然として必要である。

### フィールド動作の要求

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを要求することで、API作成者はAPIの初期作成時に動作を明示的に検討することを強いられる。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更が生じる可能性がある。例えば、オプションフィールドを必須にすると、RPCのメソッドシグネチャ、または[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023年5月に field_behavior が必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は、高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後に field_behavior 値の一部を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

API作成時に field_behavior を要求することの利点は、そうしないことによるクライアントとAPIユーザーへのコストを上回る。
