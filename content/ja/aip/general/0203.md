# フィールド動作のドキュメント化

Protocol Buffers でフィールドを定義する際、フィールドの動作の特定の側面（必須かオプショナルかなど）をユーザーに説明するのが慣例である。さらに、他のツールがこの動作を理解できることは有用である（例えば、クライアントライブラリのシグネチャを最適化するためなど）。

## ガイダンス

API は、フィールドが必須である、不変であるなど、よく理解されているフィールド動作を記述するために `google.api.field_behavior` アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- API は、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに `google.api.field_behavior` アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上の AIP-154 `etag` フィールドには、`google.api.field_behavior` を一切割り当て**るべきではない**（should not）。
  - さらに、`oneof` フィールドは `google.api.field_behavior` を省略**してもよい**（may）が、この場合、コメント内で特定の動作を**文書化すべきである**（should）。
- アノテーションは、フィールドの動作を正確に記述するすべての [google.api.FieldBehavior][] 値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED` を使用**してはならない**（must not）。
- API は最低限 `REQUIRED`、`OPTIONAL`、または `OUTPUT_ONLY` のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior` は proto レベルの動作には影響しないが、多くのクライアント（CLI や SDK など）はコード生成のためにそれらに依存している。新しいフィールドを追加する際には、どの値が関連するかを徹底的に確認し検討すること。

アノテーションのないフィールドは、後方互換性のために `OPTIONAL` と解釈される。それでもなお、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで与えられる語彙は*記述的*な目的のためのみであり、それ自体ではいかなる検証も追加しない。その目的は、クライアントに対してこの動作を一貫してドキュメント化することである。

### ネストされたメッセージの field behavior

ネストされたメッセージ上の `google.api.field_behavior` アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージは `REQUIRED` のフィールド動作を持つことができ、親フィールドは `OPTIONAL` であることができる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記のケースでは、`title` が指定された場合、`text` フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER` の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは `name` フィールドに付加**しなければならず**（must）、他のフィールドに付加**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names] を参照）。

`IDENTIFIER` 値は、create メソッドの文脈ではフィールドが入力として受け入れられない（つまり `OUTPUT_ONLY`）ことを伝えると同時に、リソースを主要入力として受け入れる変更メソッド（例：[標準 Update][aip-134]）では `IMMUTABLE` とみなされ、入力として受け入れられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE` の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、必須またはオプショナルのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または同様のもの）で immutable フィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はフィールドを無視**すべきである**（should）が、変更が要求された場合は `INVALID_ARGUMENT` でエラーに**すべきである**（should）。

immutable フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- アプリケーションの存続期間中変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きで不変」なフィールドには、immutable アノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY` の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input only と記述**すべきである**（should）。特に、リクエストメッセージ（RPC の引数としてのみ機能し、通常 `Request` で終わる名前を持つメッセージ）内のフィールドは、既にこれが暗示されているため、input only と記述**すべきではない**（should not）。

input only フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- AIP-214 で説明されている `ttl` フィールド。

**警告:** input only フィールドはまれであり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL` の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPC の引数となるメッセージで、通常 `Request` で終わる）、またはサブメッセージ上のフィールドである場合、optional と記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル `optional` とフィールド動作 `OPTIONAL` は相互に排他的ではない。詳細については AIP-149 を参照。

### Output only

`OUTPUT_ONLY` の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も起こらないことを示す（サーバーはこのフィールドの値をすべてクリア**しなければならず**（must）、入力時にこのフィールドに値が存在する結果としてエラーをスロー**してはならない**（must not））。同様に、サービスは更新フィールドマスク内の output only フィールドの存在を無視**しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはより下位のメッセージのフィールドである場合にのみ、output only と記述**すべきである**（should）。特に、レスポンスメッセージ（RPC の戻り値としてのみ機能し、通常 `Response` で終わるメッセージ）内のフィールドは、既にこれが暗示されているため、output only と記述**すべきではない**（should not）。

output only フィールドは、API にとって適切であれば空の値に設定**してもよい**（may）。

output only フィールドの潜在的なユースケース（これは網羅的なリストではない）は以下の通りである：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生または構造化された情報。
- 変更できない、サービスによって割り当てられるリソースのプロパティ。

### Required

`REQUIRED` の使用は、フィールドがリクエストまたはリソースに存在**しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみ required と記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成する][aip-133]際、create リクエストでフィールドに値を**提供しなければならない**（must）。
  - リソースを[更新する][aip-134]際、ユーザーはフィールドがフィールドマスクにも存在しない場合にフィールドを**省略してもよい**（may）。これはフィールドへの変更がないことを示す（そうでなければ値を**提供しなければならない**（must））。
- リクエストメッセージ（RPC の引数となるメッセージで、通常 `Request` で終わる名前を持つ）上のフィールドである。この場合、リクエストの一部として値を**提供しなければならず**（must）、提供しない場合はエラー（通常 `INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/バイト、`false` 以外の値
- repeated フィールドやマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

以下のことを示すために、フィールドを required と記述**すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として決して使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（boolean の `false`、整数の `0`、enum の未指定値など）は未設定値と区別がつかないため、required フィールドに falsy な値を設定するとエラーになる。この帰結として、required boolean は `true` に設定されなければならない。

### Unordered List

リソースの repeated フィールドに `UNORDERED_LIST` を使用することは、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合、サービスがユーザーに代わってリストをソートする状況を含めて、unordered list と記述**すべきである**（should）。

unordered list を持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior` 値の追加や変更は、既存のクライアントにとって非互換と認識される API の意味的な変更を表す可能性がある。以下は `google.api.field_behavior` に関する後方互換性のない変更の例である：

* 既存の（暗黙的または明示的に）`OPTIONAL` とみなされていたフィールドに `REQUIRED` を追加する
* 既存のリクエストメッセージに `REQUIRED` とアノテーションされた新しいフィールドを追加する
* 以前に入力として受け入れられていた既存のフィールドに `OUTPUT_ONLY` を追加する
* 以前に出力として出力されていた既存のフィールドに `INPUT_ONLY` を追加する
* 以前に変更可能とみなされていた既存のフィールドに `IMMUTABLE` を追加する
* 以前に入力として無視されていた既存のフィールドから `OUTPUT_ONLY` を削除する
* 既存のフィールドから `IDENTIFIER` を削除する。

後方互換性の*ある*変更もいくつかあり、以下の通りである：

* 既存のフィールドに `OPTIONAL` を追加する
* 既存の `name` フィールドに `IDENTIFIER` を追加する
* 既存のフィールドで `REQUIRED` から `OPTIONAL` に変更する
* 既存のフィールドで `OUTPUT_ONLY` および/または `IMMUTABLE` から `IDENTIFIER` に変更する
* 既存のフィールドから `REQUIRED` を削除する
* 以前にレスポンスで除外されていた既存のフィールドから `INPUT_ONLY` を削除する
* 以前に immutable とみなされていた既存のフィールドから `IMMUTABLE` を削除する

## 根拠

### Identifier フィールド動作

リソース名は、準拠するあらゆるリソースの主要な識別子であり、作成時にユーザーによって完全に構築されることは決してない。そのようなフィールドは通常 `OUTPUT_ONLY` フィールド動作が割り当てられる。しかし、それらはまた、リソース自体が主要なリクエストペイロードであるシナリオにおいて主要な識別子として消費されることも多い。そのようなフィールドは `OUTPUT_ONLY` とはみなせ*ない*だろう。さらに、標準 Update のような変更リクエストでは、主要な識別子としてのリソース名はその場で変更することができない。そのようなフィールドは通常 `IMMUTABLE` フィールド動作が割り当てられる。これらの文脈依存で矛盾するフィールド動作は、リソース名フィールドの動作を特定して伝達するために、新しい値が必要であることを意味した。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY` アノテーションで十分である。

入力の場合、フィールドは必須またはオプショナルのいずれかであり、したがってそれぞれ少なくとも `REQUIRED` または `OPTIONAL` アノテーションを**持つべきである**（should）。`INPUT_ONLY` のみを提供してもフィールドの必要性を伝えないため、`REQUIRED` または `OPTIONAL` のいずれかの指定が依然として必要である。

### field behavior の必須化

各フィールドに field behavior アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラム的なクライアントとユーザーの理解を向上させる。

アノテーションを必須化することは、API 作者に API の初期作成時に動作を明示的に検討させることにもなる。

初期作成後に field behavior を変更すると、クライアントにおいて後方互換性のない変更を引き起こす可能性がある。例えば、オプショナルフィールドを必須にすることは、RPC のメソッドシグネチャや[宣言的クライアント][Declarative client]におけるリソースの後方互換性のない変更をもたらす。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023-05 に field_behavior が必須化された。この変更以前は、アノテーションが省略されることがしばしばあった。その値は高品質なクライアントを生成するために利用されている。さらに、メジャーバージョン内で事後にいくつかの field_behavior 値を追加または変更することは後方互換性がない場合がある。詳細な互換性ガイダンスについては[後方互換性](#後方互換性)セクションを参照。

API 作成時に field_behavior を必須化することの利点は、そうしない場合のクライアントと API ユーザーへのコストを上回る。
