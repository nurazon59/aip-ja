# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（requiredかoptionalかなど）をユーザーに説明するのが通例である。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリのシグネチャを最適化するためなど）。

## ガイダンス

APIは`google.api.field_behavior`アノテーションを使用して、フィールドがrequiredやimmutableであるなど、よく理解されたフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - これに対する例外は、リソースメッセージ上のAIP-154の`etag`フィールドであり、`google.api.field_behavior`を割り当て**るべきではない**（should not）。
- アノテーションは、フィールドの動作を正確に記述する[google.api.FieldBehavior][]値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは少なくとも`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作に影響を与えないが、多くのクライアント（CLIやSDKなど）はコード生成にこれらに依存している。新しいフィールドを追加する際は、どの値が関連するかを徹底的にレビューし検討すること。

アノテーションのないフィールドは、後方互換性のために`OPTIONAL`として解釈される。それでも、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は*説明的*な目的のみのものであり、それ自体が検証を追加するものではない。目的は、この動作をクライアントに対して一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の`google.api.field_behavior`アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージは`REQUIRED`のフィールド動作を持ち、親フィールドは`OPTIONAL`にできる：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されていれば、`text`フィールドはrequiredである。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは`name`フィールドに付与**しなければならず**（must）、他のフィールドに付与**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、そのフィールドがcreateメソッドの文脈では入力として受け付けられず（すなわち`OUTPUT_ONLY`）、一方でリソースを主要入力として受け取る変更メソッド（例：[標準Update][aip-134]）では`IMMUTABLE`とみなされ入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは入力または出力、requiredまたはoptionalのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受信した場合、更新マスクに含まれていても、値が一致する場合はフィールドを無視**すべきである**（should）が、変更が要求された場合は`INVALID_ARGUMENT`でエラーと**すべきである**（should）。

immutableフィールドの使用例として考えられるもの（これは網羅的なリストではない）：

- アプリケーションの存続期間中に変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドには、immutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールドまたはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、名前が通常`Request`で終わるメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの使用例として考えられるもの（これは網羅的なリストではない）：

- AIP-214で説明されている`ttl`フィールド。

**警告:** input onlyフィールドはまれであり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドがrequiredでないことを示す。

フィールドは、リクエストメッセージ（RPCの引数となるメッセージで、通常`Request`で終わる）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエストのメッセージにそのフィールドを含めても何も行われないことを示す（サーバーはこのフィールドの値をクリア**しなければならず**（must）、入力時にこのフィールドに値が存在する結果としてエラーをスロー**してはならない**（must not））。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーの下位にあるメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常`Response`で終わるメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして記述**すべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの使用例として考えられるもの（これは網羅的なリストではない）：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ、変更できないリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして記述**すべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、createリクエスト上のフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在せず、フィールドへの変更がないことを示す場合に限り、フィールドを省略**してもよい**（may）（そうでない場合は提供**しなければならない**（must））。
- リクエストメッセージ（RPCの引数となるメッセージで、通常`Request`で終わる）上のフィールドである。この場合、リクエストの一部として値を提供**しなければならず**（must）、提供しない場合はエラー（通常`INVALID_ARGUMENT`）を発生させ**なければならない**（must）。

上記の「truthy」という用語を次のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false`以外の値
- repeatedフィールドおよびマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つ任意のメッセージ

以下のことを示すためにフィールドをrequiredとして記述**すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きでrequiredとなるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定の値と区別がつかないため、requiredフィールドをfalsyな値に設定するとエラーになる。このことの帰結として、requiredなブール値は`true`に設定されなければならない。

### Unordered List

リソースのrepeatedフィールドでの`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、順序なしリストとして記述**すべきである**（should）。

順序なしリストを持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`値の追加または変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味的変更を表す可能性がある。以下は`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前は`OPTIONAL`とみなされていた（暗黙的にかどうかを問わず）既存のフィールドに`REQUIRED`を追加する
* 既存のリクエストメッセージに`REQUIRED`としてアノテーションされた新しいフィールドを追加する
* 以前は入力として受け付けられていた既存のフィールドに`OUTPUT_ONLY`を追加する
* 以前は出力として出力されていた既存のフィールドに`INPUT_ONLY`を追加する
* 以前はmutableとみなされていた既存のフィールドに`IMMUTABLE`を追加する
* 以前は入力として無視されていた既存のフィールドから`OUTPUT_ONLY`を削除する
* 既存のフィールドから`IDENTIFIER`を削除する。

後方互換性が*ある*変更は以下の通り：

* 既存のフィールドに`OPTIONAL`を追加する
* 既存の`name`フィールドに`IDENTIFIER`を追加する
* 既存のフィールドで`REQUIRED`から`OPTIONAL`に変更する
* 既存のフィールドで`OUTPUT_ONLY`または`IMMUTABLE`（あるいはその両方）から`IDENTIFIER`に変更する
* 既存のフィールドから`REQUIRED`を削除する
* 以前はレスポンスで除外されていた既存のフィールドから`INPUT_ONLY`を削除する
* 以前はimmutableとみなされていた既存のフィールドから`IMMUTABLE`を削除する

## 根拠

### Identifierフィールド動作

リソース名は、準拠するリソースの主要識別子であり、作成時にユーザーによって完全に構築されることは決してない。このようなフィールドは通常`OUTPUT_ONLY`のフィールド動作が割り当てられる。しかし、リソース自体が主要なリクエストペイロードであるシナリオでは、主要識別子として消費されることも多い。このようなフィールドは`OUTPUT_ONLY`とはみなせ*ない*。さらに、標準Updateのような変更リクエストでは、主要識別子としてのリソース名はその場で変更できない。このようなフィールドは通常`IMMUTABLE`のフィールド動作が割り当てられる。これらの競合し文脈に依存するフィールド動作は、リソース名フィールドの動作を明確にし伝達するために新しい値が必要であることを意味した。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドはrequiredまたはoptionalのいずれかであり、したがってそれぞれ少なくとも`REQUIRED`または`OPTIONAL`アノテーションを持つべきである。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラマティックなクライアントとユーザーの理解を向上させる。

アノテーションを必須にすることは、API作成者がAPIの初期作成時に動作を明示的に検討することも強制する。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更が生じる可能性がある。例えば、optionalフィールドをrequiredにすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]内のリソースに後方互換性のない変更が生じる。詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須化された。この変更以前は、アノテーションが省略されることがよくあった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後に一部のfield_behavior値を追加または変更すると、後方互換性がなくなる可能性がある。詳細な互換性ガイダンスについては[後方互換性](#backwards-compatibility)セクションを参照。

API作成時にfield_behaviorを必須とするメリットは、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
