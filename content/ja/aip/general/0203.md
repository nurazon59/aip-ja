# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（必須かオプショナルかなど）をユーザーに説明するのが慣例である。さらに、他のツールがこの動作を理解することも有用である（例えば、クライアントライブラリのシグネチャを最適化するためなど）。

## ガイダンス

APIは、`google.api.field_behavior`アノテーションを使用して、フィールドが必須やimmutableであるなど、十分に理解されているフィールド動作を記述する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - この例外として、リソースメッセージ上のAIP-154の`etag`フィールドには、`google.api.field_behavior`を割り当て**るべきではない**（should not）。
  - さらに、`oneof`フィールドは`google.api.field_behavior`を省略**してもよい**（may）が、この場合、特定の動作をコメントに文書化する**べきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する[google.api.FieldBehavior][]の値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは最低限、`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作には影響しないが、多くのクライアント（例：CLIやSDK）はコード生成のためにこれらに依存している。新しいフィールドを追加する際には、どの値が関連するかを十分に確認し検討する。

アノテーションが付いていないフィールドは、後方互換性のため`OPTIONAL`と解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントに記載されている語彙は*説明的な*目的のみのものであり、それ自体は検証を追加するものではない。目的は、この動作をクライアント向けに一貫して文書化することである。

### ネストされたメッセージのfield behavior

ネストされたメッセージ上の`google.api.field_behavior`アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージは`REQUIRED`のフィールド動作を持ち、親フィールドは`OPTIONAL`であってもよい：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されている場合、`text`フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは`name`フィールドに付加**しなければならず**（must）、他のフィールドに付加**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、作成メソッドのコンテキストでは、フィールドが入力として受け付けられず（すなわち`OUTPUT_ONLY`）、同時に`IMMUTABLE`と見なされ、リソースを主要入力として受け付ける変更メソッド（例：[標準Update][aip-134]）では入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、必須またはオプショナルのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致すればそのフィールドを無視する**べきであり**（should）、変更が要求された場合は`INVALID_ARGUMENT`でエラーにする**べきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- アプリケーションのライフタイムにわたって変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件的にimmutable」なフィールドには、immutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールドまたはリソースメッセージ内に含まれるメッセージのフィールドである場合にのみ、input onlyとして記述する**べきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常は`Request`で終わる名前のメッセージ）内のフィールドは、これがすでに暗黙的であるため、input onlyとして記述する**べきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- AIP-214で説明されている`ttl`フィールド。

**警告:** input onlyフィールドはまれであり、使用前に慎重に検討する必要がある。

### Optional

`OPTIONAL`の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数として機能し、通常は`Request`で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合に、optionalとして記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル`optional`とフィールド動作`OPTIONAL`は相互に排他的ではない。詳細についてはAIP-149を参照。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにフィールドを含めても何も行われないことを示す（サーバーはこのフィールドの値をクリア**しなければならず**（must）、入力にこのフィールドの値が存在する結果としてエラーを投げ**てはならない**（must not））。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（AIP-161参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーのより深い位置にあるメッセージのフィールドである場合にのみ、output onlyとして記述する**べきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常は`Response`で終わるメッセージ）内のフィールドは、これがすでに暗黙的であるため、output onlyとして記述する**べきではない**（should not）。

output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）は：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- 変更できない、サービスによって割り当てられるリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソースに存在し（かつ空でない値に設定され）**なければならない**（must）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして記述する**べきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである場合。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでフィールドの値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在せず、フィールドへの変更がないことを示す場合に限り、フィールドを省略**してもよい**（may）（そうでない場合は提供**しなければならない**（must））。
- リクエストメッセージ（RPCの引数として機能し、通常は`Request`で終わる名前のメッセージ）上のフィールドである場合。この場合、リクエストの一部として値を提供**しなければならず**（must）、提供しない場合はエラー（通常は`INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト列、`false`以外の値
- 繰り返しフィールドとマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

以下のことを示すために、フィールドをrequiredとして記述する**べきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件的に必須となるフィールド。
- ユーザー入力として決して使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定値と区別がつかないため、requiredフィールドにfalsyな値を設定するとエラーになる。このことから、requiredなブール値は`true`に設定しなければならない。

### Unordered List

リソースの繰り返しフィールドでの`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、unordered listとして記述する**べきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`の値を追加または変更することは、既存のクライアントにとって互換性がないと認識されるAPIの意味的な変更を表す可能性がある。以下は、`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前に（暗黙的または明示的に）`OPTIONAL`と見なされていた既存のフィールドに`REQUIRED`を追加する
* 既存のリクエストメッセージに`REQUIRED`とアノテーションされた新しいフィールドを追加する
* 以前に入力として受け付けられていた既存のフィールドに`OUTPUT_ONLY`を追加する
* 以前に出力として出力されていた既存のフィールドに`INPUT_ONLY`を追加する
* 以前に可変と見なされていた既存のフィールドに`IMMUTABLE`を追加する
* 以前に入力として無視されていた既存のフィールドから`OUTPUT_ONLY`を削除する
* 既存のフィールドから`IDENTIFIER`を削除する。

後方互換性が*ある*変更もあり、以下の通りである：

* 既存のフィールドに`OPTIONAL`を追加する
* 既存の`name`フィールドに`IDENTIFIER`を追加する
* 既存のフィールドを`REQUIRED`から`OPTIONAL`に変更する
* 既存のフィールドを`OUTPUT_ONLY`や`IMMUTABLE`から`IDENTIFIER`に変更する
* 既存のフィールドから`REQUIRED`を削除する
* 以前にレスポンスで除外されていた既存のフィールドから`INPUT_ONLY`を削除する
* 以前にimmutableと見なされていた既存のフィールドから`IMMUTABLE`を削除する

## 根拠

### Identifierフィールド動作

リソース名は、あらゆる準拠リソースの主要識別子であり、作成時にユーザーが完全に構築することは決してない。このようなフィールドには通常`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、リソース自体が主要リクエストペイロードとなるシナリオでは、主要識別子として利用されることも多い。このようなフィールドは`OUTPUT_ONLY`と見なすことは*できなかった*。さらに、標準Updateのような変更リクエストでは、主要識別子としてのリソース名はその場で変更できない。このようなフィールドには通常`IMMUTABLE`フィールド動作が割り当てられる。これらの矛盾するコンテキスト依存のフィールド動作により、リソース名フィールドの動作を特定して伝達するための新しい値が必要になった。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドは必須かオプショナルのいずれかであり、したがって少なくともそれぞれ`REQUIRED`または`OPTIONAL`アノテーションを持つ**べきである**（should）。`INPUT_ONLY`だけを提供してもフィールドの必要性を伝えないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の必須化

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラムによるクライアントとユーザーの理解を向上させる。

アノテーションを必須にすることで、API作成者はAPIの初回作成時に動作を明示的に考慮することも強制される。

初回作成後にフィールド動作を変更すると、クライアントで後方互換性のない変更が生じる可能性がある。例えば、オプショナルフィールドを必須にすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須になった。この変更以前は、アノテーションが省略されることが多かった。その値は高品質のクライアントを生成するために信頼されている。さらに、メジャーバージョン内で事後に一部のfield_behavior値を追加または変更することは、後方互換性がない可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

API作成時にfield_behaviorを必須とすることの利点は、そうしない場合のクライアントとAPIユーザーへのコストを上回る。
