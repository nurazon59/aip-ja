# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する際、フィールドの動作に関する特定の側面（必須かオプショナルかなど）をユーザーに説明するのが通例である。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは、フィールドが必須やimmutableであるなど、よく理解されたフィールド動作を記述するために`google.api.field_behavior`アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - これに対する例外は、リソースメッセージ上のAIP-154の`etag`フィールドであり、これは`google.api.field_behavior`を割り当て**るべきではない**（should not）。
  - さらに、`oneof`フィールドは`google.api.field_behavior`を省略**してもよい**（may）が、この場合、コメントで特定の動作を**文書化すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する任意の[google.api.FieldBehavior][]値を**含めなければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは、最低でも`REQUIRED`、`OPTIONAL`、`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作には影響しないが、多くのクライアント（CLIやSDKなど）はこれらに依存してコードを生成する。新しいフィールドを追加する際は、どの値が関連するかを十分に確認し検討すること。

アノテーションがないフィールドは、後方互換性のため`OPTIONAL`として解釈される。それにもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は*記述的*な目的のみであり、それ自体はバリデーションを追加しない。その目的は、クライアントに対してこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の`google.api.field_behavior`アノテーションは、親のアノテーションとは独立している。

例えば、ネストされたメッセージが`REQUIRED`のフィールド動作を持ち、親フィールドが`OPTIONAL`である場合がある：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定されていれば、`text`フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースの識別に使用されることを示す。これは`name`フィールドに付加**されなければならず**（must）、他のフィールドに付加**してはならない**（must not）（[リソース名を表すフィールド][fields representing resource names]を参照）。

`IDENTIFIER`値は、そのフィールドが作成メソッドのコンテキストでは入力として受け付けられず（すなわち`OUTPUT_ONLY`）、同時に`IMMUTABLE`と見なされ、リソースを主要な入力として受け付ける変更メソッド（例：[標準Update][aip-134]）では入力として受け付けられることを伝える。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、必須またはオプショナルのいずれのフィールドにも適用できる。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受け取った場合、更新マスクに含まれていても、値が一致する場合はフィールドを無視**すべきである**（should）が、変更が要求された場合は`INVALID_ARGUMENT`で**エラーすべきである**（should）。

immutableフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- アプリケーションのライフタイム全体で変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドには、immutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**されるべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常`Request`で終わる名前を持つメッセージ）内のフィールドは、すでに暗黙的であるため、input onlyとして記述**されるべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- AIP-214で説明されている`ttl`フィールド。

**警告:** Input onlyフィールドはまれであり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドが必須でないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常`Request`で終わる名前を持つメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合に、optionalとして**記述してもよい**（may）。

**注:** フィールドプレゼンスラベル`optional`とフィールド動作`OPTIONAL`は相互排他的ではない。詳細はAIP-149を参照。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにフィールドを含めても何も行われない（サーバーはこのフィールドの値を**クリアしなければならず**（must）、入力に値が存在することによるエラーを**スローしてはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を**無視しなければならない**（must）（AIP-161参照）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーのさらに下位のメッセージのフィールドである場合にのみ、output onlyとして記述**されるべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常`Response`で終わる名前を持つメッセージ）内のフィールドは、すでに暗黙的であるため、output onlyとして記述**されるべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは網羅的なリストではない）：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- 変更できない、サービスによって割り当てられたリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソース上に**存在しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の*いずれか*の場合にのみrequiredとして記述**されるべきである**（should）：

- ユーザーが入力としてどこかで提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が*格納されている*場合にのみ有効である。
  - リソースを[作成][aip-133]する際、作成リクエストでフィールドに値が**提供されなければならない**（must）。
  - リソースを[更新][aip-134]する際、ユーザーはフィールドがフィールドマスクにも存在しない限りフィールドを**省略してもよい**（may）（フィールドに変更がないことを示す）。それ以外の場合は値が**提供されなければならない**（must）。
- リクエストメッセージ（RPCの引数であり、通常`Request`で終わる名前を持つメッセージ）上のフィールドである。この場合、リクエストの一部として値が**提供されなければならず**（must）、提供されなかった場合はエラー（通常`INVALID_ARGUMENT`）を**引き起こさなければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空の文字列/バイト、`false`以外の値
- repeatedフィールドおよびマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

以下を示すためにフィールドをrequiredとして記述**すべきではない**（should not）：

- 常にレスポンスに存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（ブール値の`false`、整数の`0`、enumの未指定値など）は未設定の値と区別がつかないため、requiredフィールドをfalsyな値に設定するとエラーになる。これの帰結として、requiredなブール値は`true`に設定**しなければならない**（must）。

### Unordered List

リソースのrepeatedフィールドでの`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスが要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、unordered listとして記述**されるべきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`値の追加や変更は、既存のクライアントにとって互換性がないと認識されるAPIの意味上の変更を表す可能性がある。以下は、`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前`OPTIONAL`（暗黙的か明示的かを問わず）と見なされていた既存のフィールドに`REQUIRED`を追加する
* 既存のリクエストメッセージに`REQUIRED`とアノテーションされた新しいフィールドを追加する
* 以前入力として受け付けられていた既存のフィールドに`OUTPUT_ONLY`を追加する
* 以前出力として生成されていた既存のフィールドに`INPUT_ONLY`を追加する
* 以前変更可能と見なされていた既存のフィールドに`IMMUTABLE`を追加する
* 以前入力として無視されていた既存のフィールドから`OUTPUT_ONLY`を削除する
* 既存のフィールドから`IDENTIFIER`を削除する。

後方互換性の*ある*変更もあり、以下の通りである：

* 既存のフィールドに`OPTIONAL`を追加する
* 既存の`name`フィールドに`IDENTIFIER`を追加する
* 既存のフィールドで`REQUIRED`から`OPTIONAL`に変更する
* 既存のフィールドで`OUTPUT_ONLY`および/または`IMMUTABLE`から`IDENTIFIER`に変更する
* 既存のフィールドから`REQUIRED`を削除する
* 以前レスポンスで除外されていた既存のフィールドから`INPUT_ONLY`を削除する
* 以前immutableと見なされていた既存のフィールドから`IMMUTABLE`を削除する

## 根拠

### Identifierフィールド動作

リソース名は、準拠するすべてのリソースの主要な識別子であり、作成時にユーザーによって完全に構築されることはない。そのようなフィールドは通常、`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、それらはリソース自体が主要なリクエストペイロードであるシナリオでも主要な識別子として消費されることが多い。そのようなフィールドは`OUTPUT_ONLY`とは見なせなかった。さらに、標準Updateのような変更リクエストでは、主要な識別子としてのリソース名はその場で変更できない。そのようなフィールドは通常、`IMMUTABLE`フィールド動作が割り当てられる。これらの矛盾しコンテキスト依存のフィールド動作は、リソース名フィールドの動作を特定し伝えるために新しい値が必要であることを意味した。

### 必須のアノテーションセット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドは必須かオプショナルのいずれかであり、したがって少なくともそれぞれ`REQUIRED`または`OPTIONAL`アノテーションを持つべきである。`INPUT_ONLY`のみを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の要求

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラマティッククライアントとユーザーの理解を向上させる。

アノテーションを要求することで、API作成者はAPIの初期作成時に動作を明示的に検討することも強制される。

初期作成後にフィールド動作を変更すると、クライアントに後方互換性のない変更をもたらす可能性がある。例えば、オプショナルフィールドを必須にすると、RPCのメソッドシグネチャや[宣言的クライアント][Declarative client]のリソースに後方互換性のない変更が生じる。詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

## 履歴

2023年5月にfield_behaviorが必須となった。この変更以前は、アノテーションが省略されることがよくあった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で事後に一部のfield_behavior値を追加または変更することは後方互換性がない可能性がある。詳細な互換性ガイダンスについては、[後方互換性](#後方互換性)セクションを参照。

API作成時にfield_behaviorを要求することの利点は、それをしない場合のクライアントやAPIユーザーへのコストを上回る。
