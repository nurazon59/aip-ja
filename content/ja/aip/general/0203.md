# フィールド動作のドキュメント化

Protocol Buffersでフィールドを定義する場合、フィールドの動作の特定の側面（requiredかoptionalかなど）をユーザーに説明することが慣例となっている。さらに、他のツールがこの動作を理解することは有用である（例えば、クライアントライブラリのシグネチャを最適化するため）。

## ガイダンス

APIは、フィールドがrequiredやimmutableであるといった、よく理解されたフィールドの動作を記述するために`google.api.field_behavior`アノテーションを使用する。

```proto
// The audio data to be recognized.
RecognitionAudio audio = 2 [(google.api.field_behavior) = REQUIRED];
```

- APIは、リクエストで使用されるメッセージまたはサブメッセージ上のすべてのフィールドに`google.api.field_behavior`アノテーションを適用**しなければならない**（must）。
  - この例外は、リソースメッセージ上のAIP-154の`etag`フィールドであり、これにはいかなる`google.api.field_behavior`も割り当て**るべきではない**（should not）。
  - さらに、`oneof`フィールドは`google.api.field_behavior`を省略**してもよい**（may）が、この場合、コメントに特定の動作を文書化**すべきである**（should）。
- アノテーションには、フィールドの動作を正確に記述する任意の[google.api.FieldBehavior][]値を含め**なければならない**（must）。
  - `FIELD_BEHAVIOR_UNSPECIFIED`を使用**してはならない**（must not）。
- APIは、最低限`REQUIRED`、`OPTIONAL`、または`OUTPUT_ONLY`のいずれかを使用**しなければならない**（must）。

**警告:** `field_behavior`はprotoレベルの動作には影響しないが、多くのクライアント（CLIやSDKなど）はコード生成にこれらに依存している。新しいフィールドを追加する際には、どの値が関連するかを徹底的に確認・検討すること。

アノテーションのないフィールドは、後方互換性のため`OPTIONAL`と解釈される。にもかかわらず、このアノテーションを省略**してはならない**（must not）。

**注:** このドキュメントで提供される語彙は_記述的_な目的のみのためのものであり、それ自体はバリデーションを追加するものではない。目的は、クライアントのためにこの動作を一貫して文書化することである。

### ネストされたメッセージのフィールド動作

ネストされたメッセージ上の`google.api.field_behavior`アノテーションは、親のアノテーションから独立している。

例えば、ネストされたメッセージは`REQUIRED`のフィールド動作を持ち、親フィールドは`OPTIONAL`であってもよい：

```proto
message Title {
  string text = 1 [(google.api.field_behavior) = REQUIRED];
}

message Slide {
  Title title = 1 [(google.api.field_behavior) = OPTIONAL];
}
```

上記の場合、`title`が指定された場合、`text`フィールドは必須である。

## 語彙

### Identifier

`IDENTIFIER`の使用は、リソースメッセージ内のフィールドがリソースを識別するために使用されることを示す。これは`name`フィールドに付加**しなければならず**（must）、他のいかなるフィールドにも付加**してはならない**（must not）（[フィールドによるリソース名の表現][fields representing resource names]を参照）。

`IDENTIFIER`値は、createメソッドのコンテキストでは、そのフィールドが入力として受け入れられない（すなわち`OUTPUT_ONLY`）ことを伝える一方で、リソースをプライマリ入力として受け取る変更メソッド（例：[標準Update][aip-134]）では`IMMUTABLE`と見なされ、入力として受け入れられる。

このアノテーションは、メッセージ内の他のリソースへの参照に適用**してはならない**（must not）。

### Immutable

`IMMUTABLE`の使用は、リソース上のフィールドが作成後に変更できないことを示す。これは、入力または出力、requiredまたはoptionalのフィールドのいずれにも適用され得る。

サービスが更新リクエスト（または類似のもの）でimmutableフィールドを受信した場合、更新マスクに含まれている場合でも、値が一致する場合はそのフィールドを無視**すべきである**（should）が、変更が要求された場合は`INVALID_ARGUMENT`でエラーと**すべきである**（should）。

immutableフィールドの潜在的なユースケース（これは完全なリストではない）は以下の通り：

- アプリケーションのライフタイムにわたって変更できないリソースの属性（例：ディスクタイプ）。

**注:** 「条件付きでimmutable」なフィールドにimmutableアノテーションを付与**してはならない**（must not）。

### Input only

`INPUT_ONLY`の使用は、フィールドがリクエストで提供され、対応するフィールドが出力に含まれないことを示す。

さらに、フィールドは、リソースメッセージ内のフィールド、またはリソースメッセージに含まれるメッセージのフィールドである場合にのみ、input onlyとして記述**すべきである**（should）。特に、リクエストメッセージ（RPCの引数としてのみ機能し、通常`Request`で終わる名前を持つメッセージ）内のフィールドは、これが既に暗黙的であるため、input onlyとして記述**すべきではない**（should not）。

input onlyフィールドの潜在的なユースケース（これは完全なリストではない）は以下の通り：

- AIP-214で説明されている`ttl`フィールド。

**警告:** Input onlyフィールドは稀であり、使用前に慎重に検討すべきである。

### Optional

`OPTIONAL`の使用は、フィールドが必須ではないことを示す。

フィールドは、リクエストメッセージ（RPCの引数であり、通常`Request`で終わるメッセージ）上のフィールド、またはサブメッセージ上のフィールドである場合、optionalとして記述**してもよい**（may）。

**注:** フィールドプレゼンスラベル`optional`とフィールド動作`OPTIONAL`は相互排他的ではない。詳細はAIP-149を参照。

### Output only

`OUTPUT_ONLY`の使用は、フィールドがレスポンスで提供されるが、リクエスト内のメッセージにそのフィールドを含めても何も行われない（サーバーはこのフィールドの値をすべてクリア**しなければならず**（must）、入力時にこのフィールドに値が存在する結果としてエラーをスロー**してはならない**（must not））ことを示す。同様に、サービスは更新フィールドマスク内のoutput onlyフィールドの存在を無視**しなければならない**（must）（参照：AIP-161）。

さらに、フィールドは、リソースメッセージ内のフィールド、またはツリーのより下位にあるメッセージのフィールドである場合にのみ、output onlyとして記述**すべきである**（should）。特に、レスポンスメッセージ（RPCの戻り値としてのみ機能し、通常`Response`で終わるメッセージ）内のフィールドは、これが既に暗黙的であるため、output onlyとして記述**すべきではない**（should not）。

Output onlyフィールドは、APIにとって適切であれば、空の値に設定**してもよい**（may）。

output onlyフィールドの潜在的なユースケース（これは完全なリストではない）は以下の通り：

- 作成または更新のタイムスタンプ。
- 元のユーザー入力に基づく派生情報または構造化情報。
- サービスによって割り当てられ変更できないリソースのプロパティ。

### Required

`REQUIRED`の使用は、フィールドがリクエストまたはリソース上に存在**しなければならず**（must）（かつ空でない値に設定されなければならない）ことを示す。

フィールドは、以下の_いずれか_の場合にのみ、requiredとして記述**すべきである**（should）：

- ユーザーがどこかで入力として提供するリソース上のフィールドである。この場合、リソースは「truthy」な値が_保存された_場合にのみ有効である。
  - リソースを[作成][aip-133]する際、createリクエスト上でそのフィールドに値を提供**しなければならない**（must）。
  - リソースを[更新][aip-134]する際、フィールドがフィールドマスクからも除外されており、フィールドに変更がないことを示している場合、ユーザーはそのフィールドを省略**してもよい**（may）（それ以外の場合は提供**しなければならない**（must））。
- リクエストメッセージ（RPCの引数であり、通常`Request`で終わる名前を持つメッセージ）上のフィールドである。この場合、リクエストの一部として値を提供**しなければならず**（must）、そうしない場合はエラー（通常`INVALID_ARGUMENT`）を引き起こさ**なければならない**（must）。

上記の「truthy」という用語を以下のように定義する：

- プリミティブの場合、`0`、`0.0`、空文字列/空バイト、および`false`以外の値
- repeatedフィールドおよびマップの場合、少なくとも1つのエントリを持つ値
- メッセージの場合、少なくとも1つの「truthy」なフィールドを持つメッセージ

以下のことを示すために、フィールドをrequiredとして記述**すべきではない**（should not）：

- レスポンスに常に存在するフィールド。
- 状況によって条件付きで必須となるフィールド。
- ユーザー入力として決して使用されないメッセージ（リソースであるメッセージを含む）上のフィールド。

**注:** ほとんどの場合、空の値（booleanの`false`、整数の`0`、enumの未指定値など）は未設定の値と区別がつかないため、requiredフィールドにfalsyな値を設定するとエラーになる。この帰結として、required booleanは`true`に設定しなければならない。

### Unordered List

リソースのrepeatedフィールドに対する`UNORDERED_LIST`の使用は、サービスがリスト内の項目の順序を保証しないことを示す。

フィールドは、サービスがリスト内の要素の順序がユーザーが送信した順序と一致することを保証しない場合（サービスがユーザーに代わってリストをソートする状況を含む）、unordered listとして記述**すべきである**（should）。

unordered listを持つリソースは、リストを安定した順序で返し**てもよい**（may）し、ランダム化された不安定な順序で返し**てもよい**（may）。

## 後方互換性

`google.api.field_behavior`値の追加や変更は、既存のクライアントにとって非互換と認識されるAPIのセマンティックな変更を表す可能性がある。以下は、`google.api.field_behavior`に関する後方互換性のない変更の例である：

* 以前に（暗黙的または明示的に）`OPTIONAL`と見なされていた既存のフィールドに`REQUIRED`を追加すること
* 既存のリクエストメッセージに`REQUIRED`とアノテーションされた新しいフィールドを追加すること
* 以前に入力として受け入れられていた既存のフィールドに`OUTPUT_ONLY`を追加すること
* 以前に出力として発行されていた既存のフィールドに`INPUT_ONLY`を追加すること
* 以前にmutableと見なされていた既存のフィールドに`IMMUTABLE`を追加すること
* 以前に入力として無視されていた既存のフィールドから`OUTPUT_ONLY`を削除すること
* 既存のフィールドから`IDENTIFIER`を削除すること

後方互換性が_ある_変更もいくつかあり、以下の通りである：

* 既存のフィールドに`OPTIONAL`を追加すること
* 既存の`name`フィールドに`IDENTIFIER`を追加すること
* 既存のフィールドで`REQUIRED`から`OPTIONAL`に変更すること
* 既存のフィールドで`OUTPUT_ONLY`または`IMMUTABLE`、あるいはその両方から`IDENTIFIER`に変更すること
* 既存のフィールドから`REQUIRED`を削除すること
* 以前にレスポンスで除外されていた既存のフィールドから`INPUT_ONLY`を削除すること
* 以前にimmutableと見なされていた既存のフィールドから`IMMUTABLE`を削除すること

## 理論的根拠

### Identifierフィールド動作

リソース名（任意の準拠リソースのプライマリ識別子）は、作成時にユーザーによって完全に構築されることは決してない。そのようなフィールドは通常`OUTPUT_ONLY`フィールド動作が割り当てられる。しかし、リソース自体がプライマリリクエストペイロードであるシナリオでは、プライマリ識別子としても使用されることが多い。そのようなフィールドは`OUTPUT_ONLY`と見なすことは_できなかった_。さらに、標準Updateなどの変更リクエストでは、プライマリ識別子としてのリソース名はその場で変更できない。そのようなフィールドは通常`IMMUTABLE`フィールド動作が割り当てられる。これらの矛盾しコンテキストに依存するフィールド動作は、リソース名フィールドの動作を特定して伝えるために新しい値が必要であることを意味していた。

### アノテーションの必須セット

リクエストメッセージで使用されるフィールドは、入力または出力のいずれかでなければならない。

出力の場合、`OUTPUT_ONLY`アノテーションで十分である。

入力の場合、フィールドはrequiredまたはoptionalのいずれかであり、したがってそれぞれ少なくとも`REQUIRED`または`OPTIONAL`アノテーションを持つべきである。`INPUT_ONLY`だけを提供してもフィールドの必要性は伝わらないため、`REQUIRED`または`OPTIONAL`のいずれかを指定することが依然として必要である。

### フィールド動作の要求

各フィールドにフィールド動作アノテーションを含めることで、リソースが示す全体的な動作がより明確に定義される。明確に定義されたフィールド動作は、プログラム的なクライアントとユーザーの理解を向上させる。

アノテーションを要求することは、APIの初期設計時にAPI作成者が動作を明示的に検討することも強制する。

初期設計後にフィールド動作を変更すると、クライアントに後方互換性のない変更が生じる可能性がある。例えば、optionalフィールドをrequiredにすると、[宣言的クライアント][Declarative client]におけるRPCのメソッドシグネチャやリソースに後方互換性のない変更が生じる。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

## 履歴

2023-05にfield_behaviorが必須化された。この変更以前は、アノテーションが省略されることが多かった。その値は高品質なクライアントを生成するために依存されている。さらに、メジャーバージョン内で後から一部のfield_behavior値を追加または変更すると、後方互換性がなくなる可能性がある。より詳細な互換性ガイダンスについては、[後方互換性](#backwards-compatibility)セクションを参照。

APIの作成時にfield_behaviorを要求することの利点は、そうしないことによるクライアントとAPIユーザーへのコストを上回る。
