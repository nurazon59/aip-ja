# カスタム メソッド

リソース指向設計（AIP-121）では、標準メソッドだけではモデル化が難しい任意のアクションを表現する手段としてカスタム メソッドを使用する。カスタム メソッドは、APIの語彙がユーザーの意図に沿う手段を提供するため重要である。

## ガイダンス

カスタム メソッドは、標準メソッドでは容易に表現できない機能にのみ使用**すべきである**（should）。可能であれば、一貫したセマンティクスを持つ標準メソッドを優先する。（もちろん、これは対象の機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドを「なんとか機能させる」ために無理にねじ曲げるのは良い考えでは_ない_。）

カスタム メソッドの設計方法は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して動作するカスタム メソッドを示している。カスタム メソッドは、リソース、コレクション、またはサービスに関連付けることができる。以下の箇条書きは3つのケースすべてに適用される。

- メソッドの名前は、動詞に名詞が続く形と**すべきである**（should）。
  - 名前には前置詞（"for"、"with"など）を含め**てはならない**（must not）。
  - 名前の動詞には、標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）を含める**べきではない**（should not）。
  - 名前には `Async` という用語を含め**てはならない**（must not）。代わりに、即時RPCとlong-running RPCを区別することが目的である場合、この目的のために接尾辞 `LongRunning` を使用**してもよい**（may）。例えば、long-runningな書籍作成RPCを作成する場合（標準の `CreateBook` メソッドがlong-runningの側面を考慮する前に設計された場合）、カスタム `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` で**なければならない**（must）：
  - `GET` は、データやリソースの状態を取得するメソッドに使用**しなければならない**（must）。
    - リクエストペイロードがURLサイズの制限を超える可能性があり、`body` が必要になる場合、データ取得メソッドに `POST` を使用**してもよい**（may）。
  - メソッドに副作用がある場合、またはリソースやデータを変更する場合は、`POST` を使用**しなければならない**（must）。
- HTTP URIでは、カスタム動詞の前に `:` 文字を使用**しなければならず**（must）（上記の例では `:archive`）、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` と**すべきである**（should）。
  - 詳細については [HTTP and gRPC Transcoding][transcoding] を参照。
- カスタム メソッドは、RPC名に一致し `Request` サフィックスを付けたリクエストメッセージを受け取る**べきである**（should）。
- カスタム メソッドは、RPC名に一致し `Response` サフィックスを付けたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して動作する場合、カスタム メソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタム メソッド

APIをリソースとしてモデル化できる場合、カスタム メソッドはリソースに対して動作**しなければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と呼称**しなければならず**（must）、URIパス内の唯一の変数で**なければならない**（must）。

### コレクションベースのカスタム メソッド

ほとんどのカスタム メソッドは単一のリソースに対して動作するが、一部のカスタム メソッドは代わりにコレクションに対して動作**してもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは `parent` と呼称**しなければならず**（must）、URIパス内の唯一の変数で**なければならない**（must）。
- コレクションキー（上記の例では `books`）はリテラルで**なければならない**（must）。

### ステートレス メソッド

一部のカスタム メソッドは、リソースにまったく関連付けられない。これらのメソッドは一般に_ステートレス_である。リクエストを受け取りレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例ではプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名はスコープリソースの名前と**すべきである**（should）。単語の区切りが必要な場合は、`snake_case` を使用**しなければならない**（must）。
- URIでは、動詞と名詞の両方を `:` セパレータの後に配置**すべきである**（should）（この場合、コレクションが存在しないため、URI内の「疑似コレクションキー」は避ける）。例えば、`text:translate` よりも `:translateText` が望ましい。
- ステートレス メソッドは、課金を伴う場合に `POST` を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは通常、カスタム メソッドを使用**すべきではない**（should not）（他のAIPで説明されている特定の宣言的フレンドリーなカスタム メソッドを除く）。なぜなら、宣言的フレンドリーなツールはそれらに対して何をすべきかを自動的に判断できないためである。

この例外は、めったに使用されない根本的に命令型の操作（`Move` や `Rename` 操作など）であり、これらには宣言的サポートの期待がない。

## 根拠

### HTTP パス

標準メソッドと同様に、リソースまたはコレクションに対して動作するカスタム メソッドは、操作対象のリソースを示すために `name` または `parent` パラメータを必要とする。この規則により、クライアントはカスタム メソッドを適切なリソースにマッピングできる。

### HTTP メソッド

`GET` と `POST` の両方のHTTP動詞を許可することで、データを変更しないメソッドと変更するメソッドを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformのDataSources）で第一級の概念を持ち、実行時の影響リスクなしに呼び出せるメソッドをユーザーに明確に示す。

他の方法では `GET` を使用するリクエストに `POST` を使用できるようにすることは、以下の利便性のためである：

- 大きなクエリ文字列がURLサイズ制限に違反するリクエストを引き起こすのを回避する。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できるようにする。または、少なくともrepeatedフィールドなどの複雑なルールを実装する必要を回避する。
- 通常はシンプルなRPCでも、クエリパラメータでは表現できない可能性のあるデータを複雑な状況のために含めることを可能にする。

### 前置詞の禁止

一般に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべきところで新しいメソッドを使用しているか、またはそのメソッドが異なる動詞を使用すべきであることを示している。例えば、`CreateBook` メッセージがすでに存在し、`CreateBookFromDictation` の追加を検討している場合、代わりに `TranscribeBook` メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合は、`GetBookByAuthor` の代わりに、検索ディメンションとして `author` フィールドを持つ `SearchBooks` を検討する。これにより、APIとクライアントサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを加える過剰に特化したメソッドの爆発的な増加を防ぐことができる。

### RPC 名

"async"という用語は、RPCの作成を含め、特定のメソッド呼び出しが同期か非同期かを示すためにプログラミング言語で一般的に使用される。その同期/非同期の側面は、RPC自体がlong-running operationを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名自体に"async"を使用すると混乱を招き、一部の言語ではRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成するクライアントライブラリに問題を引き起こす可能性さえある。
