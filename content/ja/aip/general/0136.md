# カスタム メソッド

リソース指向設計（AIP-121）は、標準メソッドだけではモデル化が難しい任意のアクションを表現する手段として、カスタム メソッドを使用する。カスタム メソッドが重要な理由は、APIの語彙がユーザーの意図に沿うための手段を提供するからである。

## ガイダンス

カスタム メソッドは、標準メソッドでは容易に表現できない機能に対してのみ使用**すべきである**（should）。一貫したセマンティクスを持つ標準メソッドを可能な限り優先する。（もちろん、これは対象の機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドが「なんとか動く」ようにするために無理に捻じ曲げるのは良い考えでは*ない*。）

カスタム メソッドの設計は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタム メソッドを示している。カスタム メソッドは、リソース、コレクション、またはサービスに関連付けることができる。以下の箇条書きは3つのケースすべてに適用される。

- メソッドの名前は、動詞に名詞が続く形式に**すべきである**（should）。
  - 名前に前置詞（「for」「with」など）を含めて**はならない**（must not）。
  - 名前に含まれる動詞は、標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）を含め**てはならない**（must not）。
  - 名前に`Async`という語を含めて**はならない**（must not）。代わりに、即時RPCとlong-running RPCを区別する場合は、その目的でサフィックス`LongRunning`を使用**してもよい**（may）。例えば、long-runningの書庫作成RPCを作成する場合（標準の`CreateBook`メソッドがlong-runningの側面が考慮される前に設計された場合）、カスタムの`CreateBookLongRunning`メソッドを導入できる。
- HTTPメソッドは`GET`または`POST`**でなければならない**（must）：
  - データやリソースの状態を取得するメソッドでは`GET`を使**わなければならない**（must）。
    - リクエストペイロードがURLサイズ制限を超え、`body`を必要とする可能性がある場合、データ取得メソッドに`POST`を使用**してもよい**（may）。
  - 副作用がある場合やリソースやデータを変更する場合は`POST`を使**わなければならない**（must）。
- HTTP URIでは、`:`文字に続けてカスタム動詞（上記の例では`:archive`）を**使用しなければならず**（must）、URI内の動詞はRPCの名前の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は`camelCase`を**使用しなければならない**（must）。
- `google.api.http`アノテーションの`body`節は`"*"`に**すべきである**（should）。
  - 詳細については[HTTPとgRPCトランスコーディング][transcoding]を参照。
- カスタム メソッドは、RPC名に`Request`サフィックスを付けたリクエストメッセージを受け取る**べきである**（should）。
- カスタム メソッドは、RPC名に`Response`サフィックスを付けたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作を行う場合、カスタム メソッドはリソース自体を返し**てもよい**（may）。

### リソースベースのカスタム メソッド

APIをリソースとしてモデル化できる場合、カスタム メソッドはリソースに対して操作を行**わなければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは`name`と呼ば**なければならず**（must）、URIパス内の唯一の変数**でなければならない**（must）。

### コレクションベースのカスタム メソッド

ほとんどのカスタム メソッドは単一のリソースに対して操作を行うが、一部のカスタム メソッドは代わりにコレクションに対して操作を行っ**てもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは`parent`と呼ば**れなければならず**（must）、URIパス内の唯一の変数**でなければならない**（must）。
- コレクションキー（上記の例では`books`）はリテラル**でなければならない**（must）。

### ステートレス メソッド

一部のカスタム メソッドは、リソースにまったく関連付けられていない。これらのメソッドは一般に*ステートレス*である：リクエストを受け取り、レスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例ではプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名はスコープリソースの名前に**すべきである**（should）。単語の区切りが必要な場合は`snake_case`を**使用しなければならない**（must）。
- URIでは、動詞と名詞の両方を`:`区切りの後に配置**すべきである**（should）（この場合、コレクションが存在しないため、URIに「疑似コレクションキー」を含めないようにする）。例えば、`:translateText`は`text:translate`より好ましい。
- ステートレス メソッドは、課金を伴う場合`POST`を**使用しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは、通常カスタム メソッドを採用**すべきではない**（should not）（他のAIPで説明されている特定の宣言的フレンドリーなカスタム メソッドを除く）。宣言的フレンドリーなツールは、それらをどう扱うべきかを自動的に判断できないためである。

この例外は、`Move`や`Rename`操作のように、めったに使用されず本質的に命令型の操作であり、宣言的サポートが期待されない場合である。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースまたはコレクションに対して操作を行うカスタム メソッドは、操作対象のリソースを示す`name`または`parent`パラメータを必要とする。この規約により、クライアントはカスタム メソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET`と`POST`の両方のHTTP動詞を許可することで、データを変更しないメソッドと変更するメソッドを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformのDataSources）で第一級の概念となり、ユーザーに対してどのメソッドがランタイムに影響を与えるリスクなしに呼び出せるかを明確に示す。

他の方法では`GET`で行われるリクエストに`POST`の使用を許可することは、以下の便宜のためである：

- URLサイズ制限に違反するリクエストにつながる大きなクエリ文字列を回避する。
- クライアントがリクエストデータをシリアル化する単一の方法を実装できるようにする。または少なくとも、繰り返しフィールドなどのための複雑なルールを実装しなければならない状況を回避する。
- 通常は単純なRPCであっても、クエリパラメータでは表現できない可能性のあるデータを複雑な状況のために含められるようにする。

### 前置詞の禁止

一般に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべき場合や、別の動詞を使用すべき場合に新しいメソッドを使用していることを示す。例えば、`CreateBook`メッセージが既に存在し、`CreateBookFromDictation`の追加を検討している場合、代わりに`TranscribeBook`メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合、`GetBookByAuthor`の代わりに、検索ディメンションとして`author`フィールドを持つ`SearchBooks`を検討する。これは、APIとクライアントサーフェスを肥大化させ、APIの管理と消費の両方に複雑さを加える、過度に特化したメソッドの爆発を防ぐのに役立つ。

### RPC名

「async」という用語は、RPCの作成を含め、特定のメソッド呼び出しが同期か非同期かを示すためにプログラミング言語で一般的に使用される。その同期/非同期の側面は、RPC自体がlong-running operationの開始を意図しているかどうかとは異なる抽象レベルにある。RPC名自体に「async」を使用すると混乱を引き起こし、一部の言語でRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成するクライアント ライブラリに問題さえ引き起こす可能性がある。
