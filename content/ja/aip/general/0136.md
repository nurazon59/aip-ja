# カスタムメソッド

リソース指向設計（AIP-121）は、標準メソッドだけではモデル化が困難な任意の
アクションを表現する手段として、カスタムメソッドを使用する。カスタムメソッドは、
APIの語彙がユーザーの意図に沿う手段を提供するため重要である。

## ガイダンス

カスタムメソッドは、標準メソッドでは容易に表現できない機能に対してのみ使用
**すべきである**（should）。その一貫したセマンティクスのため、可能であれば標準
メソッドを優先する。（もちろん、これは問題の機能が実際に通常のセマンティクスに
適合する場合にのみ適用される。標準メソッドが「なんとか動作する」ように無理に
ねじ曲げるのは良い考えでは_ない_。）

カスタムメソッドの設計方法は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタムメソッドを
示している。カスタムメソッドは、リソース、コレクション、またはサービスに関連
付けることができる。以下の箇条書きはこれら3つのケースすべてに適用される。

- メソッド名は動詞に名詞を続けたもの**にすべきである**（should）。
  - 名前に前置詞（"for"、"with" など）を含ん**ではならない**（must not）。
  - 名前に含まれる動詞は、標準メソッドの動詞（[Get][]、[List][]、[Create][]、
    [Update][]、[Delete][]）を含ん**ではならない**（should not）。
  - 名前に `Async` という語を含ん**ではならない**（must not）。代わりに、
    即時RPCと長時間実行RPCを区別する意図がある場合、`LongRunning` サフィックスを
    この目的で使用**してもよい**（may）。例えば、長時間実行の書籍作成RPCを
    作成する場合（標準の `CreateBook` メソッドが長時間実行の側面を考慮する前に
    設計された場合）、カスタムの `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` **でなければならない**（must）：
  - データまたはリソースの状態を取得するメソッドには `GET` を使用
    **しなければならない**（must）。
    - リクエストペイロードがURLサイズの制限を超える可能性があり、`body` が
      必要な場合、データ取得メソッドに `POST` を使用**してもよい**（may）。
  - メソッドに副作用がある場合、またはリソースやデータを変更する場合は、
    `POST` を使用**しなければならない**（must）。
- HTTP URIでは、カスタム動詞の前に `:` 文字を使用**しなければならず**（must）
  （上記の例では `:archive`）、URI内の動詞はRPCの名前に含まれる動詞と一致
  **しなければならない**（must）。
  - 単語の区切りが必要な場合、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` **にすべきである**
  （should）。
  - 詳細については [HTTP と gRPC Transcoding][transcoding] を参照。
- カスタムメソッドは、RPC名に `Request` サフィックスを付けたリクエスト
  メッセージを受け取る**べきである**（should）。
- カスタムメソッドは、RPC名に `Response` サフィックスを付けたレスポンス
  メッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作を行う場合、カスタムメソッドはリソース自体を
    返し**てもよい**（may）。


### リソースベースのカスタムメソッド

APIをリソース指向でモデル化できる場合、カスタムメソッドはリソースに対して
操作を行わ**なければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と呼ば**なければならず**（must）、URIパス
  の唯一の変数**でなければならない**（must）。

### コレクションベースのカスタムメソッド

ほとんどのカスタムメソッドは単一のリソースに対して操作を行うが、一部の
カスタムメソッドは代わりにコレクションに対して操作を行っ**てもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは `parent` と呼ば
  **なければならず**（must）、URIパスの唯一の変数**でなければならない**
  （must）。
- コレクションキー（上記の例では `books`）はリテラル**でなければならない**
  （must）。

### ステートレスメソッド

一部のカスタムメソッドは、リソースにまったく結び付いていない。これらの
メソッドは一般に_ステートレス_である：リクエストを受け取りレスポンスを返し、
API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例のようにプロジェクトなど）で実行される
  場合、リクエストメッセージ内のフィールド名はスコープリソースの名前に
  **すべきである**（should）。単語の区切りが必要な場合、`snake_case` を使用
  **しなければならない**（must）。
- URIでは、動詞と名詞の両方を `:` セパレータの後に配置**すべきである**
  （should）（この場合、コレクションが存在しないため、URIに「疑似コレクション
  キー」を置くことを避ける）。例えば、`:translateText` は `text:translate` より
  望ましい。
- 課金を伴う場合、ステートレスメソッドは `POST` を使用**しなければならない**
  （must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは通常、カスタムメソッドを使用**すべきではない**
（should not）（他のAIPで説明されている特定の宣言的フレンドリーなカスタム
メソッドを除く）。宣言的フレンドリーなツールは、それらをどう処理すべきか
自動的に判断できないためである。

これに対する例外は、`Move` や `Rename` 操作のような、ほとんど使用されない
基本的に命令的な操作であり、宣言的サポートの期待がないものである。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースまたはコレクションに対して操作を行うカスタム
メソッドは、操作対象のリソースを示す `name` または `parent` パラメータを
必要とする。この慣習により、クライアントはカスタムメソッドを適切なリソースに
マッピングできる。

### HTTPメソッド

`GET` と `POST` の両方のHTTP動詞を許可することで、データを変更しないメソッドと
変更するメソッドを明確に区別できる。データの読み取りのみを行うメソッドは、
一部のクライアント（TerraformのDataSources）で第一級の概念として扱われ、
ランタイムへの影響リスクなしにどのメソッドを呼び出せるかをユーザーに明確に
示す。

通常 `GET` で行われるリクエストに `POST` を使用できるのは利便性のためである：

- URLサイズ制限に違反する大きなクエリ文字列を避けられる。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できるか、
  少なくともrepeatedフィールドなどの複雑なルールを実装する必要がなくなる。
- 通常は単純なRPCでも、クエリパラメータで表現できない複雑な状況のデータを
  含められる。

### 前置詞の禁止

一般に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべき
ところで新しいメソッドを使用しているか、メソッドに別の動詞を使用すべき
ことを示している。例えば、`CreateBook` メッセージが既に存在し、
`CreateBookFromDictation` の追加を検討している場合、代わりに `TranscribeBook`
メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合は、
`GetBookByAuthor` の代わりに、検索次元として `author` フィールドを持つ
`SearchBooks` を検討する。これは、APIとクライアントサーフェスを肥大化させ、
APIの管理と利用の両方に複雑さを加える過度に特化したメソッドの爆発的増加を
防ぐのに役立つ。

### RPC名

「async」という用語は、RPCの作成を含め、特定のメソッド呼び出しが同期的か
非同期的かを示すためにプログラミング言語で一般的に使用される。その同期/非同期の
側面は、RPC自体が長時間実行操作を開始することを意図しているかどうかとは
異なる抽象化レベルにある。RPC名自体に「async」を使用すると混乱を招き、
一部の言語でRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成する
クライアントライブラリに問題を引き起こす可能性さえある。
