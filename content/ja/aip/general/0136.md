# カスタム メソッド

リソース指向設計（AIP-121）では、標準メソッドだけではモデル化が難しい任意のアクションを表現する手段としてカスタム メソッドを使用する。カスタム メソッドは、APIの語彙がユーザーの意図に沿う手段を提供するため重要である。

## ガイダンス

カスタム メソッドは、標準メソッドでは容易に表現できない機能にのみ使用**すべきである**（should）。標準メソッドが一貫したセマンティクスを持つため、可能であれば標準メソッドを優先する。（もちろん、これは問題となる機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドを「なんとか機能させる」ために物事を歪曲するのは _良くない_ 考えである。）

カスタム メソッドの設計方法は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタム メソッドを示している。カスタム メソッドはリソース、コレクション、またはサービスに関連付けることができる。以下の箇条書きは3つのケースすべてに適用される。

- メソッド名は動詞の後に名詞が続く形に**すべきである**（should）。
  - メソッド名に前置詞（"for"、"with" など）を含め**てはならない**（must not）。
  - メソッド名の動詞は標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）を含ん**ではならない**（should not）。
  - メソッド名に `Async` を含め**てはならない**（must not）。代わりに、即時RPCとlong-running RPCを区別する意図がある場合、この目的のためにサフィックス `LongRunning` を使用**してもよい**（may）。例えば、long-runningな書籍作成RPCを作成する場合（標準の `CreateBook` メソッドがlong-runningの側面が考慮される前に設計されていた場合）、カスタム `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` で**なければならない**（must）：
  - `GET` はデータまたはリソースの状態を取得するメソッドに使用**しなければならない**（must）。
    - リクエストペイロードがURLサイズの制限を超える可能性があり、`body` が必要となる場合、データ取得メソッドに `POST` を使用**してもよい**（may）。
  - `POST` はメソッドが副作用を持つか、リソースやデータを変更する場合に使用**しなければならない**（must）。
- HTTP URI は `:` 文字に続けてカスタム動詞（上記の例では `:archive`）を使用**しなければならない**（must）。また、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` に**すべきである**（should）。
  - 詳細については [HTTP and gRPC Transcoding][transcoding] を参照。
- カスタム メソッドは、RPC名に一致し、`Request` サフィックスを持つリクエストメッセージを受け取る**べきである**（should）。
- カスタム メソッドは、RPC名に一致し、`Response` サフィックスを持つレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作を行う場合、カスタム メソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタム メソッド

APIがそのようにモデル化できる場合、カスタム メソッドはリソースに対して操作**しなければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と呼ばれ**なければならず**（must）、URIパス内の唯一の変数でなければならない。

### コレクションベースのカスタム メソッド

ほとんどのカスタム メソッドは単一のリソースに対して操作を行うが、一部のカスタム メソッドは代わりにコレクションに対して操作を行っ**てもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースが親を持つ場合、そのリソースは `parent` と呼ばれ**なければならず**（must）、URIパス内の唯一の変数でなければならない。
- コレクションキー（上記の例では `books`）はリテラルで**なければならない**（must）。

### ステートレスメソッド

一部のカスタム メソッドはリソースにまったく結びついていない。これらのメソッドは一般に _ステートレス_ である。つまり、リクエストを受け取りレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例ではプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名はそのスコープリソースの名前に**すべきである**（should）。単語の区切りが必要な場合は、`snake_case` を使用**しなければならない**（must）。
- URI は `:` 区切りの後に動詞と名詞の両方を配置**すべきである**（should）（この場合、コレクションが存在しないため、URI内に「疑似コレクションキー」を使用しないこと）。例えば、`:translateText` は `text:translate` よりも望ましい。
- ステートレスメソッドは、課金を伴う場合に `POST` を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは通常、カスタム メソッドを使用**すべきではない**（should not）（他のAIPで議論されている特定の宣言的フレンドリーなカスタム メソッドを除く）。なぜなら、宣言的フレンドリーなツールはそれらに対して自動的に何をすべきかを判断できないからである。

この例外は、`Move` や `Rename` 操作のような、ほとんど使用されず本質的に命令的な操作であり、宣言的サポートの期待がないものである。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースまたはコレクションに対して操作を行うカスタム メソッドは、操作対象のリソースを示すために `name` または `parent` パラメータを必要とする。この規約により、クライアントはカスタム メソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET` と `POST` の両方のHTTP動詞を許可することで、どのメソッドがデータを変更せず、どのメソッドが変更するかを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformのDataSources）で第一級の概念として扱われ、実行時の影響リスクなしに呼び出せるメソッドをユーザーに明確に示す。

通常は `GET` を使用するリクエストに `POST` を使用できるようにすることは便宜である：

- 大きなクエリ文字列によってURLサイズの制限に違反するリクエストを回避できる。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できるようになる。少なくとも、繰り返しフィールドなどの複雑なルールを実装する必要がなくなる。
- 通常は単純なRPCでも、クエリパラメータで表現できない可能性がある複雑な状況のためにデータを含むことができる。

### 前置詞の禁止

一般的に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべきところで新しいメソッドが使われているか、またはメソッドが別の動詞を使用すべきであることを示す。例えば、`CreateBook` メッセージが既に存在し、`CreateBookFromDictation` の追加を検討している場合、代わりに `TranscribeBook` メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合、`GetBookByAuthor` の代わりに `author` フィールドを検索ディメンションとする `SearchBooks` を検討する。これにより、APIとクライアントのサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを加える過度に特化したメソッドの爆発的増加を防ぐことができる。

### RPC名

「async」という用語は、プログラミング言語で特定のメソッド呼び出しが同期的か非同期的かを示すために一般的に使用されており、RPCの実行にも使われる。そのsync/asyncの側面は、RPC自体がlong-running operationを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名自体に「async」を使用すると混乱を招き、一部の言語でRPCを呼び出すために同期メソッドと非同期メソッドの両方を生成するクライアントライブラリに問題を引き起こす可能性さえある。
