# カスタム メソッド

リソース指向（resource-oriented）設計（AIP-121）では、カスタム メソッドを用いて標準メソッドだけではモデル化が難しい任意のアクションを表現する手段を提供する。カスタム メソッドは、APIの語彙がユーザー意図に準拠する手段を提供するため重要である。

## ガイダンス

カスタム メソッドは、標準メソッドでは容易に表現できない機能に対してのみ使用**すべきである**（should）。一貫したセマンティクスがあるため、可能であれば標準メソッドを優先する。（もちろん、これは問題の機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドを「なんとか動作させる」ために無理に適合させるのは良い考えでは _ない_。）

カスタム メソッドの設計方法は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して動作するカスタム メソッドを示している。カスタム メソッドはリソース、コレクション、またはサービスに関連付けることができる。以下の各項目は、3つのケースすべてに適用される。

- メソッド名は、動詞の後に名詞が続く形式と**すべきである**（should）。
  - メソッド名に前置詞（"for"、"with"など）を含めて**はならない**（must not）。
  - メソッド名の動詞には、標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）を含め**るべきではない**（should not）。
  - メソッド名に `Async` という用語を含めて**はならない**（must not）。代わりに、即時RPCとlong-running operationを区別する意図がある場合、接尾辞 `LongRunning` をこの目的で使用**してもよい**（may）。例えば、long-runningな書籍作成RPCを作成する場合（標準の `CreateBook` メソッドがlong-runningの側面が検討される前に設計されていた場合）、カスタムの `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` **でなければならない**（must）：
  - `GET` はデータまたはリソース状態を取得するメソッドに使用**しなければならない**（must）。
    - `POST` は、リクエストペイロードがURLサイズ制限を超える可能性があり `body` が必要な場合、データ取得メソッドに使用**してもよい**（may）。
  - `POST` は、メソッドに副作用がある場合やリソースまたはデータを変更する場合に使用**しなければならない**（must）。
- HTTP URIは `:` 文字の後にカスタム動詞を続ける形式（上記の例では `:archive`）を**使用しなければならず**（must）、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` と**すべきである**（should）。
  - 詳細については [HTTPとgRPCのトランスコーディング][transcoding] を参照。
- カスタム メソッドは、RPC名に `Request` 接尾辞を付けたリクエストメッセージを受け取る**べきである**（should）。
- カスタム メソッドは、RPC名に `Response` 接尾辞を付けたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して動作する場合、カスタム メソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタム メソッド

APIとしてモデル化できる場合、カスタム メソッドはリソースに対して動作**しなければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と呼ぶ**必要があり**（must）、URIパス内の唯一の変数**でなければならない**（must）。

### コレクションベースのカスタム メソッド

ほとんどのカスタム メソッドは単一のリソースに対して動作するが、一部のカスタム メソッドは代わりにコレクションに対して動作**してもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは `parent` と呼ぶ**必要があり**（must）、URIパス内の唯一の変数**でなければならない**（must）。
- コレクションキー（上記の例では `books`）はリテラル**でなければならない**（must）。

### ステートレスメソッド

一部のカスタム メソッドはリソースにまったく関連付けられていない。これらのメソッドは一般に*ステートレス*である：リクエストを受け取りレスポンスを返し、API内のデータに対して永続的な効果を持たない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例のプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名はスコープリソースの名前と**すべきである**（should）。単語の区切りが必要な場合は、`snake_case` を使用**しなければならない**（must）。
- URIは `:` セパレータの後に動詞と名詞の両方を配置**すべきである**（should）（この場合、コレクションが存在しないため、URIに「疑似コレクションキー」を置くのは避ける）。例えば、`text:translate` よりも `:translateText` が好ましい。
- ステートレスメソッドは、課金を伴う場合 `POST` を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリー（Declarative-friendly）なリソースは通常、カスタム メソッドを使用**すべきではない**（should not）（他のAIPで説明されている特定の宣言的フレンドリー向けカスタム メソッドを除く）。宣言的フレンドリーツールは、それらをどのように処理するかを自動的に判断できないためである。

これに対する例外は、`Move` や `Rename` 操作のような、めったに使用されず本質的に命令型の操作であり、宣言的サポートの期待がないものである。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースまたはコレクションに対して動作するカスタム メソッドは、操作対象のリソースを示すために `name` または `parent` パラメータが必要である。この規則により、クライアントはカスタム メソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET` と `POST` の両方のHTTP動詞を許可することで、どのメソッドがデータを変更せず、どのメソッドが変更するかを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformにおけるDataSources）で第一級の概念を持ち、ランタイムに影響を与えるリスクなしに呼び出せるメソッドをユーザーに明確に示す。

通常 `GET` で行われるリクエストに `POST` を使用できるようにすることは便宜的なものである：

- URLサイズ制限に違反する大きなクエリ文字列を回避できる。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できるようになるか、少なくとも繰り返しフィールドなどに対する複雑なルールを実装する必要を回避できる。
- 通常は単純なRPCでも、クエリパラメータでは表現できないデータを含む複雑な状況に対応できる。

### 前置詞の禁止

一般的に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべき場合や、メソッドが異なる動詞を使用すべき場合に新しいメソッドが使用されていることを示す。例えば、`CreateBook` メッセージが既に存在し、`CreateBookFromDictation` の追加を検討している場合、代わりに `TranscribeBook` メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合、`GetBookByAuthor` の代わりに、検索ディメンションとして `author` フィールドを持つ `SearchBooks` を検討する。これにより、APIとクライアントサーフェスを肥大化させ、APIの管理と消費の両方に複雑さを追加する過剰に焦点化されたメソッドの爆発的な増加を防ぐことができる。

### RPC名

"async" という用語は、プログラミング言語で特定のメソッド呼び出しが同期的か非同期的か（RPCの作成を含む）を示すために一般的に使用される。その同期/非同期の側面は、RPC自体がlong-running operationを開始することを意図しているかどうかとは異なる抽象レベルにある。RPC名自体に "async" を使用すると混乱を招き、一部の言語でRPCを呼び出すために同期メソッドと非同期メソッドの両方を生成するクライアント ライブラリで問題を引き起こす可能性さえある。
