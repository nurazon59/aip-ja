# カスタム メソッド

リソース指向設計（AIP-121）では、標準メソッドだけではモデル化が難しい任意のアクションを表現する手段として、カスタム メソッドを使用する。カスタム メソッドは、APIの語彙をユーザーの意図に適合させる手段を提供するため重要である。

## ガイダンス

カスタム メソッドは、標準メソッドでは容易に表現できない機能にのみ使用**すべきである**（should）。可能であれば、一貫したセマンティクスを持つ標準メソッドを優先すること。（もちろん、これは対象の機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドを「なんとか動作させる」ために物事を歪めるのは良い考えで_はない_。）

カスタム メソッドの設計方法は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタム メソッドを示している。カスタム メソッドは、リソース、コレクション、サービスのいずれにも関連付けることができる。以下の箇条書きは3つのケースすべてに適用される。

- メソッド名は、動詞の後に名詞が続く形と**すべきである**（should）。
  - 名前に前置詞（"for"、"with"など）を含め**てはならない**（must not）。
  - 名前に含まれる動詞に、標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）を含め**るべきではない**（should not）。
  - 名前に `Async` という語を含め**てはならない**（must not）。代わりに、即時RPCとlong-running RPCを区別する目的であれば、接尾辞 `LongRunning` をこの目的で使用**してもよい**（may）。たとえば、long-runningな書籍作成RPCを作成する場合（long-runningの側面が考慮される前に標準の `CreateBook` メソッドが設計されていた場合）、カスタムの `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` で**なければならない**（must）：
  - データやリソースの状態を取得するメソッドには `GET` を使用**しなければならない**（must）。
    - リクエストペイロードがURLサイズの制限を超える可能性があり、`body` が必要となるデータ取得メソッドには `POST` を使用**してもよい**（may）。
  - メソッドに副作用がある場合や、リソースやデータを変更する場合は `POST` を使用**しなければならない**（must）。
- HTTP URIには、カスタム動詞の前に `:` 文字を使用**しなければならず**（must）（上記の例では `:archive`）、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` と**すべきである**（should）。
  - 詳細については [HTTP and gRPC Transcoding][transcoding] を参照すること。
- カスタム メソッドは、RPC名に一致し `Request` 接尾辞を持つリクエストメッセージを受け取る**べきである**（should）。
- カスタム メソッドは、RPC名に一致し `Response` 接尾辞を持つレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作を行う場合、カスタム メソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタム メソッド

カスタム メソッドは、APIがそのようにモデル化できる場合、リソースに対して操作を行わ**なければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と命名**しなければならず**（must）、URIパス内の唯一の変数で**なければならない**（must）。

### コレクションベースのカスタム メソッド

ほとんどのカスタム メソッドは単一のリソースに対して操作を行うが、一部のカスタム メソッドは代わりにコレクションに対して操作を行っ**てもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは `parent` と命名**しなければならず**（must）、URIパス内の唯一の変数で**なければならない**（must）。
- コレクションキー（上記の例では `books`）はリテラルで**なければならない**（must）。

### ステートレスメソッド

一部のカスタム メソッドは、リソースにまったく関連付けられていない。これらのメソッドは一般に_ステートレス_である。つまり、リクエストを受け取ってレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例のプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名はスコープリソースの名前と**すべきである**（should）。単語の区切りが必要な場合は、`snake_case` を使用**しなければならない**（must）。
- URIは、動詞と名詞の両方を `:` 区切り文字の後に配置**すべきである**（should）（この場合、コレクションが存在しないため、URI内の「偽のコレクションキー」を避けること）。たとえば、`text:translate` よりも `:translateText` が望ましい。
- ステートレスメソッドは、課金を伴う場合に `POST` を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは、通常、カスタム メソッドを使用**すべきではない**（should not）（他のAIPで説明されている特定の宣言的フレンドリーなカスタム メソッドを除く）。宣言的フレンドリーなツールは、それらをどう処理すべきか自動的に判断できないためである。

この例外は、`Move` や `Rename` 操作のような、めったに使用されない本質的に命令的な操作であり、宣言的サポートが期待されないものである。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースやコレクションに対して操作を行うカスタム メソッドには、操作対象のリソースを示すために `name` または `parent` パラメータが必要である。この規則により、クライアントはカスタム メソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET` と `POST` の両方のHTTP動詞を許可することで、どのメソッドがデータを変更せず、どのメソッドが変更するかを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアントでファーストクラスの概念（TerraformのDataSources）を持ち、実行時の影響リスクなしにどのメソッドを呼び出せるかをユーザーに明確に示す。

`GET` で行うはずのリクエストに `POST` を使用することを許可するのは、便宜上の措置である：

- 大きなクエリ文字列がURLサイズの制限に違反するリクエストにつながるのを回避できる。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できるか、少なくともrepeatedフィールドなどの複雑なルールを実装する必要を回避できる。
- 通常はシンプルなRPCでも、クエリパラメータでは表現できない可能性のあるデータを複雑な状況のために含めることができる。

### 前置詞の禁止

一般的に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべき箇所で新しいメソッドを使用しているか、またはメソッドが別の動詞を使用すべきであることを示す。たとえば、`CreateBook` メッセージがすでに存在し、`CreateBookFromDictation` の追加を検討している場合は、代わりに `TranscribeBook` メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合は、`GetBookByAuthor` の代わりに、検索軸として `author` フィールドを持つ `SearchBooks` を検討する。これにより、APIおよびクライアントサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを追加する、過度に特化したメソッドの爆発的増加を防ぐことができる。

### RPC名

「async」という用語は、RPCの実行を含め、特定のメソッド呼び出しが同期的か非同期的かを示すためにプログラミング言語で一般的に使用される。この同期/非同期の側面は、RPC自体がlong-running operationを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名に「async」を使用すると混乱を招き、一部の言語ではRPCを呼び出すために同期メソッドと非同期メソッドの両方を生成するクライアントライブラリに問題を引き起こす可能性さえある。
