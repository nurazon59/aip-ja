# カスタムメソッド

リソース指向設計（AIP-121）では、標準メソッドだけではモデル化が難しい任意のアクションを表現する手段として、カスタムメソッドを使用する。カスタムメソッドは、APIの語彙がユーザーの意図に沿う手段を提供するため、重要である。

## ガイダンス

カスタムメソッドは、標準メソッドでは容易に表現できない機能に対してのみ使用**すべきである**（should）。一貫したセマンティクスを持つ標準メソッドを可能な限り優先すること。（もちろん、これは問題の機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドを「なんとか動作させる」ために物事を歪めるのは良い考えでは _ない_。）

カスタムメソッドの設計方法は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタムメソッドを示している。カスタムメソッドは、リソース、コレクション、サービスのいずれにも関連付けることができる。以下の箇条書きは3つのケースすべてに適用される。

- メソッド名は、動詞の後に名詞を続けたものと**すべきである**（should）。
  - 名前に前置詞（"for"、"with"など）を含め**てはならない**（must not）。
  - 名前に含まれる動詞は、標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）のいずれも含む**べきではない**（should not）。
  - 名前に `Async` という語を含め**てはならない**（must not）。代わりに、即時RPCとlong-running RPCを区別する目的であれば、接尾辞 `LongRunning` をこの目的で使用**してもよい**（may）。例えば、long-runningな書籍作成RPCを作成する場合（標準の `CreateBook` メソッドがlong-runningの側面を考慮する前に設計されていた場合）、カスタムの `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` で**なければならない**（must）：
  - データやリソースの状態を取得するメソッドには `GET` を使用**しなければならない**（must）。
    - リクエストペイロードがURLサイズの制限を超える可能性があり、`body` が必要となる場合は、データ取得メソッドに `POST` を使用**してもよい**（may）。
  - メソッドに副作用がある場合、またはリソースやデータを変更する場合は、`POST` を使用**しなければならない**（must）。
- HTTP URI は `:` 文字に続けてカスタム動詞（上記の例では `:archive`）を使用**しなければならず**（must）、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` と**すべきである**（should）。
  - 詳細については [HTTPとgRPCトランスコーディング][transcoding] を参照。
- カスタムメソッドは、RPC名に一致し、`Request` 接尾辞が付いたリクエストメッセージを受け取る**べきである**（should）。
- カスタムメソッドは、RPC名に一致し、`Response` 接尾辞が付いたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作を行う場合、カスタムメソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタムメソッド

APIがそのようにモデル化できる場合、カスタムメソッドはリソースに対して操作**しなければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と呼ば**なければならず**（must）、URIパス内の唯一の変数で**なければならない**（must）。

### コレクションベースのカスタムメソッド

ほとんどのカスタムメソッドは単一のリソースに対して操作を行うが、一部のカスタムメソッドは代わりにコレクションに対して操作を行っ**てもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは `parent` と呼ば**なければならず**（must）、URIパス内の唯一の変数で**なければならない**（must）。
- コレクションキー（上記の例では `books`）はリテラルで**なければならない**（must）。

### ステートレスメソッド

一部のカスタムメソッドは、リソースにまったく関連付けられない。これらのメソッドは一般に _ステートレス_ である。つまり、リクエストを受け取ってレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例ではプロジェクトなど）で実行される場合、リクエストメッセージのフィールド名はスコープリソースの名前と**すべきである**（should）。単語の区切りが必要な場合は、`snake_case` を使用**しなければならない**（must）。
- URI は動詞と名詞の両方を `:` 区切り文字の後に配置**すべきである**（should）（この場合、コレクションが存在しないため、URI内の「疑似的なコレクションキー」を避ける）。例えば、`text:translate` よりも `:translateText` が望ましい。
- ステートレスメソッドは、課金を伴う場合に `POST` を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは通常、カスタムメソッドを使用**すべきではない**（should not）（他のAIPで説明されている特定の宣言的フレンドリーなカスタムメソッドを除く）。なぜなら、宣言的フレンドリーなツールはそれらをどう処理すべきか自動的に判断できないためである。

この例外として、`Move` や `Rename` 操作など、ほとんど使用されず、本質的に命令的な操作があり、これらには宣言的サポートの期待はない。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースやコレクションに対して操作を行うカスタムメソッドは、操作対象のリソースを示すために `name` または `parent` パラメータを必要とする。この規則により、クライアントはカスタムメソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET` と `POST` の両方のHTTPメソッドを許可することで、どのメソッドがデータを変更せず、どのメソッドが変更するかを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformのDataSources）で第一級の概念を持ち、どのメソッドが実行時の影響リスクなしに呼び出せるかをユーザーに明確に示す。

通常であれば `GET` を使用するリクエストに `POST` の使用を許可することは、以下の利便性を提供する：

- 大きなクエリ文字列が原因でURLサイズ制限に違反するリクエストを回避できる。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できるようにする。少なくとも、repeatedフィールドなどの複雑なルールを実装する必要がなくなる。
- 通常は単純なRPCであっても、クエリパラメータでは表現できないデータを複雑な状況のために含めることができる。

### 前置詞の禁止

一般に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべきところで新しいメソッドが使用されているか、メソッドが別の動詞を使用すべきであることを示している。例えば、`CreateBook` メッセージが既に存在し、`CreateBookFromDictation` の追加を検討している場合、代わりに `TranscribeBook` メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合、`GetBookByAuthor` の代わりに、検索ディメンションとして `author` フィールドを持つ `SearchBooks` を検討する。これにより、APIとクライアントのサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを加える、過度に特化したメソッドの爆発的な増加を防ぐことができる。

### RPC名

"async"という用語は、RPCの呼び出しを含め、特定のメソッド呼び出しが同期か非同期かを示すためにプログラミング言語で一般的に使用されている。その同期／非同期の側面は、RPC自体がlong-running operationを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名自体に"async"を使用することは混乱を招き、一部の言語ではRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成するクライアントライブラリに問題を引き起こす可能性さえある。
