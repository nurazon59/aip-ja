# カスタムメソッド

リソース指向設計（AIP-121）では、カスタムメソッドを使用して、標準メソッドだけではモデル化が難しい任意のアクションを表現する手段を提供する。カスタムメソッドは、APIの語彙がユーザーの意図に沿うための手段を提供するため、重要である。

## ガイダンス

カスタムメソッドは、標準メソッドでは容易に表現できない機能に対してのみ使用**すべきである**（should）。一貫したセマンティクスを持つ標準メソッドが可能な場合は、そちらを優先すること。（もちろん、これは対象の機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドを「なんとか機能させる」ために物事を歪めるのは良い考えでは*ない*。）

カスタムメソッドの設計は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタムメソッドを示している。カスタムメソッドは、リソース、コレクション、またはサービスに関連付けることができる。以下の箇条書きは、3つのケースすべてに適用される。

- メソッドの名前は、動詞の後に名詞を続けたものと**すべきである**（should）。
  - 名前に前置詞（"for"、"with"など）を含め**てはならない**（must not）。
  - 名前の動詞に標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）を含め**るべきではない**（should not）。
  - 名前に`Async`という語を含め**てはならない**（must not）。代わりに、即時RPCと長時間実行RPCを区別する目的であれば、サフィックス`LongRunning`を使用**してもよい**（may）。例えば、標準の`CreateBook`メソッドが長時間実行の側面を考慮する前に設計されていた場合に、長時間実行の書籍作成RPCを作成するには、カスタムの`CreateBookLongRunning`メソッドを導入できる。
- HTTPメソッドは`GET`または`POST`**でなければならない**（must）：
  - `GET`は、データやリソースの状態を取得するメソッドに使用**しなければならない**（must）。
    - `POST`は、リクエストペイロードがURLサイズの制限を超える可能性があり、そのために`body`が必要な場合、データ取得メソッドに使用**してもよい**（may）。
  - `POST`は、メソッドに副作用がある場合やリソースやデータを変更する場合に使用**しなければならない**（must）。
- HTTP URIは、`:`文字の後にカスタム動詞（上記の例では`:archive`）を続け**なければならず**（must）、URI内の動詞はRPCの名前の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase`を使用**しなければならない**（must）。
- `google.api.http`アノテーションの`body`句は`"*"`と**すべきである**（should）。
  - 詳細については[HTTP and gRPC Transcoding][transcoding]を参照。
- カスタムメソッドは、RPC名に`Request`サフィックスを付けたリクエストメッセージを受け取る**べきである**（should）。
- カスタムメソッドは、RPC名に`Response`サフィックスを付けたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作を行う場合、カスタムメソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタムメソッド

APIがそのようにモデル化できる場合、カスタムメソッドはリソースに対して操作**しなければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは`name`と呼ば**なければならず**（must）、URIパス内の唯一の変数でなければならない。

### コレクションベースのカスタムメソッド

ほとんどのカスタムメソッドは単一のリソースに対して操作を行うが、一部のカスタムメソッドは代わりにコレクションに対して操作を**してもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは`parent`と呼ば**れなければならず**（must）、URIパス内の唯一の変数でなければならない。
- コレクションキー（上記の例では`books`）はリテラル**でなければならない**（must）。

### ステートレスメソッド

一部のカスタムメソッドは、リソースにまったく関連付けられない。これらのメソッドは一般に*ステートレス*である：リクエストを受け取りレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例のようにプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名はスコープリソースの名前と**すべきである**（should）。単語の区切りが必要な場合は、`snake_case`を使用**しなければならない**（must）。
- URIは、`:`区切りの後に動詞と名詞の両方を配置**すべきである**（この場合、コレクションが存在しないため、URIに「疑似的なコレクションキー」を使わないこと）。例えば、`:translateText`は`text:translate`よりも好ましい。
- ステートレスメソッドは、課金を伴う場合、`POST`を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは、通常、カスタムメソッドを使用**すべきではない**（should）（他のAIPで説明されている特定の宣言的フレンドリーなカスタムメソッドを除く）。宣言的フレンドリーなツールは、それらをどう扱うべきかを自動的に判断できないためである。

これに対する例外は、`Move`や`Rename`操作のような、めったに使用されない根本的に命令型の操作であり、これらには宣言的サポートの期待がない。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースやコレクションに対して操作を行うカスタムメソッドは、操作対象のリソースを示す`name`または`parent`パラメータを必要とする。この規則により、クライアントはカスタムメソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET`と`POST`の両方のHTTP動詞を許可することで、データを変更しないメソッドと変更するメソッドを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformのDataSources）において第一級の概念を持ち、実行時の影響のリスクなしに呼び出せるメソッドをユーザーに明確に示す。

`POST`を、そうでなければ`GET`で行われるリクエストに使用できることは利便性である：

- URLサイズ制限に違反するリクエストにつながる大きなクエリ文字列を回避できる。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できる、あるいは少なくともrepeatedフィールドなどの複雑なルールを実装する必要を回避できる。
- 通常は単純なRPCであっても、クエリパラメータでは表現できない可能性のあるデータを複雑な状況で含められる。

### 前置詞の禁止

一般に、前置詞を含むメソッド名は、新しいメソッドが使用されているが、代わりに既存のメソッドにフィールドを追加すべきか、あるいはメソッドが別の動詞を使用すべきであることを示している。例えば、`CreateBook`メッセージがすでに存在し、`CreateBookFromDictation`の追加を検討している場合は、代わりに`TranscribeBook`メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合は、`GetBookByAuthor`の代わりに、検索ディメンションとして`author`フィールドを持つ`SearchBooks`を検討する。これにより、APIとクライアントサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを加える、過度に特化したメソッドの爆発的な増加を防ぐことができる。

### RPC名

「async」という用語は、RPCの作成を含め、特定のメソッド呼び出しが同期的か非同期的かを示すためにプログラミング言語で一般的に使用されている。この同期/非同期の側面は、RPC自体が長時間実行オペレーションを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名自体に「async」を使用すると混乱を招き、一部の言語でRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成するクライアントライブラリで問題を引き起こす可能性さえある。
