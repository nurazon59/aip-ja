# カスタムメソッド

リソース指向設計（AIP-121）では、標準メソッドだけではモデル化が難しい任意のアクションを表現する手段としてカスタムメソッドを使用する。カスタムメソッドは、APIの語彙をユーザーの意図に沿わせる手段を提供するため重要である。

## ガイダンス

カスタムメソッドは、標準メソッドでは容易に表現できない機能にのみ使用**すべきである**（should）。可能であれば、一貫したセマンティクスを持つ標準メソッドを優先すること。（もちろん、これは問題の機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドを「なんとか動作させる」ために無理に捻じ曲げるのは良い考えで*はない*。）

カスタムメソッドの設計は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタムメソッドを示している。カスタムメソッドはリソース、コレクション、またはサービスに関連付けることができる。以下の箇条書きは3つのケースすべてに適用される。

- メソッド名は動詞の後に名詞を続けたものに**すべきである**（should）。
  - 名前に前置詞（"for"、"with"など）を含めて**はならない**（must not）。
  - 名前の動詞に標準メソッド動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）を含め**てはならない**（must not）。
  - 名前に `Async` という用語を含めて**はならない**（must not）。代わりに、即時RPCとlong-running RPCを区別する意図がある場合、この目的のために `LongRunning` という接尾辞を使用**してもよい**（may）。例えば、long-runningな書籍作成RPCを作成する場合（標準の `CreateBook` メソッドがlong-runningの側面を考慮する前に設計されていた場合）、カスタムの `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` **でなければならない**（must）：
  - `GET` はデータやリソース状態を取得するメソッドに使用**しなければならない**（must）。
    - リクエストペイロードがURLサイズ制限を超える可能性があり、そのために `body` が必要な場合、データ取得メソッドに `POST` を使用**してもよい**（may）。
  - `POST` は、メソッドに副作用がある場合やリソースやデータを変更する場合に使用**しなければならない**（must）。
- HTTP URIは `:` 文字の後にカスタム動詞（上記の例では `:archive`）を続けたものを使用**しなければならず**（must）、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` と**すべきである**（should）。
  - 詳細については [HTTP and gRPC Transcoding][transcoding] を参照。
- カスタムメソッドは、RPC名に `Request` 接尾辞を付けたリクエストメッセージを受け取る**べきである**（should）。
- カスタムメソッドは、RPC名に `Response` 接尾辞を付けたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作を行う場合、カスタムメソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタムメソッド

APIがそのようにモデル化できる場合、カスタムメソッドはリソースに対して操作**しなければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と**呼ばなければならず**（must）、URIパス内の唯一の変数で**なければならない**（must）。

### コレクションベースのカスタムメソッド

ほとんどのカスタムメソッドは単一のリソースに対して操作を行うが、一部のカスタムメソッドは代わりにコレクションに対して操作を**行ってもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは `parent` と**呼ばなければならず**（must）、URIパス内の唯一の変数で**なければならない**（must）。
- コレクションキー（上記の例では `books`）はリテラル**でなければならない**（must）。

### ステートレスメソッド

一部のカスタムメソッドはリソースにまったく関連付けられていない。これらのメソッドは一般的に*ステートレス*である：リクエストを受け取りレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例のプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名はスコープリソースの名前に**すべきである**（should）。単語の区切りが必要な場合は、`snake_case` を使用**しなければならない**（must）。
- URIは `:` セパレータの後に動詞と名詞の両方を配置**すべきである**（should）（この場合、コレクションが存在しないため、URI内の「擬似コレクションキー」を避ける）。例えば、`:translateText` は `text:translate` よりも好ましい。
- ステートレスメソッドは、課金を伴う場合 `POST` を使用**しなければならない**（must）。

### 宣言的クライアント向けリソース

宣言的クライアント向けリソースは通常、カスタムメソッドを使用**すべきではない**（should not）（他のAIPで説明されている特定の宣言的クライアント向けカスタムメソッドを除く）。なぜなら、宣言的クライアント向けツールはそれらをどう処理すべきかを自動的に判断できないからである。

この例外は、`Move` や `Rename` 操作のような、ほとんど使用されず本質的に命令的な操作であり、宣言的サポートが期待されない場合である。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースまたはコレクションに対して操作を行うカスタムメソッドには、操作対象のリソースを示す `name` または `parent` パラメータが必要である。この規約により、クライアントはカスタムメソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET` と `POST` の両方のHTTP動詞を許可することで、データを変更しないメソッドと変更するメソッドを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformのDataSourcesなど）で第一級の概念を持ち、ランタイムへの影響リスクなしにどのメソッドを呼び出せるかをユーザーに明確に示す。

そうでなければ `GET` で行われるリクエストに `POST` を使用できるようにすることは便宜上の措置である：

- URLサイズ制限に違反するリクエストにつながる大きなクエリ文字列を回避できる。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できるようにするか、少なくともrepeatedフィールドなどの複雑なルールを実装する必要を回避できる。
- 通常は単純なRPCでも、データがクエリパラメータで表現できない複雑な状況に対応するためのデータを含めることができる。

### 前置詞の禁止

一般に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべきところで新しいメソッドが使用されているか、またはメソッドに別個の動詞を使用すべきであることを示している。例えば、`CreateBook` メッセージが既に存在し、`CreateBookFromDictation` の追加を検討している場合、代わりに `TranscribeBook` メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合、`GetBookByAuthor` の代わりに、検索ディメンションとして `author` フィールドを持つ `SearchBooks` を検討する。これにより、APIとクライアントサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを加える過度に特化したメソッドの爆発的増加を防ぐことができる。

### RPC名

「async」という用語は、RPCの実行を含め、特定のメソッド呼び出しが同期的か非同期的かを示すためにプログラミング言語で一般的に使用されている。その同期的/非同期的側面は、RPC自体がlong-running operationを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名自体に「async」を使用すると混乱を招き、一部の言語でRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成するクライアントライブラリで問題を引き起こす可能性さえある。
