# カスタムメソッド

リソース指向設計（AIP-121）では、標準メソッドのみでモデル化することが困難な任意のアクションを表現する手段としてカスタムメソッドを使用する。カスタムメソッドは、APIの語彙がユーザーの意図に沿うための手段を提供するため重要である。

## ガイダンス

カスタムメソッドは、標準メソッドでは容易に表現できない機能に対してのみ使用**すべきである**（should）。標準メソッドの方が一貫したセマンティクスを持つため、可能であれば標準メソッドを優先する。（もちろん、これは問題の機能が実際に通常のセマンティクスに適合する場合にのみ当てはまる。標準メソッドを「なんとか機能させる」ために物事を捻じ曲げるのは良い考えでは _ない_。）

カスタムメソッドの設計方法は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタムメソッドを示している。カスタムメソッドはリソース、コレクション、またはサービスに関連付けることができる。以下の箇条書きは3つのケースすべてに適用される。

- メソッドの名前は、動詞に続けて名詞を置いたものに**すべきである**（should）。
  - 名前に前置詞（「for」、「with」など）を含め**てはならない**（must not）。
  - 名前に含まれる動詞は、標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）のいずれも含め**てはならない**（must not）。
  - 名前に `Async` という用語を含め**てはならない**（must not）。代わりに、即時RPCとlong-running RPCを区別する意図がある場合は、その目的のために `LongRunning` というサフィックスを使用**してもよい**（may）。例えば、標準の `CreateBook` メソッドがlong-runningの側面が考慮される前に設計されていた場合、long-runningな書籍作成RPCを作成するために、カスタムの `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` で**なければならない**（must）：
  - `GET` は、データやリソースの状態を取得するメソッドに使用**しなければならない**（must）。
    - リクエストペイロードがURLサイズ制限を超える可能性があり、そのために `body` が必要な場合、データ取得メソッドに `POST` を使用**してもよい**（may）。
  - メソッドが副作用を持つ場合や、リソースやデータを変更する場合は、`POST` を使用**しなければならない**（must）。
- HTTP URIは、カスタム動詞の前に `:` 文字を使用し（上記の例では `:archive`）、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` に**すべきである**（should）。
  - 詳細については [HTTPとgRPCトランスコーディング][transcoding] を参照。
- カスタムメソッドは、RPC名に `Request` サフィックスを付けたリクエストメッセージを受け取る**べきである**（should）。
- カスタムメソッドは、RPC名に `Response` サフィックスを付けたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作を行う場合、カスタムメソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタムメソッド

APIがそのようにモデル化できる場合、カスタムメソッドはリソースに対して操作を行わ**なければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と呼ば**なければならず**（must）、URIパス内の唯一の変数でなければならない。

### コレクションベースのカスタムメソッド

ほとんどのカスタムメソッドは単一のリソースに対して操作を行うが、一部のカスタムメソッドは代わりにコレクションに対して操作を行っ**てもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは `parent` と呼ば**れなければならず**（must）、URIパス内の唯一の変数でなければならない。
- コレクションキー（上記の例では `books`）はリテラルで**なければならない**（must）。

### ステートレスメソッド

一部のカスタムメソッドは、リソースに全く関連付けられない。これらのメソッドは一般的に _ステートレス_ である：リクエストを受け取りレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例のようにプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名は、そのスコープリソースの名前に**すべきである**（should）。単語の区切りが必要な場合は、`snake_case` を使用**しなければならない**（must）。
- URIは、動詞と名詞の両方を `:` 区切りの後に配置**すべきである**（should）（この場合、コレクションが存在しないため、URI内の「疑似コレクションキー」を避ける）。例えば、`:translateText` は `text:translate` よりも望ましい。
- ステートレスメソッドで課金を伴う場合は、`POST` を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは通常、カスタムメソッドを使用**すべきではない**（should not）（他のAIPで説明されている特定の宣言的フレンドリーなカスタムメソッドを除く）。なぜなら、宣言的フレンドリーなツールはそれらをどう扱うべきかを自動的に判断できないためである。

この例外は、`Move` や `Rename` 操作のような、めったに使用されない基本的に命令的な操作であり、宣言的サポートの期待がない場合である。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースやコレクションに対して操作を行うカスタムメソッドは、操作対象のリソースを示すための `name` または `parent` パラメータを必要とする。この規則により、クライアントはカスタムメソッドを適切なリソースに対応付けることができる。

### HTTPメソッド

`GET` と `POST` の両方のHTTP動詞を許可することで、どのメソッドがデータを変更せず、どのメソッドが変更するかを明確に区別できる。データを読み取るだけのメソッドは、一部のクライアント（TerraformにおけるDataSources）において第一級の概念を持ち、どのメソッドが実行時の影響のリスクなしに呼び出せるかをユーザーに明確に示す。

他の方法では `GET` を使用するリクエストに対して `POST` の使用を許可することは、便宜上の措置である：

- 大きなクエリ文字列がURLサイズ制限に違反するリクエストを引き起こすのを回避する。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できるようにする。あるいは、少なくとも繰り返しフィールドなどの複雑なルールを実装する必要を回避する。
- 通常は単純であるはずのRPCが、クエリパラメータでは表現できない可能性のあるデータを複雑な状況に対応するために含むことを可能にする。

### 前置詞の禁止

一般的に、名前に前置詞を含むメソッドは、新しいメソッドを導入する代わりに既存のメソッドにフィールドを追加すべき場合や、メソッドに別の動詞を使用すべき場合を示している。例えば、`CreateBook` メッセージが既に存在し、`CreateBookFromDictation` の追加を検討している場合は、代わりに `TranscribeBook` メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合は、`GetBookByAuthor` の代わりに、検索ディメンションとして `author` フィールドを持つ `SearchBooks` を検討する。これにより、APIとクライアントサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを加える、過度に特化したメソッドの急増を防ぐことができる。

### RPC名

「async」という用語は、RPCの作成を含め、特定のメソッド呼び出しが同期か非同期かを示すためにプログラミング言語で一般的に使用されている。その同期/非同期の側面は、RPC自体がlong-running operationを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名自体に「async」を使用すると混乱を招き、一部の言語ではRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成するクライアントライブラリに問題を引き起こすことさえある。
