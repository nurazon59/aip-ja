# カスタムメソッド

リソース指向設計（AIP-121）では、標準メソッドだけではモデル化が難しい任意のアクションを表現する手段として、カスタムメソッドを使用する。カスタムメソッドは、APIの語彙をユーザーの意図に適合させる手段を提供するため重要である。

## ガイダンス

カスタムメソッドは、標準メソッドでは容易に表現できない機能にのみ使用**すべきである**（should）。可能であれば、標準メソッドを優先すること（一貫したセマンティクスのため）。もちろん、これは問題の機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドを「なんとか動作させる」ために物事を歪めるのは良い考えでは*ない*。

カスタムメソッドの設計方法は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作するカスタムメソッドを示している。カスタムメソッドはリソース、コレクション、またはサービスに関連付けることができる。以下の箇条書きは3つのケースすべてに適用される。

- メソッド名は動詞の後に名詞が続く形と**すべきである**（should）。
  - 名前に前置詞（"for"、"with"など）を含め**てはならない**（must not）。
  - 名前に含まれる動詞は、標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）のいずれかを含む**べきではない**（should not）。
  - 名前に`Async`という語を含め**てはならない**（must not）。代わりに、即時RPCと長時間実行RPCを区別する意図がある場合、この目的のために接尾辞`LongRunning`を使用**してもよい**（may）。例えば、標準の`CreateBook`メソッドが長時間実行の側面を考慮する前に設計された場合、長時間実行の書籍作成RPCを作成するためには、カスタムの`CreateBookLongRunning`メソッドを導入できる。
- HTTPメソッドは`GET`または`POST`**でなければならない**（must）：
  - `GET`はデータまたはリソースの状態を取得するメソッドに使用**しなければならない**（must）。
    - リクエストペイロードがURLサイズ制限を超える可能性があり、`body`が必要となる場合、データ取得メソッドに`POST`を使用**してもよい**（may）。
  - `POST`は副作用があるか、リソースやデータを変更するメソッドに使用**しなければならない**（must）。
- HTTP URIは`:`文字の後にカスタム動詞（上記の例では`:archive`）を続けて使用**しなければならず**（must）、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合、`camelCase`を使用**しなければならない**（must）。
- `google.api.http`アノテーション内の`body`句は`"*"`と**すべきである**（should）。
  - 詳細については[HTTPとgRPCトランスコーディング][transcoding]を参照。
- カスタムメソッドはRPC名に一致し、`Request`接尾辞が付いたリクエストメッセージを受け取る**べきである**（should）。
- カスタムメソッドはRPC名に一致し、`Response`接尾辞が付いたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作する場合、カスタムメソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタムメソッド

APIがリソースとしてモデル化できる場合、カスタムメソッドはリソースに対して操作**しなければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは`name`と呼ば**なければならず**（must）、URIパス内の唯一の変数**でなければならない**（must）。

### コレクションベースのカスタムメソッド

ほとんどのカスタムメソッドは単一のリソースに対して操作するが、一部のカスタムメソッドは代わりにコレクションに対して操作し**てもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは`parent`と呼ば**なければならず**（must）、URIパス内の唯一の変数**でなければならない**（must）。
- コレクションキー（上記の例では`books`）はリテラル**でなければならない**（must）。

### ステートレスメソッド

一部のカスタムメソッドはリソースにまったく結びついていない。これらのメソッドは一般に*ステートレス*である：リクエストを受け取りレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例のプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名はスコープリソースの名前と**すべきである**（should）。単語の区切りが必要な場合、`snake_case`を使用**しなければならない**（must）。
- URIは`:`区切り文字の後に動詞と名詞の両方を配置**すべきである**（should）（この場合、コレクションが存在しないため、URI内の「疑似コレクションキー」を避ける）。例えば、`:translateText`は`text:translate`よりも好ましい。
- ステートレスメソッドは請求を伴う場合、`POST`を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは通常、カスタムメソッドを採用**すべきではない**（should not）（他のAIPで説明されている特定の宣言的フレンドリーなカスタムメソッドを除く）。これは、宣言的フレンドリーなツールがそれらをどう扱うべきかを自動的に判断できないためである。

この例外は、`Move`や`Rename`操作のように、宣言的サポートの期待がない、稀にしか使われない根本的に命令的な操作の場合である。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースやコレクションに対して操作するカスタムメソッドは、操作対象のリソースを示すための`name`または`parent`パラメータを必要とする。この規則により、クライアントはカスタムメソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET`と`POST`の両方のHTTP動詞を許可することで、どのメソッドがデータを変更せず、どのメソッドが変更するかが明確に区別される。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformのDataSources）で第一級の概念を持ち、ランタイムに影響を与えるリスクなしに呼び出せるメソッドをユーザーに明確に示す。

`GET`で行われるはずのリクエストに`POST`を使用できるようにすることは便宜上の措置である：

- URLサイズ制限に違反するリクエストにつながる大きなクエリ文字列を回避できる。
- クライアントがリクエストデータをシリアル化する単一の方法を実装できるか、少なくとも繰り返しフィールドなどの複雑なルールを実装する必要を回避できる。
- 通常は単純なRPCでも、クエリパラメータでは表現できない可能性のある複雑な状況のデータを保持できる。

### 前置詞の禁止

一般的に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべき箇所で新しいメソッドが使用されているか、またはメソッドが別個の動詞を使用すべきであることを示している。例えば、`CreateBook`メッセージが既に存在し、`CreateBookFromDictation`の追加を検討している場合、代わりに`TranscribeBook`メソッドを検討する。同様に、プロパティ固有の検索メソッドの要望がある場合、`GetBookByAuthor`の代わりに`author`フィールドを検索次元として持つ`SearchBooks`を検討する。これにより、APIとクライアントサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを加える過度に特化したメソッドの爆発的増加を防ぐことができる。

### RPC名

"async"という用語は、RPCの作成を含め、特定のメソッド呼び出しが同期的か非同期的かを示すためにプログラミング言語で一般的に使用されている。この同期的/非同期的な側面は、RPC自体が長時間実行オペレーションを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名自体に"async"を使用すると混乱を招き、一部の言語ではRPCを呼び出すために同期的メソッドと非同期的メソッドの両方を生成するクライアントライブラリに問題を引き起こすことさえある。
