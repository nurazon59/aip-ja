# カスタムメソッド

リソース指向設計（AIP-121）は、標準メソッドだけではモデル化が難しい任意のアクションを表現する手段として、カスタムメソッドを使用する。カスタムメソッドは、APIの語彙がユーザーの意図に沿う手段を提供するため、重要である。

## ガイダンス

カスタムメソッドは、標準メソッドでは容易に表現できない機能に対してのみ使用**すべきである**（should）。可能であれば、一貫したセマンティクスを持つ標準メソッドを優先すること。（もちろん、これは対象の機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドを「なんとか動作させる」ために物事を歪めるのは良いアイデアでは*ない*。）

カスタムメソッドの設計方法は多岐にわたるが、多くの原則が一貫して適用される。

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタムメソッドを示している。カスタムメソッドは、リソース、コレクション、またはサービスに関連付けることができる。以下の箇条書きは、これら3つのすべての場合に適用される。

- メソッド名は、動詞の後に名詞を続ける形**であるべきである**（should）。
  - 名前に前置詞（"for"、"with"など）を含め**てはならない**（must not）。
  - 名前に含まれる動詞は、標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）のいずれも含む**べきではない**（should not）。
  - 名前に `Async` という語を含め**てはならない**（must not）。代わりに、即時RPCと長時間実行RPCを区別する意図がある場合は、この目的のためにサフィックス `LongRunning` を使用**してもよい**（may）。例えば、長時間実行の書籍作成RPCを作成するために（標準の `CreateBook` メソッドが長時間実行の側面を考慮する前に設計された場合）、カスタムの `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` で**なければならない**（must）。
  - `GET` は、データまたはリソースの状態を取得するメソッドに使用**しなければならない**（must）。
    - `POST` は、リクエストペイロードがURLサイズの制限を超える可能性があり、そのため `body` が必要となるデータ取得メソッドに使用**してもよい**（may）。
  - メソッドが副作用を持つか、リソースやデータを変更する場合、`POST` を使用**しなければならない**（must）。
- HTTP URIは `:` 文字の後にカスタム動詞を続けた形式（上記の例では `:archive`）を使用**しなければならない**（must）。また、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` **であるべきである**（should）。
  - 詳細については [HTTP と gRPC トランスコーディング][transcoding] を参照。
- カスタムメソッドは、RPC名に一致し、`Request` サフィックスを付けたリクエストメッセージを受け取る**べきである**（should）。
- カスタムメソッドは、RPC名に一致し、`Response` サフィックスを付けたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作する場合、カスタムメソッドはリソース自体を返し**てもよい**（may）。

### リソースベースのカスタムメソッド

カスタムメソッドは、APIがそのようにモデル化できる場合、リソースに対して操作を行わ**なければならない**（must）。

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と名付けられ、URIパス内で唯一の変数で**なければならない**（must）。

### コレクションベースのカスタムメソッド

ほとんどのカスタムメソッドは単一のリソースに対して操作を行うが、一部のカスタムメソッドは代わりにコレクションに対して操作を行っ**てもよい**（may）。

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは `parent` と名付けられ、URIパス内で唯一の変数で**なければならない**（must）。
- コレクションキー（上記の例では `books`）はリテラルで**なければならない**（must）。

### ステートレスメソッド

一部のカスタムメソッドは、まったくリソースに関連付けられていない。これらのメソッドは一般的に*ステートレス*である。つまり、リクエストを受け取りレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例のようにプロジェクトなど）で実行される場合、リクエストメッセージのフィールド名はスコープリソースの名前に**すべきである**（should）。単語の区切りが必要な場合は、`snake_case` を使用**しなければならない**（must）。
- URIは、動詞と名詞の両方を `:` 区切り文字の後に配置**すべきである**（should）（この場合、コレクションが存在しないため、URIに「偽のコレクションキー」を置くことを避ける）。例えば、`:translateText` の方が `text:translate` よりも望ましい。
- ステートレスメソッドは、課金を伴う場合に `POST` を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは、通常はカスタムメソッドを使用**すべきではない**（should not）（他のAIPで議論される特定の宣言的フレンドリーなカスタムメソッドを除く）。なぜなら、宣言的フレンドリーなツールはそれらに対して何をすべきかを自動的に判断できないためである。

この例外は、`Move` や `Rename` 操作のような、めったに使用されず本質的に命令的な操作であり、宣言的サポートの期待がないものである。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースまたはコレクションに対して操作を行うカスタムメソッドは、操作対象のリソースを示すために `name` または `parent` パラメータを必要とする。この規約により、クライアントはカスタムメソッドを適切なリソースに対応付けることができる。

### HTTPメソッド

`GET` と `POST` の両方のHTTP動詞を許可することで、どのメソッドがデータを変更せず、どのメソッドが変更するのかを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformのDataSources）において第一級の概念であり、ランタイムに影響を与えるリスクなしにどのメソッドを呼び出せるかをユーザーに明確に示す。

通常であれば `GET` で行われるリクエストに `POST` を使用できるようにすることは利便性がある。

- URLサイズの制限に違反するような大きなクエリ文字列を回避できる。
- クライアントがリクエストデータを単一の方法でシリアライズできるようになり、少なくとも繰り返しフィールドなどの複雑なルールを実装する必要を回避できる。
- 通常は単純なRPCでも、クエリパラメータでは表現できない可能性のある複雑な状況のためのデータを保持できる。

### 前置詞の禁止

一般に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべきところで新しいメソッドが使われているか、またはメソッドが別の動詞を使うべきであることを示している。例えば、`CreateBook` メッセージがすでに存在し、`CreateBookFromDictation` の追加を検討している場合、代わりに `TranscribeBook` メソッドを検討すること。同様に、プロパティ固有の検索メソッドが必要な場合、`GetBookByAuthor` の代わりに、`author` フィールドを検索ディメンションとして持つ `SearchBooks` を検討すること。これは、APIとクライアントサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを加える過度に焦点を絞ったメソッドの爆発的な増加を防ぐのに役立つ。

### RPC名

「async」という用語は、RPCの実行を含め、特定のメソッド呼び出しが同期的か非同期的かを示すためにプログラミング言語で一般的に使用される。この同期/非同期の側面は、RPC自体がlong-running operationを開始することを意図しているかどうかとは、異なる抽象化レベルにある。RPC名自体に「async」を使用すると混乱を招き、一部の言語ではRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成するクライアントライブラリに問題を引き起こす可能性さえある。
