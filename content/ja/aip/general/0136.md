# カスタム メソッド

リソース指向設計（AIP-121）では、標準メソッドのみでモデル化するのが難しい任意のアクションを表現する手段を提供するために、カスタム メソッドを使用する。カスタム メソッドは、APIの語彙がユーザーの意図に従うための手段を提供するため重要である。

## ガイダンス

カスタム メソッドは、標準メソッドでは容易に表現できない機能に対して**のみ使用すべきである**（should）。可能であれば、その一貫したセマンティクスのために標準メソッドを優先する。（もちろん、これは問題の機能が実際に通常のセマンティクスに適合する場合にのみ適用される。標準メソッドが「なんとなく動く」ように無理に捻じ曲げようとするのは良くない考えである。）

カスタム メソッドは設計方法が大きく異なるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタム メソッドを示している。カスタム メソッドは、リソース、コレクション、またはサービスに関連付けることができる。以下の箇条書きは3つのケースすべてに適用される。

- メソッド名は動詞の後に名詞を続けたもの**であるべきである**（should）。
  - 名前に前置詞（"for"、"with"など）を含めて**はならない**（must not）。
  - 名前の動詞には標準メソッド動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）を含め**るべきではない**（should not）。
  - 名前には `Async` という用語を含めて**はならない**（must not）。代わりに、即時RPCと長時間実行RPCを区別する目的であれば、接尾辞 `LongRunning` をこの目的のために使用**してもよい**（may）。例えば、長時間実行の書籍作成RPCを作成する場合（標準の `CreateBook` メソッドが長時間実行の側面が考慮される前に設計された場合）、カスタム `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` **でなければならない**（must）：
  - `GET` は、データまたはリソース状態を取得するメソッドに使用**しなければならない**（must）。
    - `POST` は、リクエストペイロードがURLサイズ制限を超える可能性があり、`body` が必要となる場合に、データ取得メソッドに使用**してもよい**（may）。
  - `POST` は、メソッドに副作用がある場合やリソースやデータを変更する場合に使用**しなければならない**（must）。
- HTTP URIでは、`:` 文字の後にカスタム動詞を使用**しなければならず**（must）（上記の例では `:archive`）、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` **であるべきである**（should）。
  - 詳細については[HTTP and gRPC Transcoding][transcoding]を参照。
- カスタム メソッドは、RPC名に一致するリクエストメッセージを受け取る**べきであり**（should）、接尾辞は `Request` とする。
- カスタム メソッドは、RPC名に一致するレスポンスメッセージを返す**べきであり**（should）、接尾辞は `Response` とする。
  - 特定のリソースに対して操作を行う場合、カスタム メソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタム メソッド

APIがリソースとしてモデル化できる場合、カスタム メソッドはリソースに対して操作を行わ**なければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と**呼ばなければならず**（must）、URIパス内の唯一の変数**でなければならない**（must）。

### コレクションベースのカスタム メソッド

ほとんどのカスタム メソッドは単一のリソースに対して操作を行うが、一部のカスタム メソッドは代わりにコレクションに対して操作を行っ**てもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは `parent` と**呼ばなければならず**（must）、URIパス内の唯一の変数**でなければならない**（must）。
- コレクションキー（上記の例では `books`）はリテラル**でなければならない**（must）。

### ステートレスメソッド

一部のカスタム メソッドは、リソースにまったく関連付けられていない。これらのメソッドは一般に*ステートレス*である。つまり、リクエストを受け取りレスポンスを返すが、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例のプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名はスコープリソースの名前**であるべきである**（should）。単語の区切りが必要な場合は、`snake_case` を使用**しなければならない**（must）。
- URIでは、動詞と名詞の両方を `:` 区切り文字の後に配置**すべきである**（should）（この場合、コレクションが存在しないため、URI内の「疑似コレクションキー」を避ける）。例えば、`:translateText` は `text:translate` よりも好ましい。
- ステートレスメソッドは、課金を伴う場合に `POST` を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは通常、カスタム メソッドを使用**すべきではない**（should not）（他のAIPで説明されている特定の宣言的フレンドリーなカスタム メソッドを除く）。なぜなら、宣言的フレンドリーなツールはそれらを自動的にどう処理すればよいか判断できないからである。

この例外は、`Move` や `Rename` 操作のように、ごく稀にしか使用されず、本質的に命令的な操作であり、宣言的サポートが期待されない場合である。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースまたはコレクションに対して操作を行うカスタム メソッドは、操作対象のリソースを示すために `name` または `parent` パラメータを必要とする。この規約により、クライアントはカスタム メソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET` と `POST` の両方のHTTP動詞を許可することで、データを変更しないメソッドと変更するメソッドを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformのDataSources）で第一級の概念を持ち、どのメソッドが実行時の影響のリスクなしに呼び出せるかをユーザーに明確に示す。

他の方法では `GET` を使用するリクエストに `POST` を使用できるようにすることは、以下のような利便性のためである：

- 大きなクエリ文字列がURLサイズ制限に違反するリクエストを回避できる。
- クライアントがリクエストデータをシリアル化する単一の方法を実装できるか、または少なくとも繰り返しフィールドなどに対する複雑なルールを実装しなければならなくなるのを回避できる。
- 通常は単純であるはずのRPCでも、クエリパラメータでは表現できない複雑な状況のためのデータを含めることができる。

### 前置詞の禁止

一般に、前置詞を含むメソッド名は、代わりに既存のメソッドにフィールドを追加すべき、またはメソッドに別の動詞を使用すべき箇所で新しいメソッドが使われていることを示す。例えば、`CreateBook` メッセージが既に存在し、`CreateBookFromDictation` の追加を検討している場合、代わりに `TranscribeBook` メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合、`GetBookByAuthor` の代わりに、検索次元として `author` フィールドを持つ `SearchBooks` を検討する。これにより、APIやクライアントサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを追加するような、過度に特化したメソッドの爆発を防ぐことができる。

### RPC名

"async" という用語は、プログラミング言語で特定のメソッド呼び出しが同期か非同期か（RPCの実行を含む）を示すために一般的に使用される。その同期/非同期の側面は、RPC自体が長時間実行オペレーションを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名自体に "async" を使用すると混乱を招き、一部の言語でRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成するクライアント ライブラリで問題を引き起こすことさえある。
