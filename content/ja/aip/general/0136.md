# カスタムメソッド

リソース指向設計（AIP-121）では、カスタムメソッドを使用して、標準メソッドのみではモデル化が困難な任意のアクションを表現する手段を提供する。カスタムメソッドは、APIの語彙がユーザーの意図に沿うための手段を提供するため重要である。

## ガイダンス

カスタムメソッドは、標準メソッドで簡単に表現できない機能にのみ使用**すべきである**（should）。可能であれば、一貫したセマンティクスのために標準メソッドを優先する。（もちろん、これは問題の機能が実際に通常のセマンティクスに従っている場合にのみ適用される。標準メソッドを「なんとか動作」させるために無理に歪めるのは良い考えでは*ない*。）

カスタムメソッドの設計方法は多岐にわたるが、一貫して適用される原則が多くある：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して動作するカスタムメソッドを示している。カスタムメソッドはリソース、コレクション、またはサービスに関連付けることができる。以下の項目は3つのケースすべてに適用される。

- メソッド名は動詞の後に名詞が続く形式**すべきである**（should）。
  - 名前には前置詞（「for」「with」など）を含め**てはならない**（must not）。
  - 名前内の動詞には、標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）をいずれも含め**てはならない**（should not）。
  - 名前に`Async`という用語を含め**てはならない**（must not）。代わりに、即時RPCとlong-running RPCを区別する場合、サフィックス`LongRunning`をこの目的で使用**してもよい**（may）。例えば、long-runningな本の作成RPCを作成する場合（標準の`CreateBook`メソッドがlong-runningの側面が検討される前に設計された場合）、カスタムの`CreateBookLongRunning`メソッドを導入できる。
- HTTPメソッドは`GET`または`POST`**でなければならない**（must）：
  - `GET`はデータまたはリソースの状態を取得するメソッドに使用**しなければならない**（must）。
    - `POST`は、リクエストペイロードがURLサイズの制限を超える可能性があり、`body`を必要とする場合に、データ取得メソッドに使用**してもよい**（may）。
  - `POST`は、メソッドに副作用がある場合や、リソースまたはデータを変更する場合に使用**しなければならない**（must）。
- HTTP URIでは、`:`文字の後にカスタム動詞を続け（上記の例では`:archive`）、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase`を使用**しなければならない**（must）。
- `google.api.http`アノテーションの`body`句は`"*"`**すべきである**（should）。
  - 詳細については[HTTPとgRPCトランスコーディング][transcoding]を参照。
- カスタムメソッドは、RPC名に`Request`サフィックスを付けたリクエストメッセージを受け取る**べきである**（should）。
- カスタムメソッドは、RPC名に`Response`サフィックスを付けたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して動作する場合、カスタムメソッドはリソース自体を返し**てもよい**（may）。


### リソースベースのカスタムメソッド

APIがリソースとしてモデル化できる場合、カスタムメソッドはリソースに対して動作**しなければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは`name`と呼ば**なければならず**（must）、URIパス内で唯一の変数でなければならない。

### コレクションベースのカスタムメソッド

ほとんどのカスタムメソッドは単一のリソースに対して動作するが、一部のカスタムメソッドはコレクションに対して動作**してもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは`parent`と呼ば**れなければならず**（must）、URIパス内で唯一の変数でなければならない。
- コレクションキー（上記の例では`books`）はリテラル**でなければならない**（must）。

### ステートレスメソッド

一部のカスタムメソッドは、リソースにまったく関連付けられない。これらのメソッドは一般に*ステートレス*である：リクエストを受け取りレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例のようにプロジェクトなど）で実行される場合、リクエストメッセージ内のフィールド名はスコープリソースの名前**すべきである**（should）。単語の区切りが必要な場合は、`snake_case`を使用**しなければならない**（must）。
- URIは`:`区切りの後に動詞と名詞の両方を配置**すべきである**（should）（この場合、コレクションが存在しないため、URI内の「擬似コレクションキー」を避ける）。例えば、`:translateText`は`text:translate`よりも好ましい。
- ステートレスメソッドは、課金を伴う場合に`POST`を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは通常、カスタムメソッドを使用**すべきではない**（should not）（他のAIPで説明されている特定の宣言的フレンドリーなカスタムメソッドを除く）。これは、宣言的フレンドリーなツールが自動的に何をすべきかを判断できないためである。

これに対する例外は、稀にしか使用されない、本質的に命令的な操作（`Move`や`Rename`操作など）であり、宣言的サポートが期待されないものである。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースまたはコレクションに対して動作するカスタムメソッドは、操作対象のリソースを示す`name`または`parent`パラメータを必要とする。この規則により、クライアントはカスタムメソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET`と`POST`の両方のHTTP動詞を許可することで、データを変更しないメソッドと変更するメソッドを明確に区別できる。データの読み取りのみを行うメソッドは、一部のクライアント（TerraformのDataSources）においてファーストクラスの概念を持ち、ランタイムへの影響リスクなしに呼び出せるメソッドをユーザーに明確に示す。

`GET`で行われるリクエストに`POST`を使用できることは利便性である：

- URLサイズ制限に違反するリクエストにつながる大きなクエリ文字列を回避する。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できるか、少なくともrepeatedフィールドなどに対する複雑なルールを実装する必要を回避する。
- 通常は単純なRPCであっても、クエリパラメータで表現できないデータを含む複雑な状況に対応できるようにする。

### 前置詞の禁止

一般に、名前に前置詞を含むメソッドは、既存のメソッドにフィールドを追加すべきところで新しいメソッドを使用しているか、メソッドが別の動詞を使用すべきであることを示している。例えば、`CreateBook`メッセージが既に存在し、`CreateBookFromDictation`の追加を検討している場合、代わりに`TranscribeBook`メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合、`GetBookByAuthor`ではなく、検索次元として`author`フィールドを持つ`SearchBooks`を検討する。これにより、APIとクライアントサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを加える過度に特化したメソッドの爆発的増加を防ぐ。

### RPC名

「async」という用語は、RPC作成を含む特定のメソッド呼び出しが同期か非同期かを示すためにプログラミング言語で一般的に使用される。この同期/非同期の側面は、RPC自体がlong-running operationを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名自体に「async」を使用すると混乱を招き、一部の言語でRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成するクライアントライブラリに問題を引き起こす可能性さえある。
