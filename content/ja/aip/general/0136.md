# カスタムメソッド

リソース指向設計（AIP-121）では、標準メソッドだけではモデル化が難しい任意のアクションを表現する手段としてカスタムメソッドを使用する。カスタムメソッドは、APIの語彙をユーザーの意図に適合させる手段を提供するため重要である。

## ガイダンス

カスタムメソッドは、標準メソッドでは簡単に表現できない機能に対してのみ使用**すべきである**（should）；可能であれば、一貫したセマンティクスを持つ標準メソッドを優先する。（もちろん、これは問題の機能が実際に通常のセマンティクスに準拠する場合にのみ適用される；標準メソッドを「なんとか動作させる」ために物事を歪曲するのは _良い考えではない_。）

カスタムメソッドの設計方法は多岐にわたるが、多くの原則が一貫して適用される：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

**注:** 上記のパターンは、特定のリソースに対して操作を行うカスタムメソッドを示している。カスタムメソッドは、リソース、コレクション、またはサービスに関連付けることができる。以下の箇条書きは、3つのケースすべてに適用される。

- メソッドの名前は、動詞の後に名詞が続く形に**すべきである**（should）。
  - 名前に前置詞（"for"、"with"など）を含め**てはならない**（must not）。
  - 名前の動詞に標準メソッドの動詞（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）を含め**るべきではない**（should not）。
  - 名前に `Async` という語を含め**てはならない**（must not）。代わりに、即時RPCとlong-running RPCを区別することが目的の場合、この目的のために接尾辞 `LongRunning` を使用**してもよい**（may）。例えば、long-runningな書籍作成RPCを作成する場合（標準の `CreateBook` メソッドがlong-runningの側面を考慮する前に設計された場合）、カスタムの `CreateBookLongRunning` メソッドを導入できる。
- HTTPメソッドは `GET` または `POST` で**なければならない**（must）：
  - データやリソースの状態を取得するメソッドには `GET` を使用**しなければならない**（must）。
    - リクエストペイロードがURLサイズ制限を超える可能性があり、`body` が必要となる場合、データ取得メソッドに `POST` を使用**してもよい**（may）。
  - メソッドに副作用がある場合やリソースやデータを変更する場合は `POST` を使用**しなければならない**（must）。
- HTTP URIでは `:` 文字の後にカスタム動詞（上記の例では `:archive`）を続け**なければならない**（must）。また、URI内の動詞はRPC名の動詞と一致**しなければならない**（must）。
  - 単語の区切りが必要な場合は、`camelCase` を使用**しなければならない**（must）。
- `google.api.http` アノテーションの `body` 句は `"*"` に**すべきである**（should）。
  - 詳細については、[HTTP and gRPC Transcoding][transcoding]を参照。
- カスタムメソッドは、RPC名に `Request` 接尾辞を付けたリクエストメッセージを受け取る**べきである**（should）。
- カスタムメソッドは、RPC名に `Response` 接尾辞を付けたレスポンスメッセージを返す**べきである**（should）。
  - 特定のリソースに対して操作を行う場合、カスタムメソッドはそのリソース自体を返し**てもよい**（may）。


### リソースベースのカスタムメソッド

APIをリソースとしてモデル化できる場合、カスタムメソッドはリソースに対して操作を行わ**なければならない**（must）：

```proto
// Archives the given book.
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

- リソース名のパラメータは `name` と**しなければならない**（must）。また、URIパス内の唯一の変数でなければならない。

### コレクションベースのカスタムメソッド

ほとんどのカスタムメソッドは単一のリソースに対して操作を行うが、一部のカスタムメソッドは代わりにコレクションに対して操作を行っ**てもよい**（may）：

```proto
// Sorts the books from this publisher.
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

- コレクションのリソースに親がある場合、そのリソースは `parent` と**しなければならない**（must）。また、URIパス内の唯一の変数でなければならない。
- コレクションキー（上記の例では `books`）はリテラルで**なければならない**（must）。

### ステートレスメソッド

一部のカスタムメソッドは、リソースにまったく関連付けられない。これらのメソッドは一般に _ステートレス_ である：リクエストを受け取りレスポンスを返し、API内のデータに永続的な影響を与えない。

```proto
// Translates the provided text from one language to another.
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

- メソッドが特定のスコープ（上記の例ではプロジェクトなど）で実行される場合、リクエストメッセージのフィールド名はスコープリソースの名前に**すべきである**（should）。単語の区切りが必要な場合は、`snake_case` を使用**しなければならない**（must）。
- URIでは、`:` 区切りの後に動詞と名詞の両方を配置**すべきである**（should）（この場合、コレクションが存在しないため、URIに「疑似コレクションキー」を使用しない）。例えば、`:translateText` は `text:translate` よりも望ましい。
- ステートレスメソッドは、課金を伴う場合に `POST` を使用**しなければならない**（must）。

### 宣言的フレンドリーなリソース

宣言的フレンドリーなリソースは、通常カスタムメソッドを採用**すべきではない**（should not）（他のAIPで議論されている特定の宣言的フレンドリーなカスタムメソッドを除く）。これは、宣言的フレンドリーなツールがそれらをどう扱うべきかを自動的に判断できないためである。

この例外として、`Move` や `Rename` 操作など、宣言的サポートの期待がない、ほとんど使用されない根本的に命令的な操作がある。

## 根拠

### HTTPパス

標準メソッドと同様に、リソースまたはコレクションに対して操作を行うカスタムメソッドには、操作対象のリソースを示す `name` または `parent` パラメータが必要である。この規則により、クライアントはカスタムメソッドを適切なリソースにマッピングできる。

### HTTPメソッド

`GET` と `POST` の両方のHTTP動詞を許可することで、データを変更しないメソッドとデータを変更するメソッドを明確に区別できる。データを読み取るだけのメソッドは、一部のクライアント（TerraformのDataSources）でファーストクラスの概念として扱われ、ランタイムへの影響リスクなしにどのメソッドを呼び出せるかをユーザーに明確に示す。

通常なら `GET` で行われるリクエストに `POST` の使用を許可することは便宜上の措置である：

- URLサイズ制限に違反するような大きなクエリ文字列を回避できる。
- クライアントがリクエストデータをシリアライズする単一の方法を実装できるか、少なくとも繰り返しフィールドなどの複雑なルールを実装する必要がなくなる。
- 通常は単純なRPCでも、クエリパラメータで表現できない複雑な状況のデータを含めることができる。

### 前置詞の禁止

一般的に、前置詞を含むメソッド名は、既存のメソッドにフィールドを追加すべき箇所で新しいメソッドが使用されているか、またはメソッドに別の動詞を使用すべきであることを示す。例えば、`CreateBook` メッセージが既に存在し、`CreateBookFromDictation` の追加を検討している場合、代わりに `TranscribeBook` メソッドを検討する。同様に、プロパティ固有の検索メソッドが必要な場合、`GetBookByAuthor` の代わりに、`author` フィールドを検索ディメンションとして持つ `SearchBooks` を検討する。これにより、APIとクライアントのサーフェスを肥大化させ、APIの管理と利用の両方に複雑さを加える、過度に特化したメソッドの爆発を防ぐことができる。

### RPC名

"async"という用語は、RPCの作成を含め、特定のメソッド呼び出しが同期か非同期かを示すためにプログラミング言語で一般的に使用されている。この同期/非同期の側面は、RPC自体がlong-running operationを開始することを意図しているかどうかとは異なる抽象化レベルにある。RPC名自体に"async"を使用すると混乱を招き、一部の言語でRPCを呼び出すための同期メソッドと非同期メソッドの両方を生成するクライアントライブラリに問題を引き起こす可能性さえある。
