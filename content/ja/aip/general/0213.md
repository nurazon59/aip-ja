# 共通コンポーネント

[AIP-215][]で規定されているように、APIは、複数のAPIによる使用を意図した「共通コンポーネント」パッケージの使用を除き、自己完結型で**なければならない**（must）。

共通コンポーネントパッケージには2種類ある：

- 組織固有の共通コンポーネント。Maps の「ビューポート」のような組織固有の概念をカバーする。
- 汎用的な（つまりドメイン固有でない）グローバル共通コンポーネント。「タイムスタンプ」や「住所」など。

複数のAPIにわたって単一の表現を共有することが安全である場合、共通コンポーネントはクライアントがそれらのAPIとやり取りしやすくすることができる。例えば、概念固有のクライアントコードを一度記述すればよく、あるAPIのレスポンスからのメッセージを別のAPIのリクエストで、不格好なコピーなしに使用できる。

しかし、この利点には重大な制約と制限が伴い、軽々しく試み**るべきではない**（should not）。

コンポーネントの*ドメイン*が一般的であっても、コンポーネントの要件は組織固有である場合があることに注意する。例えば、ある組織では財務価値の表現方法に特定の要件がある場合があり、その結果、複数の財務指向の組織固有の共通コンポーネントが生まれる — なぜなら、グローバルな共通コンポーネントは組織固有の要件を満たさないか、あるいは一般的な使用には複雑すぎるかのいずれかだからである。

## ガイダンス

- 組織全体の共通コンポーネントパッケージは、`.type` で終わ**らなければならない**（must）。例：`google.geo.type` や `google.shopping.type`。
- 組織は、新しい組織全体の共通コンポーネントパッケージを作成する前に、API設計チームに相談**しなければならない**（must）。
- 組織全体の共通コンポーネントパッケージは、[`googleapis` リポジトリ](https://github.com/googleapis/googleapis)で公開**されなければならない**（must）。
- 新しい組織全体の共通コンポーネントパッケージを作成および公開する組織は、このAIPを更新して[以下のリスト](#existing-organization-specific-common-component-packages)に含め**なければならない**（must）。
- 組織は、組織固有の共通コンポーネントパッケージ内に汎用コンポーネントを定義**してはならない**（must not）。代わりにグローバル共通コンポーネントを優先する。
- 共通コンポーネントは、組織固有の共通コンポーネントパッケージからグローバルな共通コンポーネントパッケージへ、またはその逆へ「移動」（すなわち、ある共通コンポーネントパッケージから削除し、別の共通コンポーネントパッケージに追加すること）**されてはならない**（must not）。
  - 共通コンポーネントが当初の想定よりも広く適用可能であることが判明した場合、（元のコンポーネントを削除せずに）組織固有の共通コンポーネントパッケージからグローバルな共通コンポーネントパッケージへコピー**してもよい**（may）。
- 既存のメッセージにフィールドを追加**すべきではない**（should not）。
- 既存の enum に値を追加**すべきではない**（should not）。
- 既存のメッセージからフィールドを削除**してはならない**（must not）。
- 既存の enum から値を削除**してはならない**（must not）。
- ドキュメントの明確化は**してもよい**（may）が、既存の値の意味（特定のメッセージやメッセージセットの有効性を含む）を変更**すべきではない**（should not）。
- 新しい proto メッセージと enum は、共通コンポーネントパッケージに追加**してもよい**（may）。
  - APIチームは、新しいメッセージや enum を API で使用する前に、クライアントへの伝播に十分な時間を確保**すべきである**（should）。フィールドの変更がクライアントライブラリやその他のサーフェスへの公開を通じて伝播するには、ある程度の時間がかかる場合がある。
  - APIチームは、上記の制限のため、新しいメッセージや enum を追加する前に、組織内で広く相談し、理想的にはAPI設計チームにも相談**すべきである**（should）。

## 既存のグローバル共通コンポーネント

APIの公開向け proto が安全にインポート**してもよい**（may）グローバル共通コンポーネントは以下のとおりである：

- [`google.api.*`](https://github.com/googleapis/googleapis/blob/master/google/api)（ただし `google.api` のサブパッケージを除く）
- [`google.longrunning.Operation`](https://github.com/googleapis/googleapis/blob/master/google/longrunning/operations.proto)
- [`google.protobuf.*`](https://github.com/protocolbuffers/protobuf/tree/master/src/google/protobuf)
- [`google.rpc.*`](https://github.com/googleapis/googleapis/blob/master/google/rpc/)
- [`google.type.*`][type]

一部の共通コンポーネントには内部専用フィールドが含まれる場合があることに注意する。APIは通常、[オープンソースでリリースされた](https://github.com/googleapis/googleapis)フィールドのみに依存**すべきである**（should）。

Google APIは、Google全体で使用される IAM メッセージを提供する [`google.iam.v1.*`][iam] をインポート**してもよい**（may）。

<!-- prettier-ignore -->
[iam]: https://github.com/googleapis/googleapis/tree/master/google/iam/v1

**注:** 多くのAPIは、内部専用の使用のために他のパッケージからコンポーネントもインポートしている（可視性ラベルの適用や内部インフラストラクチャへの指示提供など）。これは、_公開_ コンポーネントにそのような参照が含まれていない場合に限り許容される。

### Protobuf 型

`google.protobuf` パッケージは、APIツールではなく Protocol Buffers 自体に同梱されているという点でやや特殊である。（ほとんどのAPI設計者にとって、これは実装の詳細であるべきである。）

このパッケージには、一般的なプログラミング言語の構造を表現するのに役立つ型の小さなライブラリが含まれている：

- [`google.protobuf.Duration`][duration]: ナノ秒精度の Duration。protobuf ランタイムは、該当する場合に言語ネイティブの Duration オブジェクト（Python の [`timedelta`][timedelta] など）との相互変換用のヘルパー関数を提供する。
- [`google.protobuf.Struct`][struct]: JSON ライクな構造（プリミティブ、リスト、その他の辞書で構成される辞書）。protobuf ランタイムは、ほとんどの言語で struct オブジェクトと JSON を相互変換するヘルパー関数を提供する。
- [`google.protobuf.Timestamp`][timestamp]: ナノ秒精度のタイムスタンプ。protobuf ランタイムは、ほとんどの言語で言語ネイティブのタイムスタンプオブジェクト（Python の [`datetime`][datetime] など）との相互変換用のヘルパー関数を提供する。

### API 型

`google.type` パッケージは、APIで一般的な概念を表現するのに役立つ型の「標準ライブラリ」を提供する。型は随時追加され、決定版のリストは常に[コード][type]であるが、いくつかの型は特筆に値する：

- [`google.type.Color`][color]: RGB または RGBA カラー。
- [`google.type.Date`][date]: 時刻やタイムゾーン要素を含まないカレンダー日付。
- [`google.type.DayOfWeek`][day_of_week]: 日付、時刻、タイムゾーンの要素を含まない曜日。
- [`google.type.LatLng`][lat_lng]: 地理座標。
- [`google.type.Money`][money]: 通貨。
- [`google.type.PostalAddress`][postal_address]: ほとんどの国における住所。
- [`google.type.TimeOfDay`][time_of_day]: 日付やタイムゾーン要素を含まない壁時計時刻。

### 共通 proto への追加

時折、これらのパッケージに proto を追加したり、共通利用可能な proto のリストに追加したりすることが有用な場合がある。これを行うには、GitHub 上の AIP リポジトリで [Issue を作成し][open an issue]、上記のガイドラインに注意すること。

## 非準拠の共通コンポーネントパッケージ

以下の共通コンポーネントパッケージは存在するが、上記のガイダンスに準拠しておらず、さらなる同様のパッケージの前例とはならない。

- [`google.cloud.common`](https://github.com/googleapis/googleapis/tree/master/google/cloud/common):
  パッケージ名が `.type` で終わらなければならないという要件に準拠していない。（これ以外の点では許容され、このパッケージは Cloud の共通コンポーネントパッケージと見なすべきである。）
- [`google.logging.type`](https://github.com/googleapis/googleapis/tree/master/google/logging/type):
  API固有のように見えるが、複数のAPIから使用されている。一部の側面はおそらくグローバルまたは Cloud の共通コンポーネントパッケージに含めるべきである。
- [`google.cloud.workflows.type`](https://github.com/googleapis/googleapis/tree/master/google/cloud/workflows/type):
  API固有の型。
- [`google.cloud.oslogin.common`](https://github.com/googleapis/googleapis/tree/master/google/cloud/oslogin/common):
  API固有の型であり、非準拠の名前である。
- [`google.identity.accesscontextmanager.type`](https://github.com/googleapis/googleapis/tree/master/google/identity/accesscontextmanager/type):
  API固有の型。
- [`google.networking.trafficdirector.type`](https://github.com/googleapis/googleapis/tree/master/google/networking/trafficdirector/type):
  API固有の型。

## 根拠

共通コンポーネントは事実上バージョン管理されていない。APIは定義と実装の両面で互いに独立して進化する。フィールドの追加のような変更は、特定のAPIにおいて後方互換性があり予測可能であり、APIチームはAPI定義が公開される前にサーバー実装が利用可能であることを保証できる。これに対し、共通コンポーネントの変更は、たとえほとんどのAPI実装がそれを考慮に入れていなくても、事実上普遍的に利用可能になってしまう。

新しいメッセージや enum の追加は後方互換性がある。同じ共通コンポーネントパッケージから他のメッセージや enum をインポートする可能性のある既存APIに影響を与えないからである。

API設計チームとの相談は、グローバル共通コンポーネントでは必須であり、組織固有の共通コンポーネントでは推奨される。なぜなら、「汎用的」と「組織固有」の境界はグレーゾーンであり、一部の汎用的な*概念*は組織固有のユースケースを持ち、それがコンポーネントを通じて表面化するからである。
