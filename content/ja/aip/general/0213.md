# 共通コンポーネント

[AIP-215][]で規定されているように、APIは、複数のAPIで使用することを目的とした「共通コンポーネント」パッケージの使用を除き、自己完結的で**なければならない**（must）。

共通コンポーネントパッケージには2種類ある：

- 組織固有の共通コンポーネント。Mapsの「viewport」のような組織固有の概念をカバーする。
- 汎用的（つまりドメイン固有でない）なグローバル共通コンポーネント。「timestamp」や「postal address」など。

単一の表現を複数のAPI間で安全に共有できる場合、共通コンポーネントはクライアントがそれらのAPIとやり取りするのを容易にすることができる。概念固有のクライアントコードは一度書くだけでよく、例えばメッセージをあるAPIのレスポンスから別のAPIのリクエストへと、煩雑なコピーなしで使用できる。

ただし、この利点には重大な制約と制限が伴い、軽々しく試みる**べきではない**（should not）。

コンポーネントの*ドメイン*が共通であっても、コンポーネントの要件は組織固有である可能性があることに注意すること。例えば、一部の組織では財務値の表現方法に特定の要件があり、その結果、複数の財務指向の組織固有の共通コンポーネントが存在することになる。これは、どのグローバル共通コンポーネントも組織固有の要件を満たさないか、一般的使用には複雑すぎるかのいずれかになるためである。

## ガイダンス

- 組織全体の共通コンポーネントパッケージは、`.type`で終わら**なければならない**（must）。例：`google.geo.type`または`google.shopping.type`。
- 組織は、新しい組織全体の共通コンポーネントパッケージを作成する前に、API設計チームに相談**しなければならない**（must）。
- 組織全体の共通コンポーネントパッケージは、[`googleapis`リポジトリ](https://github.com/googleapis/googleapis)で公開**しなければならない**（must）。
- 新しい組織全体の共通コンポーネントパッケージを作成・公開する組織は、本AIPを更新して[以下のリスト](#existing-organization-specific-common-component-packages)に含め**なければならない**（must）。
- 組織は、組織固有の共通コンポーネントパッケージ内に汎用コンポーネントを定義**してはならない**（must not）。代わりにグローバル共通コンポーネントを優先する。
- 共通コンポーネントを、組織固有の共通コンポーネントパッケージからグローバル共通コンポーネントパッケージへ、またはその逆へと「移動」（つまり、ある共通コンポーネントパッケージから削除し、別のパッケージに追加すること）**してはならない**（must not）。
  - 当初の想定よりも広く適用可能であることが判明した場合、共通コンポーネントを組織固有の共通コンポーネントパッケージからグローバル共通コンポーネントパッケージに（元のコンポーネントを削除せずに）コピー**してもよい**（may）。
- 既存のメッセージにフィールドを追加**すべきではない**（should not）。
- 既存のenumに値を追加**すべきではない**（should not）。
- 既存のメッセージからフィールドを削除**してはならない**（must not）。
- 既存のenumから値を削除**してはならない**（must not）。
- ドキュメントの明確化は**してもよい**（may）が、特定のメッセージや一連のメッセージの有効性を含め、既存の値の意味を変更**すべきではない**（should not）。
- 新しいprotoメッセージとenumは、共通コンポーネントパッケージに追加**してもよい**（may）。
  - APIチームは、新しいメッセージやenumをAPIで使用する前に、クライアントへの伝播に十分な時間を確保**すべきである**（should）。フィールドの変更がクライアントライブラリやその他のサーフェスへの公開を通じて伝播するには、ある程度の時間がかかる場合がある。
  - APIチームは、上記の制限のため、新しいメッセージやenumを追加する前に、組織内で広く相談し、理想的にはAPI設計チームにも相談**すべきである**（should）。

## 既存のグローバル共通コンポーネント

APIの公開向けprotoが安全にインポート**してもよい**（may）グローバル共通コンポーネントは以下の通りである：

- [`google.api.*`](https://github.com/googleapis/googleapis/blob/master/google/api)（ただし`google.api`のサブパッケージは*除く*）
- [`google.longrunning.Operation`](https://github.com/googleapis/googleapis/blob/master/google/longrunning/operations.proto)
- [`google.protobuf.*`](https://github.com/protocolbuffers/protobuf/tree/master/src/google/protobuf)
- [`google.rpc.*`](https://github.com/googleapis/googleapis/blob/master/google/rpc/)
- [`google.type.*`][type]

一部の共通コンポーネントには内部専用フィールドがある場合があることに注意すること。APIは一般に、[オープンソースにリリースされた](https://github.com/googleapis/googleapis)フィールドにのみ依存**すべきである**（should）。

Google APIは、Google全体で使用されるIAMメッセージを提供する[`google.iam.v1.*`][iam]をインポート**してもよい**（may）。

<!-- prettier-ignore -->
[iam]: https://github.com/googleapis/googleapis/tree/master/google/iam/v1

**注:** 多くのAPIは、内部専用の使用のために他のパッケージからコンポーネントもインポートしている（可視性ラベルを適用したり、内部インフラストラクチャに指示を提供したりするためなど）。これは_公開_コンポーネントにそのような参照が含まれていない限り、許容される。

### Protobuf型

`google.protobuf`パッケージは、APIツール群ではなくprotocol buffers自体に同梱されているという点で、やや特殊である。（ほとんどのAPI設計者にとって、これは実装の詳細であるべきである）。

このパッケージには、一般的なプログラミング言語の構文を表現するのに便利な型の小さなライブラリが含まれている：

- [`google.protobuf.Duration`][duration]：ナノ秒精度のduration。protobufランタイムは、該当する場合（Pythonの[`timedelta`][timedelta]など）、言語ネイティブのdurationオブジェクトとの変換を行うためのヘルパー関数を提供する。
- [`google.protobuf.Struct`][struct]：JSONライクな構造（プリミティブ、リスト、その他のディクショナリのディクショナリ）。protobufランタイムは、ほとんどの言語でstructオブジェクトをJSONとの間で変換するためのヘルパー関数を提供する。
- [`google.protobuf.Timestamp`][timestamp]：ナノ秒精度のタイムスタンプ。protobufランタイムは、ほとんどの言語で言語ネイティブのタイムスタンプオブジェクト（Pythonの[`datetime`][datetime]など）との変換を行うためのヘルパー関数を提供する。

### API型

`google.type`パッケージは、APIにおける一般的な概念を表現するのに便利な型の「標準ライブラリ」を提供する。型は随時追加され、最終的なリストは常に[コード][type]であるが、いくつかの型は特筆に値する：

- [`google.type.Color`][color]：RGBまたはRGBAカラー。
- [`google.type.Date`][date]：日付またはタイムゾーン成分を含まないカレンダー日付。
- [`google.type.DayOfWeek`][day_of_week]：他の日付、時刻、タイムゾーン成分を含まない曜日。
- [`google.type.LatLng`][lat_lng]：地理座標。
- [`google.type.Money`][money]：通貨。
- [`google.type.PostalAddress`][postal_address]：ほとんどの国の郵便住所。
- [`google.type.TimeOfDay`][time_of_day]：日付やタイムゾーン成分を含まない壁時計時刻。

### 共通protoへの追加

これらのパッケージにprotoを追加したり、一般的に利用可能なprotoのリストに追加したりすることが有用な場合がある。これを行うには、GitHubのAIPリポジトリで[issueを作成][open an issue]し、上記のガイドラインを明記すること。

## 非準拠の共通コンポーネントパッケージ

以下の共通コンポーネントパッケージは存在するが、上記のガイダンスに準拠しておらず、今後の同様のパッケージの先例とはならない。

- [`google.cloud.common`](https://github.com/googleapis/googleapis/tree/master/google/cloud/common):
  This does not conform to the requirement for the package name to end in `.type`. (This would otherwise
  be acceptable, and this package should be considered as the Cloud common component package.)
- [`google.logging.type`](https://github.com/googleapis/googleapis/tree/master/google/logging/type):
  This appears to be API-specific, although it's used from multiple APIs; some aspects should probably
  be global or in a Cloud common component package.
- [`google.cloud.workflows.type`](https://github.com/googleapis/googleapis/tree/master/google/cloud/workflows/type):
  API-specific types.
- [`google.cloud.oslogin.common`](https://github.com/googleapis/googleapis/tree/master/google/cloud/oslogin/common):
  API-specific types, and a non-conformant name.
- [`google.identity.accesscontextmanager.type`](https://github.com/googleapis/googleapis/tree/master/google/identity/accesscontextmanager/type):
  API-specific types.
- [`google.networking.trafficdirector.type`](https://github.com/googleapis/googleapis/tree/master/google/networking/trafficdirector/type):
  API-specific types.

## 根拠

共通コンポーネントは事実上バージョン管理されていない。APIは定義と実装の両方において互いに独立して進化する。フィールドの追加のような変更は、特定のAPIでは後方互換性があり予測可能であり、APIチームはAPI定義が公開される前にサーバー実装が利用可能であることを保証できる。対照的に、共通コンポーネントの変更は、ほとんどのAPI実装がそれを考慮していなくても、事実上普遍的に利用可能になる。

新しいメッセージやenumの追加は後方互換性がある。同じ共通コンポーネントパッケージから他のメッセージやenumをインポートする可能性のある既存のAPIに影響を与えないためである。

「汎用」と「組織固有」の境界はグレーゾーンであるため、グローバル共通コンポーネントについてはAPI設計チームへの相談が必須であり、組織固有の共通コンポーネントについても推奨される。一部の汎用的な*概念*には、コンポーネントを通じて表面化する組織固有のユースケースがある。
