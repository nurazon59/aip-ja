# 共通コンポーネント

[AIP-215][] で規定されているとおり、APIは、複数のAPIによる使用を意図した「共通コンポーネント」パッケージを除き、自己完結的で**なければならない**（must）。

共通コンポーネントパッケージには2種類ある：

- 組織固有の共通コンポーネント。Maps の「ビューポート」のような組織固有の概念を扱う。
- グローバルな共通コンポーネント。汎用的であり（つまりドメイン固有ではない）、「タイムスタンプ」や「郵便住所」などが該当する。

単一の表現を複数のAPI間で安全に共有できる場合、共通コンポーネントによってクライアントがそれらのAPIとやり取りしやすくなる。例えば、概念固有のクライアントコードを一度だけ記述し、あるAPIのレスポンスから取得したメッセージを別のAPIのリクエストでそのまま使用できるため、煩雑なコピーが不要になる。

しかし、この利点には重大な制約と制限が伴い、安易に試み**るべきではない**（should not）。

コンポーネントの*ドメイン*が共通であっても、コンポーネントの要件は組織固有である場合があることに注意。例えば、組織によっては金銭的価値の表現方法に特有の要件があり、その結果、金融指向の組織固有共通コンポーネントが複数生まれることがある。これは、グローバルな共通コンポーネントが組織固有の要件を満たさないか、汎用的に使うには複雑すぎるためである。

## ガイダンス

- 組織全体の共通コンポーネントパッケージは `.type` で終わら**なければならない**（must）。例：`google.geo.type` や `google.shopping.type`。
- 組織は、新しい組織全体の共通コンポーネントパッケージを作成する前にAPIデザインチームに相談**しなければならない**（must）。
- 組織全体の共通コンポーネントパッケージは、[`googleapis` リポジトリ](https://github.com/googleapis/googleapis)で公開**しなければならない**（must）。
- 新しい組織全体の共通コンポーネントパッケージを作成して公開する組織は、このAIPを更新し、[以下のリスト](#existing-organization-specific-common-component-packages)に追加**しなければならない**（must）。
- 組織は、組織固有の共通コンポーネントパッケージに汎用コンポーネントを定義**してはならない**（must not）。代わりにグローバルな共通コンポーネントを優先する。
- 共通コンポーネントを、組織固有の共通コンポーネントパッケージからグローバルな共通コンポーネントパッケージへ、またはその逆方向に「移動」**してはならない**（must not）（つまり、ある共通コンポーネントパッケージから削除して別のパッケージに追加すること）。
  - 当初の想定よりも広範に適用可能であることが判明した場合、共通コンポーネントを組織固有の共通コンポーネントパッケージからグローバルな共通コンポーネントパッケージに（元のコンポーネントを削除せずに）コピー**してもよい**（may）。
- フィールドを既存のメッセージに追加**すべきではない**（should not）。
- 値を既存の enum に追加**すべきではない**（should not）。
- フィールドを既存のメッセージから削除**してはならない**（must not）。
- 値を既存の enum から削除**してはならない**（must not）。
- ドキュメントの明確化は**してもよい**（may）が、既存の値の意味（特定のメッセージやメッセージ群の有効性を含む）を変更**すべきではない**（should not）。
- 新しい proto メッセージと enum を共通コンポーネントパッケージに追加**してもよい**（may）。
  - APIチームは、新しいメッセージや enum を API で使用する前に、クライアントへの伝播に十分な時間を確保**すべきである**（should）。フィールドの変更がクライアント ライブラリやその他のサーフェスへの公開を通じて伝播するには、ある程度の時間がかかる場合がある。
  - APIチームは、上記の制限事項のため、新しいメッセージや enum を追加する前に、組織内で広く相談し、理想的にはAPIデザインチームとも相談**すべきである**（should）。

## 既存のグローバル共通コンポーネント

APIの公開向け proto が安全にインポート**してもよい**（may）グローバルな共通コンポーネントは以下のとおりである：

- [`google.api.*`](https://github.com/googleapis/googleapis/blob/master/google/api)（ただし `google.api` のサブパッケージは除く）
- [`google.longrunning.Operation`](https://github.com/googleapis/googleapis/blob/master/google/longrunning/operations.proto)
- [`google.protobuf.*`](https://github.com/protocolbuffers/protobuf/tree/master/src/google/protobuf)
- [`google.rpc.*`](https://github.com/googleapis/googleapis/blob/master/google/rpc/)
- [`google.type.*`][type]

一部の共通コンポーネントには内部専用フィールドが含まれる場合があることに注意。APIは、一般的に、[オープンソースでリリースされた](https://github.com/googleapis/googleapis)フィールドにのみ依存**すべきである**（should）。

Google API は、Google全体で使用される IAM メッセージを提供する [`google.iam.v1.*`][iam] をインポート**してもよい**（may）。

<!-- prettier-ignore -->
[iam]: https://github.com/googleapis/googleapis/tree/master/google/iam/v1

**注:** 多くのAPIは内部専用の目的で他のパッケージのコンポーネントもインポートしている（例：可視性ラベルの適用や内部インフラストラクチャへの指示の提供）。これは、_公開_ コンポーネントにそのような参照が含まれていない限り許容される。

### Protobuf 型

`google.protobuf` パッケージは、APIツールではなく Protocol Buffers 自体と共に配布されるという点でやや特殊である（ほとんどのAPI設計者にとって、これは実装の詳細であるべきである）。

このパッケージには、一般的なプログラミング言語の構成要素を表現するのに役立つ小さな型ライブラリが含まれている：

- [`google.protobuf.Duration`][duration]：ナノ秒精度の期間。protobufランタイムは、該当する場合に言語ネイティブの duration オブジェクト（Pythonの [`timedelta`][timedelta] など）との変換用のヘルパー関数を提供する。
- [`google.protobuf.Struct`][struct]：JSONライクな構造（プリミティブ、リスト、および他の辞書からなる辞書）。protobufランタイムは、ほとんどの言語で struct オブジェクトとJSONの間の変換用のヘルパー関数を提供する。
- [`google.protobuf.Timestamp`][timestamp]：ナノ秒精度のタイムスタンプ。protobufランタイムは、ほとんどの言語で言語ネイティブのタイムスタンプオブジェクト（Pythonの [`datetime`][datetime] など）との変換用のヘルパー関数を提供する。

### API 型

`google.type` パッケージは、APIで一般的な概念を表現するのに役立つ型の「標準ライブラリ」を提供する。型は随時追加され、決定版のリストは常に[コード][type]であるが、いくつかの型は特筆に値する：

- [`google.type.Color`][color]：RGBまたはRGBA色。
- [`google.type.Date`][date]：日付またはタイムゾーンの要素を含まないカレンダー日付。
- [`google.type.DayOfWeek`][day_of_week]：他の日付、時刻、またはタイムゾーンの要素を含まない曜日。
- [`google.type.LatLng`][lat_lng]：地理座標。
- [`google.type.Money`][money]：通貨。
- [`google.type.PostalAddress`][postal_address]：ほとんどの国の郵便住所。
- [`google.type.TimeOfDay`][time_of_day]：日付またはタイムゾーンの要素を含まない壁時計時刻。

### 共通 proto への追加

これらのパッケージに proto を追加したり、一般的に利用可能な proto のリストに追加したりすることが有用な場合もある。これを行うには、GitHub の AIP リポジトリで [issue を作成][open an issue] し、上記のガイドラインを明記する。

## 非準拠の共通コンポーネントパッケージ

以下の共通コンポーネントパッケージは存在するが、上記のガイダンスに準拠しておらず、今後の同様のパッケージの前例とはならない。

- [`google.cloud.common`](https://github.com/googleapis/googleapis/tree/master/google/cloud/common)：
  パッケージ名が `.type` で終わるという要件に準拠していない。（このパッケージはそれ以外の点では許容され、Cloud 共通コンポーネントパッケージと見なすべきである。）
- [`google.logging.type`](https://github.com/googleapis/googleapis/tree/master/google/logging/type)：
  複数のAPIから使用されているにもかかわらず、API固有であるように見える。一部の側面はグローバルまたは Cloud 共通コンポーネントパッケージに含まれるべきであろう。
- [`google.cloud.workflows.type`](https://github.com/googleapis/googleapis/tree/master/google/cloud/workflows/type)：
  API固有の型。
- [`google.cloud.oslogin.common`](https://github.com/googleapis/googleapis/tree/master/google/cloud/oslogin/common)：
  API固有の型であり、非準拠の名前。
- [`google.identity.accesscontextmanager.type`](https://github.com/googleapis/googleapis/tree/master/google/identity/accesscontextmanager/type)：
  API固有の型。
- [`google.networking.trafficdirector.type`](https://github.com/googleapis/googleapis/tree/master/google/networking/trafficdirector/type)：
  API固有の型。

## 根拠

共通コンポーネントは事実上バージョン管理されていない。APIは定義と実装の両面で互いに独立して進化する。フィールドの追加のような変更は、特定のAPIでは後方互換性があり予測可能であり、APIチームはAPI定義を公開する前にサーバー実装が利用可能であることを確認できる。対照的に、共通コンポーネントの変更は、ほとんどのAPI実装がそれを考慮していなくても、事実上普遍的に利用可能になってしまう。

新しいメッセージや enum の追加は後方互換性がある。同じ共通コンポーネントパッケージから他のメッセージや enum をインポートする既存のAPIに影響を与えないためである。

グローバルな共通コンポーネントについてはAPIデザインチームとの相談が必須であり、組織固有の共通コンポーネントについては推奨される。「汎用的」と「組織固有」の境界はグレーゾーンであり、一部の汎用的な*概念*には組織固有のユースケースがあり、それがコンポーネントを通じて表出するためである。
